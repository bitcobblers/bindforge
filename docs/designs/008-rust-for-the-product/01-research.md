# Research: ADR-008 — Build the product in Rust; confine TypeScript to the pipeline

## Summary

The ADR's fixed framework choices (clap, Tauri v2, axum + Postgres via sqlx) are all current, actively maintained, and healthy as of November 2026; none is deprecated, but axum (0.8.x, 0.9 in development) and sqlx (0.9, recently moved to the `transact-rs` org) are pre-1.0 and their MSRVs (1.80, and clap's 1.74) set the repo's Rust floor. Cargo workspaces genuinely deliver the ADR's "one `cargo check` gates the product" claim via `cargo check --workspace` and workspace-wide inheritance of edition/version/lints, with one wrinkle: sqlx's compile-time query checks need a live `DATABASE_URL` (or its offline mode) at build time. Prior art strongly supports the shape: kanata and xremap chose Rust for input-path tooling, and Modrinth's app is a Rust/Tauri game launcher — while Heroic's Electron stack (~500MB) shows what Tauri's system-webview reuse avoids. The "formats are the contract" decision has mature precedent in the JSON Schema Test Suite (a language-agnostic golden-fixture suite run by validators in dozens of languages), and TOML v1.1.0 plus the format-preserving `toml_edit` crate fit the codec requirements. The sharpest open tension for the designer: Tauri's frontend is JS/TS and needs a Node build step, so "TypeScript stays in `tools/orchestration`" needs an explicit carve-out boundary.

## Findings

Workspace and tooling (verified against primary docs):

- A cargo workspace gives a shared `Cargo.lock`, one shared `target/` output dir, and commands that run across all members (`cargo check --workspace`), which is exactly the gate the ADR promises; Cargo explicitly recommends keeping members in a flat directory with a glob (`members = ["crates/*"]`), so the `crates/` + `apps/` split just needs two globs in `members` (source: https://doc.rust-lang.org/cargo/reference/workspaces.html).
- `[workspace.package]`, `[workspace.dependencies]`, and `[workspace.lints]` let the workspace pin edition, `rust-version` (MSRV), versions, and lint config once for all members (inherited with `workspace = true`); these require Rust 1.64+ / 1.74+ (source: https://doc.rust-lang.org/cargo/reference/workspaces.html).
- `cargo test --workspace` runs unit, integration, and doc tests for every member, and `--locked` gives deterministic CI builds; test binaries run with the package root as working directory, which suits per-crate golden fixtures (source: https://doc.rust-lang.org/cargo/commands/cargo-test.html).
- `cargo clippy` is the standard lint gate: 800+ lints in categories with default levels (`correctness` denies by default); `cargo fmt` is the rustfmt front end (source: https://doc.rust-lang.org/clippy/ ; https://rust-lang.github.io/rustfmt/).
- Rust 2024 is an edition, not a language version; it shipped in Rust 1.85.0 (20 Feb 2025). The repo should state an edition + `rust-version` floor in `[workspace.package]` (source: https://doc.rust-lang.org/edition-guide/rust-2024/index.html).
- Dependency freshness/MSRV as of Nov 2026: clap 4.6.7 (released 08 Nov 2026, MSRV 1.74, maintained under Rust's WG-CLI) (source: https://docs.rs/clap/latest/clap/); axum 0.8.9 on crates.io with `main` working toward breaking 0.9 changes, MSRV 1.80, `#![forbid(unsafe_code)]`, and no own middleware system — it consumes the `tower` ecosystem (timeouts, tracing, compression, rate limiting) for free (source: https://github.com/tokio-rs/axum ; https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html); sqlx is at 0.9 and its canonical repo has moved from `launchbadge/sqlx` to `transact-rs/sqlx` (source: https://github.com/launchbadge/sqlx).
- sqlx's headline feature — compile-time-checked queries (`query!`) — requires a real Postgres at compile time via `DATABASE_URL`, or a cached offline-mode checkout; the docs also note the macros do "quite a bit of work at compile time" (source: https://github.com/transact-rs/sqlx).

Formats are the contract (Standards lens):

- TOML's current spec is v1.1.0, and its stated design goal is data that maps unambiguously and is "easy to parse into data structures in a wide variety of languages" — implementations exist in 40+ languages, which is the community-tooling reach the ADR needs (source: https://toml.io/en/).
- Encoding-preserving codecs have a concrete foundation: `toml_edit` (0.25.19+spec-1.1.0) parses and modifies TOML "while preserving comments, spaces and relative order of items", and documents what it does *not* preserve (dotted-key order, trailing newline) — these belong in codec conformance fixtures (source: https://docs.rs/toml_edit/latest/toml_edit/).
- Golden-fixture conformance has a canonical prior art: the JSON Schema Test Suite is a language-agnostic collection of fixtures that validator implementers in dozens of languages run (typically as a git submodule), with the `main` branch kept stable and version-specific test directories — a directly copyable model for `schemas/` conformance tests (source: https://github.com/json-schema-org/JSON-Schema-Test-Suite).
- Key-name common denominators exist per platform, not globally: xremap names keys with Linux evdev codes (from the `evdev` crate's scancodes) and keeps its config "language-agnostic" (JSON-compatible, generatable from Ruby/Python) — precedent for ADR-009's OS-neutral key naming plus per-platform mapping tables (source: https://github.com/k0kubun/xremap).
- Hub untrusted-input posture: axum already refuses bodies over 2MB for `String`/`Json`/`Form` extractors by default (`DefaultBodyLimit`), and recommends `tower_http::limit` (`RequestBodyLimitLayer`) when accepting from untrusted remotes — the hub's upload policy should set explicit size caps on top (source: https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html).

Desktop stack:

- Tauri 2.0 hit stable and the line is current (the team announced the 2.12 release) (source: https://v2.tauri.app/blog/tauri-20/ ; https://v2.tauri.app/blog/).
- Tauri's core claims match the ADR's "no Node runtime to install": it uses the OS's own webview and does not bundle a browser engine — a minimal Tauri app is under 600KB — and the project undergoes security audits for major releases, including upstream dependencies (Radically Open Security v2 report) (source: https://v2.tauri.app/start/).
- Tauri v2's capabilities system grants granular permissions (JSON/TOML files under `src-tauri/capabilities`) to the webview per window/platform, and its docs are explicit that the boundary does *not* protect against malicious or insecure Rust core code — so the desktop threat model rests on `crates/adapters` quality, consistent with the ADR's "no escape hatch" note (source: https://v2.tauri.app/security/capabilities/).
- Node is not required to build Tauri apps that don't use a JS frontend framework; Node is listed as prerequisite "only if you intend to use a JavaScript frontend framework" — relevant to the desktop UI being deferred (source: https://v2.tauri.app/start/prerequisites/).

## Prior art

The prior-art lens (comparable solutions, names/formats, what they chose):

- **kanata** — cross-platform (Linux/macOS/Windows) keyboard remapper written in Rust; its README states it exists because its Haskell inspiration (kmonad) was hard for the author to contribute to, and ships prebuilt binaries plus `cargo install`; it grew a community ecosystem (tray app, VS Code language support, app-aware layer switchers). Direct evidence for the ADR bet that Rust attracts contributors in this exact niche (source: https://github.com/jtroo/kanata).
- **xremap** — Linux key remapper in Rust over `evdev`/`uinput`, advertising "faster than JIT-less interpreters like Python" and working identically on X11 and Wayland; config is language-agnostic YAML/JSON. Its configs, like kanata's `.kbd`, are tool-local and not designed for cross-game sharing — i.e., no existing binding-sharing format has won by convention; BindForge's `schemas/` fill a gap, they don't adopt a standard (source: https://github.com/k0kubun/xremap).
- **Modrinth App** — a shipping game/mod launcher "uses the Rust-based Tauri as the backend and Vue.js as the frontend": Rust core + web UI under one roof, the exact Tauri-era shape ADR-008 sketches (source: https://docs.modrinth.com/contributing/theseus/).
- **Goverlay** — Linux GUI that generates per-game config files (`MangoHud.conf`, `OptiScaler.ini`, …) in XDG-compliant per-game directories: the closest analog to `crates/adapters`/`crates/scanner`. It is Free Pascal/Qt6 (not Rust), and its Flatpak build hides host-dependent features (Protontricks, GameMode) because the sandbox "cannot reliably detect or execute host binaries" — a caution for game-filesystem scanning under Flatpak (source: https://github.com/benjamimgois/goverlay).
- **Heroic Games Launcher** — Electron-based launcher, ~500MB storage requirement per its FAQ: the runtime-weight counterexample justifying Tauri over Electron for a tool living on gamers' machines (source: https://heroicgameslauncher.com/faq).
- **JSON Schema Test Suite** — as above, the reference model for "reference implementation + language-neutral golden fixtures" that `schemas/` + `crates/core` propose to copy (source: https://github.com/json-schema-org/JSON-Schema-Test-Suite).

## Platform notes

Platform-notes lens, specific to BindForge's declared surface:

- **Proton prefixes**: Steam/Proton keep each game's Wine prefix at `steamapps/compatdata/[appid]/pfx` in the game's Steam library folder (Valve's Proton FAQ). Scanner/adapter path discovery must enumerate per-library `compatdata` dirs; `protontricks` exists as the prefix-management reference tool (source: https://github.com/ValveSoftware/Proton/wiki/Proton-FAQ ; https://github.com/Matoking/protontricks).
- **Windows packaging**: Tauri renders with Microsoft Edge WebView2; WebView2 is preinstalled on Windows 10 (from 1803) and Windows 11, but "some devices might not have the Runtime pre-installed," so the app installer should detect it (registry key or API) and deploy the ~2MB Evergreen bootstrapper (source: https://v2.tauri.app/start/prerequisites/ ; https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). Evergreen means the web platform auto-updates without the app's control — Microsoft recommends testing against Edge preview channels for forward-compatibility (source: https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution). Building MSI targets additionally needs the VBSCRIPT Windows optional feature, which Microsoft is deprecating (source: https://v2.tauri.app/start/prerequisites/).
- **Linux dev/packaging**: Tauri needs `libwebkit2gtk-4.1-dev` and friends (Debian list) — WebKitGTK availability per distro becomes a contributor and packaging constraint (source: https://v2.tauri.app/start/prerequisites/).
- **Flatpak**: default sandbox grants no host files, no device nodes, and no network; filesystem access is configured statically in the manifest (`--filesystem=...`, `--persist=...`), portals are preferred over blanket access, Flathub imposes permission requirements, and `--device=input` (Flatpak ≥1.15.6) is the narrow grant for `/dev/input` incl. controllers. A scanner that walks Steam libraries and Proton prefixes would need broad, possibly Flathub-hostile static permissions — AppImage/native packages may be the honest default (source: https://docs.flatpak.org/en/latest/sandbox-permissions.html ; Goverlay precedent: https://github.com/benjamimgois/goverlay).
- **Contributor prerequisite**: Rust via `rustup` is a one-command install and is required by Tauri development itself; clap and axum publish explicit MSRVs (1.74, 1.80) that become the repo floor candidates (source: https://v2.tauri.app/start/prerequisites/ ; https://docs.rs/clap/latest/clap/ ; https://github.com/tokio-rs/axum).

## Risks & unknowns

- **sqlx vs "one `cargo check`"**: compile-time-checked queries need `DATABASE_URL` (or cached offline mode) at build time, and the macros slow compiles — CI and `npm run check`-equivalent gating must plan a Postgres service or commit the offline cache (source: https://github.com/transact-rs/sqlx).
- **Pre-1.0 churn**: axum says `main` contains breaking changes toward 0.9 while 0.8.x is what ships (source: https://github.com/tokio-rs/axum); sqlx removed MSSQL in 0.7 pending rewrite and changed maintaining orgs (source: https://github.com/launchbadge/sqlx). Pin versions in `[workspace.dependencies]` and use `--locked` in CI (source: https://doc.rust-lang.org/cargo/commands/cargo-test.html).
- **Tauri's security model stops at the Rust core**: capabilities constrain the webview only; filesystem-writing adapter bugs are unmitigated, matching the ADR's accepted cost but demanding the codec layer get adversarial-fixture tests (source: https://v2.tauri.app/security/capabilities/).
- **Evergreen webview drift**: the web platform under the desktop UI updates without BindForge releasing, and some Windows 10 devices lack WebView2 entirely — the installer must detect/install it, and CI should test against preview channels (source: https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).
- **Flatpak vs file-scanning** is an unresolved conflict (see Platform notes) rather than a solved problem (source: https://docs.flatpak.org/en/latest/sandbox-permissions.html).
- **Format-preserving editing has known gaps** (dotted-key order, trailing newlines in `toml_edit`) that will surface in user-visible diffs if not pinned by conformance fixtures (source: https://docs.rs/toml_edit/latest/toml_edit/).
- **No standard schema language for TOML documents** with a test-suite ecosystem equivalent to JSON Schema: it is unknown whether `schemas/` definitions should be prose + golden fixtures only, or paired with a machine-checkable schema format; the JSON suite works because its fixtures are themselves JSON (source: https://github.com/json-schema-org/JSON-Schema-Test-Suite).

## Open questions

For the designer:

1. Where exactly does the "nothing user-facing in TypeScript" line fall once the Tauri desktop era lands — Tauri lists Node as prerequisite for a JS frontend framework, so an `apps/desktop` web UI would be JS/TS source with its own npm toolchain; is that an exempt frontend exception to ADR-008, or should the UI stay inside the pipeline's TS rules? (source: https://v2.tauri.app/start/prerequisites/)
2. Which edition and MSRV does the workspace commit to (edition 2024 requires Rust 1.85; clap wants 1.74+, axum 1.80+), and where is `rust-version` declared — workspace-inherited? (source: https://doc.rust-lang.org/edition-guide/rust-2024/index.html ; https://docs.rs/clap/latest/clap/ ; https://github.com/tokio-rs/axum)
3. How does CI gate `apps/hub` if `cargo check --workspace` triggers sqlx's compile-time query verification — ephemeral Postgres service container, or committed sqlx offline cache? (source: https://github.com/transact-rs/sqlx)
4. What is the packaging matrix (MSI/EXE, AppImage, deb, Flatpak) — and is Flatpak even viable given a game-filesystem scanner's static permission needs and Flathub's policy? (source: https://docs.flatpak.org/en/latest/sandbox-permissions.html)
5. What is the hub's upload policy beyond axum's default 2MB body cap — max file size, max chain depth, patch count — and does chain resolution need explicit recursion bounds for adversarial profiles? (source: https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html)
6. Do `schemas/` conformance obligations bind only BindForge's own formats (profile/patch/manifest/policy), or also third-party game formats (INI/TOML/UTF-16 quirks) that adapters must round-trip — the Goverlay ecosystem shows `.conf`/`.ini` variety (source: https://github.com/benjamimgois/goverlay)?
7. Are the "later hub era" Tauri v2 mobile targets (Android/iOS via `rustup target add`) ever wanted, and do they change the file-first product stance? (source: https://v2.tauri.app/start/prerequisites/)
