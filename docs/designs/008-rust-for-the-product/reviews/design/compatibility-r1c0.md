# Compatibility review r1

verdict: request-changes

Scope: whole document (pass c0). Inputs: `02-proposal.md`, `docs/adrs/008-rust-for-the-product.md`,
the Revision log (empty — "r0 initial draft", so every finding here is `new`).

## Findings

- [major][new] Compatibility matrix, macOS row — "| macOS | unknown | BindForge commits nothing; Tauri v2 itself supports 10.15+ (A16); desktop design decides |" — the checklist treats an `unknown` status as a finding: a matrix row whose status is unknown is not a compatibility statement, and here it also contradicts the document's own Deferred section, "Flatpak viability, macOS support, Tauri mobile targets — no follow-up yet; excluded for v1 per Compatibility matrix", which asserts the matrix *excludes* macOS while the matrix says `unknown`. The same `unknown` leaks into the "Contributor dev env" row, "Linux + Windows yes; macOS unknown", so a macOS contributor cannot tell whether the three cargo gate commands are expected to work for them. Fix: give both cells a definite status without taking on macOS work — set the product row to `no (v1 decision)` (the status the Deferred text already claims), and the contributor row to `Linux + Windows yes; macOS no (v1)`, or, if macOS contributor builds are wanted, name a macOS leg in Test strategy #8. Do not leave either cell `unknown`.

- [minor][new] Compatibility matrix / Chosen design — no row or sentence names an OS input API — the matrix is the document's compatibility statement, and it says nothing about X11 vs Wayland vs Windows Raw Input vs macOS HID, which the checklist requires to be either named per platform or justified as an abstraction. The design's own scope implies the answer (bindings travel as files under `schemas/`; `crates/scanner` does "installed-game detection, config fingerprinting (`compatdata` enumeration per A19)" — file reads, not event capture), but that justification is never stated, so a later reader can't tell whether input capture is out of scope or simply unaddressed. Fix: one sentence in the matrix notes (or Context): BindForge reads and writes binding *files* only; it never reads or injects input events, so no X11/Wayland/Raw Input/HID API is targeted, and any future component that captures input must name its API per platform in its own matrix.

- [minor][new] Compatibility matrix, Linux row — "| Linux (deb-based, WebKitGTK 4.1) | yes | dev deps per Tauri list (A16); shipping artifacts deb + AppImage |" — the row's status is scoped by packaging ("deb-based") while its own notes commit an AppImage artifact, which exists precisely for non-deb distros; the row therefore both claims and contradicts deb-only support. Consequence: Arch, Fedora and Steam Deck/SteamOS (read-only, not deb-based) have no status, even though the Proton-prefix work that makes those distros interesting is in this design's member table — "`crates/scanner` … (`compatdata` enumeration per A19)". Fix: relabel the row to the platform set, e.g. "Linux (glibc distros; artifacts deb + AppImage) | yes", and add a Steam Deck/SteamOS row with a status (`no (v1)` is acceptable if that is the decision) so the matrix says which Linux users get an artifact.

- [minor][new] Test strategy #8 vs Compatibility matrix — "the cargo gate must be green on the Linux CI runner; the `rust-toolchain.toml` auto-install is verified once on Linux and once on a Windows contributor machine during rollout" — the matrix claims Windows as supported twice ("Windows 10 (1803+) / 11 — desktop era | yes (target)" and "Contributor dev env | Linux + Windows yes"), but the only Windows platform check named is a rustup pin install; nothing anywhere establishes that `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, and `cargo test --workspace --locked` are green on Windows (path-length limits and case-insensitive filesystems are exactly where a Linux-only gate first breaks on Windows). Fix: add `windows-latest` to the `rust` job's runner matrix in `.github/workflows/check.yml` (or fold the same three commands into the one-time Windows verification in Rollout step 7, next to "Verify Test strategy #5"), and state in #8 that Windows gate greenness is verified there; otherwise downgrade the Windows contributor cell to `yes (toolchain only; gate unverified)`.

- [minor][new] Gates (ADR-008 clause 4), CI paragraph — "`orchestration` (`npm ci && npm run check` in `tools/orchestration`)" — this design creates the repo's first CI config (A23), so it owns the Node version that runs the pipeline gate, and none is named: on GitHub-hosted runners an unpinned job silently changes Node version when the image changes. That is asymmetric with the Rust side, where the stated goal is "A toolchain floor and pin so every contributor and CI job builds identically" (`rust-version = "1.85"` plus `rust-toolchain.toml channel = "1.85.0"`). Fix: name the Node floor once — a `setup-node` step with an explicit `node-version` (or a root `.nvmrc` the job reads) — and record the same floor in the `repo-practices` Rust/CI section added by Rollout step 5. No new Node API is introduced, so no floor violation exists today; the finding is the missing floor.

- [nit][new] Formats contract / Test strategy #1 — "walks every `schemas/*/v*/fixtures/{valid,invalid}` directory" — the fixture tree and harness ship with this design, and per the matrix the harness also runs on contributor Windows (case-insensitive, path-length-limited) while CI runs only on Linux, yet nothing constrains fixture file names, so two fixtures differing only in case or using non-ASCII names pass on the Linux runner and silently collide or fail locally. Fix: one clause in the versioning rule (mirrored in `schemas/README.md`): fixture file names are lowercase ASCII, `-`-separated, and case-unique within a fixture directory.

## FYI (no severity)

- Checklist item 5 (keyboard reality: non-QWERTY layouts, dead keys, IME, non-ASCII binding names): evaluated and not a finding here — the document hands it to ADR-009 via "Taxonomy ids, reach-table content, chain/patch/policy/manifest semantics and their fixture cases — owned by ADR-009", which is consistent with ADR-008 clause 3 ("`schemas/` … language-neutral, versioned definitions … plus golden-fixture conformance tests"). Worth carrying into ADR-009's fixture seeding: at least one valid fixture per format with a non-ASCII binding name and a layout-independent key identity, so third-party readers cannot conform to a QWERTY-only reading of `schemas/`.
- Checklist item 4 (native modules): clean — no Node native modules are introduced, `tools/orchestration` is untouched, and the packaging story for the product is compiled artifacts (deb + AppImage on Linux, NSIS primary on Windows) with the npm toolchain deferred to the desktop design, consistent with ADR-008 clause 2.
- Checklist item 6 (paths, config dirs): the only path work in scope uses `env!("CARGO_MANIFEST_DIR")` rather than hand-built strings, and config path discovery / write policy is deferred to ADR-012 exactly as ADR-008 clause 2 assigns it to `crates/adapters` — not a finding; ADR-012 will owe the per-OS conventions (XDG / AppData / Proton prefix layout).
- Assumption register gives MSRVs for clap (1.74) and axum (1.80) but not for sqlx 0.9 (A3); A25 covers it as unverified and the Risks row handles a floor bump, so it does not block the 1.85 floor — flagging for the correctness seat to weigh A25's "Med/Low" rating.
