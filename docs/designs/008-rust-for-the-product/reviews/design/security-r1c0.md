# security review r1

verdict: request-changes

## Findings

- [major][new] Chosen design — Formats contract, "Adversarial guard" (and Goals bullet "Chain resolution hardened against adversarial profile files — the precondition for the hub validating uploads with client types") — the design creates the parser that eats other people's files (`bindforge-core` is "reference implementation of `schemas/`", and the same compiled types validate hub uploads), but nowhere classifies its data sources. Nowhere does it say that a profile/patch/policy/manifest document read from disk, from another user, or from the network is UNTRUSTED at every entry point, nor that the guards it introduces (`Cycle`, `ChainTooDeep`, the version gate) apply regardless of entry point rather than only to the hub path. Every later document (ADR-009 semantics, ADR-012 codecs, ADR-014 uploads) inherits that unstated premise, and the conformance harness as written only ever parses in-repo trusted fixtures, so nothing in this design's own tests establishes the untrusted-input contract. Fix: one sentence at the head of "Adversarial guard": "profile, patch, policy, and manifest documents arriving from disk, from another user, or from the network are untrusted input at every entry point (CLI, desktop, hub); every guard in this section applies before any of them can reach a writer, and the invalid-fixture corpus is the contract for that behavior."

- [major][new] Deferred / out of scope — "upload caps beyond the chain guard (file size, patch counts — axum body-limit posture)" — the only input bound this design states is chain depth (`MAX_CHAIN_DEPTH = 32`). Size limits are handed to ADR-014, which owns only the hub's HTTP body posture; the local path — the CLI and the desktop app parsing a profile file "from elsewhere", the product's primary use case — keeps no bound, and `bindforge-core` (created by this design) is the parser there. A TOML document with no size or nesting bound means hostile input can end a parse in an allocator/stack failure rather than a typed error, which is exactly the "reject cleanly, never crash" failure the section claims to have solved. Fix: state an input budget next to `MAX_CHAIN_DEPTH` in the same sentence and mirror it in `schemas/README.md` the way the depth constant already is — a max document byte size and a max table/array nesting depth, both returned as typed errors — so the bound applies in core on every path and the ADR-014 body-limit deferral becomes redundant rather than load-bearing.

- [major][new] Chosen design — "Versioning rule (canonical, mirrored in `schemas/README.md`)" — "a document's declared version must name a major `crates/core` supports, else it is rejected with a structured error naming the supported majors". The rule constrains a *declared* version only; it never says what happens when the version is absent or empty, and a missing field is the most common malformed-input case. Defaulting it to `v1` fails open: a document written against a future major gets parsed by v1 semantics, which is the one thing versioning exists to prevent (and ADR-009's model can give future majors semantics that v1 would misapply). Test strategy #2 only covers "declaring an unsupported major version", so the gap is untested too. Fix: extend the canonical rule to "a document that declares no version is rejected with the same structured error", and add the missing-version case to Test strategy #2 plus an `invalid` fixture under the affected format.

- [major][new] Chosen design — "TypeScript boundary (clause 1; canonical)" — "everything it triggers is behavior in a workspace crate, reached through Tauri commands gated by capabilities under `apps/desktop/src-tauri/capabilities/` (A14)". The capability model is named as the control that keeps the webview presentation-only, but the design never constrains what the capability files may *grant*. Tauri's own history is the reason this matters: fs-scope grants have repeatedly been the weak seam (CVE-2022-46171 scope glob too permissive, CVE-2022-41874/CVE-2022-39215 scope bypass via symlink, CVE-2023-34460 dotfile regression), and `tauri-plugin-shell`'s `open` endpoint had a CVSS-4.0 scope-validation failure fixed only at 2.2.1 (CVE-2025-31477). If the desktop design enables the `fs`/`shell`/`dialog` plugins — the default, easy path — the webview can read and write game config files directly and the "presentation only" rule becomes decoration. A14 records only the other direction (capabilities don't restrain Rust core code). Fix: add to the boundary paragraph, and to the `repo-practices` Rust section bullet in Rollout step 5: "capability files enumerate only the app's own commands; the `fs`, `shell`, and `dialog` plugins are not enabled — file access happens in workspace crates, never through plugin scopes."

- [minor][new] Assumption register (A13) + members table ("`apps/desktop` … Tauri v2 app (A13)") — the design commits to Tauri v2 with no version floor. Advisory check for this seat found CVE-2026-42184 (GHSA-7gmj-67g7-phm9, CVSS 3.1 8.6): origin confusion letting a remote page invoke local-only IPC commands, affecting the whole `>= 2.0.0, < 2.11.1` range and fixed in 2.11.1; CVE-2024-35222 (iFrames bypass the origin check guarding Tauri API access) is in the same family. A13 says "2.12 line" is current but nothing in the design makes a patched floor a requirement, so the desktop era could pin 2.0.x from a stale template and the capability boundary above would already be bypassed at the framework level. Fix: one clause in the TypeScript boundary section: "capability-based isolation assumes a patched Tauri; the desktop design pins a `tauri` floor no lower than the release that fixes its current IPC/origin advisories (2.11.1 as of this design) in `[workspace.dependencies]`."

- [minor][new] Chosen design — "Gates (ADR-008 clause 4)" — the gate set is `fmt`, `clippy -D warnings`, `test --locked`. Nothing in the design or in the Rollout's `repo-practices` section keeps dependency advisories under watch, even though this design is the one that fixes the gate set, pins exact versions, and leaves A25 ("no direct or transitive dependency at merge needs rustc newer than 1.85") unverified. The committed `Cargo.lock` + `--locked` make the full graph known, which is precisely what an advisory scan needs; today the only check on the graph is a human reviewing an upgrade PR. Fix: add a fourth line to the gate block and the CI `rust` job — `cargo deny check advisories` with a committed `deny.toml` at the workspace root (a `cargo-audit` run is the fallback) — instead of leaving the advisory review informal.

- [minor][new] Chosen design — "Workspace shape" — "the channel equals `rust-version` and is bumped only when a reviewed dependency upgrade requires it". As written, the only sanctioned reason to move `1.85.0` is a dependency demand, so a rustc security advisory with a patch release has no defined path; contributors stay on a pinned compiler indefinitely because the policy forbids moving it. Fix: widen the clause to "bumped only when a reviewed dependency upgrade or a published security advisory in the toolchain requires it" — no new mechanism, it just stops the sentence from forbidding the obvious case.

- [minor][new] Chosen design — "Gates" — "`.github/workflows/check.yml` runs two independent jobs on every PR". This is the repo's first CI config (A23), so its permissions posture is this design's to set, and the `rust` job compiles contributor-authored code on every PR: cargo build scripts and proc macros in a PR's dependency graph execute arbitrary code on the runner. The design specifies commands but no runner posture. Fix: one sentence in the same paragraph — "`check.yml` declares `permissions: contents: read` at the job level and pins every third-party action to a commit SHA; PR-triggered runs get no write token" — before the workflow is written in Rollout step 4.

- [minor][new] Chosen design — "Harness" — "walks every `schemas/*/v*/fixtures/{valid,invalid}` directory, and asserts: every valid fixture parses and re-serializes to a semantically equal value; every invalid fixture is rejected". An empty or absent directory satisfies this trivially, so a format added later with no fixtures — or fixtures moved out of the expected glob — passes the gate while contributing zero conformance, and the versioning rule makes "a file's presence in `vN/fixtures/valid/` … the definition of 'supported'", so silent emptiness silently un-supports a format. The "at least one valid and one invalid fixture per format" requirement is prose in this section and Test strategy #1, not asserted by the harness. Fix: have `conformance.rs` fail when any `schemas/*/v*/` directory yields zero `valid` or zero `invalid` fixtures — the assertion replaces the prose promise rather than adding to it.

- [minor][new] Deferred / out of scope — the list names owners for semantics, codecs, hub policy, packaging and schemas, but no document is named as owning what a shared BindForge artifact reveals about its author: `crates/scanner` enumerates `compatdata` (A19) and therefore installed-game titles, and adapters' "config path discovery" puts absolute host paths into data that the product is built to share. Nothing records which of ADR-009 (manifest contents) or ADR-012 (fingerprinting) carries the "what may leave the machine, and what may a log contain" decision, so it can fall between them. Fix: add one Deferred bullet naming the owner (ADR-009 for manifest/scanner-derived fields that identify the user or host; ADR-012 for path redaction when fingerprinting), no new requirements.

- [nit][new] Deferred / out of scope — "Codec implementations, config path discovery, write policy, and conformance obligations for third-party game formats (INI/TOML/UTF-16 round-trips) — owned by ADR-012 (planned)" — the deferral matches ADR-008 clause 2, so it is not re-opened; but the security obligation inside it is unnamed. Fix: extend that bullet's wording with "including path canonicalization and rejection of `..`/absolute paths arriving from untrusted profile data, and never interpolating paths into shell strings", so the obligation is visible when ADR-012 is drafted.

## Checklist coverage

- 1 Trust boundaries: not evaluated as specified — see finding 1 (data sources never classified).
- 2 Parsing untrusted data: chain depth only; size/nesting unbounded locally — finding 2. No code evaluation anywhere in the design (TOML/TOML-edit only), no decompression path.
- 3 Path handling: nothing path-consuming lands in this design's own scope (fixture walk is repo-local trusted data); the obligation sits with ADR-012 consistent with ADR-008 clause 2 — nit only.
- 4 Secrets/PII: no owner named — finding 10.
- 5 Dependency advisories (queried 2026-11-11 via OSV/GitHub advisory DB, crates.io ecosystem): `clap` 0, `serde` 0, `toml_edit` 0, `toml` 0, `tower` 0, `axum` 0 — clean. `sqlx`: one advisory, RUSTSEC-2024-0363 / GHSA-xmrp-424f-vfpx (protocol-level length-prefix overflow, "all published versions <= 0.8.0", fixed 0.8.1); the design's sqlx 0.9 (A3) is outside the affected range, so not a blocker, though the advisory's own mitigation — cap request bodies — is exactly what the design defers to ADR-014. `tauri`: 9 entries, all fixed; the only one reaching the v2 line is CVE-2026-42184 (`>= 2.0.0, < 2.11.1`), which drives finding 5. `tauri-plugin-shell` CVE-2025-31477 fixed in 2.2.1. No known unfixed advisory on any dependency this design names.
- 6 Privileges: least privilege not stated for the capability surface — finding 4. Flatpak exclusion (A18) is the least-privilege-correct v1 call and is not contested.
- 7 Fail closed: chain guard is fail-closed and boundary-tested; missing-version is fail-open — finding 3; parser crash risk — finding 2; harness can pass vacuously — finding 9.

## FYI (no severity)

- `members = ["crates/*", "apps/*"]` (A7's flat-members recommendation) makes any directory dropped under those paths a compiled, gated workspace member; the naming rule in the Risks table is behavioral (A12 collisions), not an allow-list. Correctness/complexity seat's call whether to require an explicit member list.
- The committed root `.sqlx/` is build-consumed metadata that a PR can rewrite; the hub-path `cargo sqlx prepare --check` job already catches that drift, so I treat it as covered — noting only that its scope is "hub-path changes", so confirm it triggers on `apps/hub` migration edits too.
- A24/A25 are marked unverified; A25 in particular is what the MSRV and lock story rest on, and it is checked "at merge" rather than by a gate.
