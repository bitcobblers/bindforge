## Findings

- [major][new] Chosen design → The admin face and auth, **Concurrency** — "mutations take the write lock, mutate the model, and perform the atomic tmp-and-rename under a separate persist-only lock, so serving reads never wait on filesystem IO" — the sentence is either self-refuting or silently unsound, and it has no pinned case. Horn A: if the tmp-and-rename happens while the model write lock is still held (the literal reading of the clause chain), serving reads wait on filesystem IO, which is exactly what the clause promises they never do. Horn B: if the write lock is released before the persist, nothing in the text orders the persists with the mutations or states *when* the snapshot is taken, so two accepted admin mutations can persist newest-first and leave the file holding the older revision's record set while memory holds the newer one — after a restart an accepted mutation is gone and `revision` runs backwards, which 026-C4 forbids ("every accepted mutation bumps `revision` and persists atomically"). Test strategy #11 pins "a reader never sees a torn document (served from the locked in-memory model)" and #10 pins one upsert and one delete, so T-006 ships either horn with every pinned test green. Fix: state the lock order and the snapshot point in one clause — "the persist lock is taken **before** the model write lock; the mutation serializes the model into bytes while still holding both, releases the model lock, then does the tmp-and-rename under the persist lock alone" — replacing "mutate the model, and perform the atomic tmp-and-rename under a separate persist-only lock", and add to #11: N concurrent mutations ⇒ after all return, the file equals the model and `revision` equals the final value.

- [minor][new] Compatibility matrix — row 1 "Linux & other Unix | Yes" vs row 4 "Other / exotic Unix (BSD et al.) | No" — the r1 edit flipped row 4 from `unknown` to `No` without touching row 1's label, so the matrix now states that other Unix is both supported and not; the closing sentence compounds it ("the three `Yes` rows (Linux & other-Unix CI, macOS, Windows)"). Fix: relabel row 1 "Linux (primary CI target)" and let row 4 carry the `No`, or state that row 1's "other Unix" means only the shared Unix data-dir branch, not a support promise.

- [minor][new] Chosen design → Caching mode, **Upstream reachability** — "probed **at most once per TTL**, fired lazily by the first lookup or health read after expiry on that request's own thread" vs the serving face's "Answering it reads the **last-known** upstream verdict … it does not perform a live upstream probe per call" — a health read after TTL expiry now runs a synchronous upstream round trip (up to the 2 s/5 s connect/read timeouts) on the health request's thread, and because `last_upstream_fetch: 0` is expired from the first instant, test #12's freshly started body ("`upstream: down`, `last_upstream_fetch: 0`") is order-dependent: an implementer who applies the probe's verdict before writing the health response fails that very case whenever the upstream is reachable. Fix: "a health read never fires the probe; only lookups do" (or "health answers from the verdict as it stood at entry and fires the probe after the response is written"), and say so in #12.

- [minor][regression] Chosen design → Budgets — "evicts the oldest entry by **insertion sequence** (ties by `fetched_at` …)" vs `026-B1`'s words "over the cap the oldest `fetched_at` is evicted" — the r1 eviction-order fix changed the eviction *key* away from the ADR unit's own text and the divergence is recorded nowhere, while the design records far smaller divergences carefully (`026-S1` in Rollout step 6, the `026-L1`/`T-008` window in step 5); test #5 now pins "oldest insertion sequence evicted first", which is the document that gets handed to T-007. Fix: one clause — "which equals `026-B1`'s oldest-`fetched_at` order except across a backwards clock jump, where the ADR's rule would evict fresh data" — and add `026-B1` to Rollout step 6's annotations per `021-L4`; also state whether a refreshed entry keeps or takes a new insertion sequence.

- [minor][re-raised] Chosen design → Budgets — "`MAX_CATALOG_DOCUMENT_OCTETS` (1,048,576), `fs::metadata`-gated before the read of the `--corpus` or local-entries file, refused by name" — at a realistic ~120-140 octets per `{game_id, name, source_keys[]}` record, 1 MiB holds roughly 7,500 records, an order of magnitude below the ADR's stated corpus ("tens of thousands of games, each with several store keys", Context), so the named refusal fires on the root's own corpus well before the scale the ADR names as the reason for the design. I proposed the mirror of `026-B2` in r1; the design's adoption makes that number load-bearing for the root's corpus, where it was load-bearing for a cache in the ADR. Fix: size the cap from the ADR's scale and show the arithmetic in `schemas/catalog/v1/spec.md` (e.g. 16 MiB ≈ 120 k records), or state explicitly that a corpus past the cap is out of contract for v1 and what its operator does instead.

- [minor][re-raised] Chosen design → Budgets — "`MAX_REQUEST_BODY_OCTETS` (65,536, sized to one `026-C3` record inside the document cap)" — there is no per-record size bound to size against: `026-C3` bounds each `source_key` by `025-B1` and never bounds how many a record carries, so the largest legal record is unbounded, the sizing claim cannot be satisfied, and the two faces of one document disagree — `corpus.rs` loads a record with 600 keys from disk while `POST /v1/admin/games` refuses the same record as over-cap. No pinned test sits on the seam. Fix: either raise the body cap to the document cap ("any record that could legally live in a loadable corpus fits, so no per-record key-count bound is needed"), or name `MAX_SOURCE_KEYS_PER_RECORD` in `constants.rs` with its refusal in `corpus.rs`, `admin.rs` and #1, and state the record arithmetic the 65,536 figure follows from.

- [minor][new] Chosen design → Budgets — "`MAX_CONCURRENT_CONNECTIONS` (over-cap closed at accept, one thread per admitted connection)" — this is the only budget in the section without a value, so #11's "over-`MAX_CONCURRENT_CONNECTIONS` is closed at accept" has no boundary to sit on; and a bare close is the design's one inbound refusal that is not named, while every other refusal in the document is (the client's own outcome, a closed socket, is `catalog transport unavailable`/unreachable rather than a stated answer). Fix: give the number (with the thread story it prices), and state the over-cap answer — "closed without a status line; the CLI reports its named unreachable" — or a `503` with a reason phrase, which A21 already allows as temporary.

- [minor][new] Chosen design → The serving face step 1 — "the registry's one key validator tightens it: after the first `/`, exactly one non-empty `.`-free component, no embedded `/`" — the validator is stated only by two exclusions, so everything else is admitted: percent-decoded control bytes (`%0a%0d`, `%00`), spaces, and non-UTF-8 become legal keys in the cache document, the corpus via admin upsert, and in any refusal that names the key (the `503` reason phrase is written as `No catalog answer for slug`, and the design's own single-line echo discipline escapes only the failed upstream *id*). At the same time the flat `.`-ban refuses the keys the ADR names as the point of the admin face — Context: "a `local/<dir>` install has a lookup key", and directory names carry dots routinely — a refusal that reaches candidate queries, upserts and cache loads alike, while the stated purpose (never let a `..` or a separator reach a path) needs no more than banning a component that is `.`/`..` plus separators. Fix: state the accepted key grammar positively, not by exclusion — either name the byte set (e.g. `[a-z0-9-]` per component, `is_slug_name` as the cited precedent, plus "a decoded key that is not valid UTF-8 or carries a control byte is the `404`"), or keep the path-safety purpose honest ("a component equal to `.` or `..`, or any further `/`, is the `404`") and say whether a `.`-bearing external id is in contract for v1; extend #3 to pin the byte-set answer.

- [minor][re-raised] Chosen design → Catalog document and its spec — the refusal list now names "a repeated `game_id`" but still says nothing about a repeated `source_key` within one record — the r1 fix was taken halfway: a record may carry `steam/730` twice, which the `corpus.rs` slug→candidates index turns into duplicate `{game_id, name}` postings (the same game twice inside `MAX_CANDIDATES`, crowding out other answers), and makes `stats`' `source_keys` count ambiguous between total and distinct, so "the level a test engineer can pin" is lost at the count surface #10 now pins. Fix: add "a repeated `source_key` within one record" to the `corpus.rs` refusal list and to #1's `fixtures/invalid/` roster.

- [minor][new] Chosen design → Catalog document and its spec, harness list — "guard the fixture-tree loops — … and `fixture_file_names_…` (which keeps governing the `.json` fixtures: lowercase dash-separated names, case-unique) — behind the core-TOML check so catalog fixtures are not parsed as TOML" — as written these two halves cancel: a loop guarded behind the core-TOML check by definition stops governing catalog's fixtures, and #19's Windows/macOS case-collision argument rests on that very test covering them. Note too that the shipped `is_fixture_name` takes a bare name (`common/mod.rs:421`, one call site at `conformance.rs:348`), so "accepts `.json` for that directory only" is a signature change, not a predicate tweak. Fix: split the bullet — the two `every_valid/invalid_fixture` message loops and the re-serialization loop skip `catalog`; `fixture_file_names_are_lowercase_ascii_dash_separated_and_case_unique` keeps running over it, with the dir-aware `is_fixture_name` at its one call site named.

- [minor][new] Chosen design → Catalog document and its spec, harness list — "re-scope the sweep to `data/manifests` + `data/profiles`" with the Risks row "Single `const` names `catalog` at the skip sites; the re-scoped `boundary_tests` sweep … keeps the hygiene gate where it belongs" — dropping `schemas/*/v*/fixtures/valid/` from the sweep (verified: `boundary_tests.rs:116-130` walks that half today) deletes the gate's hold on every *other* format's valid fixtures, so a future `steam/`-bearing `schemas/profiles/…/valid/*.toml` passes; and the mitigation's single `const` cannot span the two harnesses it names, since `crates/core/tests/common/mod.rs` is not reachable from `crates/discovery/tests/boundary_tests.rs` (separate crates, separate test binaries). Fix: keep the sweep whole and exclude only the catalog format's own directories (its own small local list in `boundary_tests.rs`, the `const` in core's harness), rather than narrowing to two `data/` subdirs.

- [nit][new] Options considered — "the rejected location dodges neither harness consumer — the conformance walk nor the `data/`-walking source-key sweep" — the reasoning is inverted for the first half: moving the format spec out of `schemas/` dodges the conformance walk entirely (that is A9's whole point); only the `data/`-walking sweep survives, because `026-S1` fixes the seed path whatever the spec's location is. Fix: "the rejected location dodges only the conformance walk — the seed at `data/catalog/v1/` still trips the `data/`-walking sweep, and `026-C3` fixes the spec path anyway."

- [nit][new] Chosen design → The admin face and auth — "Enablement is judged from the address actually bound — the shipped `probe()` predicate `local_addr().ip().is_loopback()`, not a literal-spelling comparison" — that call is not shipped: `probe()`'s predicate is `addr.ip().is_loopback()` on a *resolved outbound* address (`apps/discovery-cli/src/catalog.rs:248`), `local_addr` appears nowhere in the codebase, and the same design deletes that shipped refusal at T-008, so pointing an implementer at "the shipped `probe()` predicate" sends them to copy a block the amendment removes; the loopback judgment is also absent from the five-block copy list in §`apps/registry`. Fix: "the predicate is `IpAddr::is_loopback()`, the one `probe()` uses today at `catalog.rs:248`, applied here to the listener's `local_addr()`", and either add it to the copy list or mark it as the registry's own.
