Scope: the `02-proposal.md` blob diff `9ff2ec7 → e1e63cb`, then the full current
document, against `docs/adrs/026-registry-service.md` and the Revision log. This
pass checks only whether the post-r1 revisions broke what this seat approved or

## Findings

- [minor][new] §Budgets → request budgets — "`MAX_REQUEST_BODY_OCTETS` (= `MAX_CATALOG_DOCUMENT_OCTETS`, so any record a loadable corpus could legally hold also fits an upsert and no per-record `source_keys` bound is needed)" — the revision moved the *inbound request-body* bound from the r1 value (65,536, "mirroring the client's own header cap") to 16,777,216 for **every** route, because the constant was re-purposed to be the document cap; the §Risks row that still cites it as the inbound mitigation ("Low-and-slow / one-inbound-per-outbound exposure on a routable bind … `MAX_REQUEST_HEADER_OCTETS`/`MAX_REQUEST_BODY_OCTETS`") therefore names a bound 256× larger than the one this seat approved, and no text pins where the route/method/`401` decision sits relative to the body read — `http.rs` describes only "the request reader admits `Content-Length`-framed bodies within the budgets below". Concrete failure: on the ADR's public-root posture (`026-C5`: non-loopback bind; admin possibly *disabled*, which still leaves the socket open), an anonymous caller sends 64 concurrent requests each claiming a 16,777,216-octet `Content-Length` body to any route, and a reader that runs before the router buffers and hands `serde_json` ~1 GiB in one `std`-only process. The removal of the per-record `source_keys` bound is the reason the equality exists, so the old implicit key-count bound is gone too. Fix: one clause in `http.rs`/§Budgets — the router answers `404`/`405`/`401` from the header block alone, and a body claim on any route other than `POST /v1/admin/games` is refused unread (that route's legitimate bodies are always zero-length) — and state the worst-case inbound figure (`MAX_CONCURRENT_CONNECTIONS` × the body cap) beside the §Risks row it belongs to; alternatively keep 65,536 as the non-admin body bound and bound `source_keys` per record, which retires the equality rather than widening it.

- [minor][re-raised] §Test strategy #3 — "`025-B1`'s cap and §The serving face step 1's rule apply to **decoded** `slug` and decoded `DELETE` path segment" — the rewrite renamed the predicate but kept the wrong pair. A `026-C3` `game_id` is `is_slug_name(id) && len ≤ 128` (A4), and `is_slug_name` is `[a-z][a-z0-9-]*` — no `/` (verified: `crates/core/src/placement.rs:107`); `spells_lookup_key` requires a `/` (`crates/discovery/src/game.rs:84`, `split_once('/')`), so step 1's rule applied to a DELETE segment `404`s **every** valid `game_id`. The two authoritative texts say otherwise, both in this diff: §The admin face — "`DELETE /v1/admin/games/<game_id>` percent-decodes the path segment, validates the grammar (A4)" — and step 1 itself, whose rule now "governs candidate queries, admin upserts and cache loads alike" (DELETE absent). So #3 contradicts both sections it is meant to pin. Fix: in #3 pin `slug` against `025-B1`'s cap plus step 1's rule, and the `DELETE` segment against the A4 grammar (`is_slug_name` + 128), keeping the separator/dot-dot/control-byte cases where they belong — the query seam.

- [nit][re-raised] §Chosen design → `http.rs` — "the request reader admits `Content-Length`-framed bodies within the budgets below — a `Transfer-Encoding`, missing or non-decimal length, or an over-cap body is refused before any mutation" — this pass *verified* the contradicting fact into the register (A23: "The shipped client sends one `GET` per connection carrying `Connection: close`, then reads a single response"; the shipped request is `GET …\r\nConnection: close\r\n\r\n` with no `Content-Length`, `apps/discovery-cli/src/catalog.rs:438`), while the request-reader sentence and #11 ("a `Transfer-Encoding`, `Content-Length`-less, or over-cap body is refused") were left saying a missing length is refused. Read literally, the reader refuses every `GET /v1/candidates` — the primary route, and the one `026-C1` requires to be byte-identical to what that client parses; the seam is loud (it fails #16), but the framing rule still has two readings exactly where smuggling discipline lives. Fix: name the zero-claim case so the refusal targets body *claims* only — `Transfer-Encoding` ⇒ refused; `Content-Length` present ⇒ read exactly that many octets within cap; absent ⇒ zero-length body.

## Checked and closed (no finding)

- The widened key alphabet (step 1's rewrite, deleting the registry-private `.`-ban and space refusal) is recorded as a deliberate decision in the Revision log, and the rebuttal holds up against the code: `MAX_DISCOVERY_SLUG_OCTETS`'s own doc states the lookup key "is exempt from `is_slug_name` by design … and it is never a path component" (`crates/core/src/placement.rs:88`), and `percent_encode` encodes everything outside the RFC 3986 unreserved set — `/`, `%`, `&`, `#`, space, control bytes (`apps/discovery-cli/src/catalog.rs:174`) — so the now-admitted dotted/space/`%` key cannot break out of the `slug=` parameter on the r4 outbound hop (#7 pins the copied `candidates_url` builder), and every sink the registry has for a key is a fixed-name JSON document or an opaque in-memory string, never a path join. The added refusals (further `/` or `\`, a `.`/`..` component, control byte or invalid UTF-8) close exactly what shape-only `spells_lookup_key` leaves open, and they keep control bytes out of refusal lines — a net log-injection improvement over r1.
- My r1 nit 3 (corpus cap enforced only at read) is closed by the admin-face clause ("the model with the upsert and the next `revision` value is serialized whole — the exact buffer renamed — and one over `MAX_CATALOG_DOCUMENT_OCTETS` … is the named `422`"), and the write-side check is against the exact renamed buffer, so a `revision` gaining a digit cannot persist a corpus its loader refuses.
- Deletions I checked for security loss and found none: the bearer-over-plaintext sentence in §Admin face (the RFC 6750 deviation still stands in §Risks row 2 and §Deferred bullet 1, which is what A20/`026-R1` require); the §Rollout "Defaults" paragraph (host/port/token-default and document locations are each still pinned in the CLI surface, §Admin face enablement, and the compatibility matrix); the `boundary_tests` re-scope (keeping both roots and skipping only `data/catalog/` + `schemas/catalog/` *widens* the `026-S1` hygiene gate relative to r1's `data/manifests`+`data/profiles` re-scope).
- Improvements introduced by this revision, in my specialty: `/v1/health` can no longer fire the upstream probe (the unauthenticated request → outbound hop trigger is gone from that route); `MAX_CONCURRENT_CONNECTIONS` is now a named number (64) with the thread/outbound-hop arithmetic shown; persist moved inside the one model write lock, so an accepted mutation cannot be lost by a restart and no reader can observe a half-written document.
- Deferred items re-read against the ADR: `026-R1` (TLS/transport assurance, bearer-over-plaintext included), `026-R2` (auth beyond the single bearer token), and public-root corpus governance all match the ADR's own reservation and "Not decided here" text; not re-opened.

## FYI (no severity)

- §Concurrency — "A reader may wait on one local write, and that latency is accepted" now understates the revised caps: with a 16 MiB document and no per-record `source_keys` bound, a mutation is a whole-document serialize plus a rename *under the model write lock*, so the reader wait is a 16 MiB write, not a local write. That is the performance seat's arithmetic, not mine.
- §Budgets — "`--refresh-interval <seconds>` — a bare unsigned count of seconds" admits `0`, which makes every lookup an upstream hop on a caching instance; operator-configured, so I read it as the ADR's `026-B3` "at the operator's call", but the spec could name a floor.
