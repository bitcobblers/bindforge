## Closure check of my r0 findings (against the changed text)

- r0-major (per-lookup cost on the request path) — **closed**. §Budgets now says "The in-memory cache holds each entry's serialized octet count with a running total … O(1) plus evictions, never a whole-document re-serialization. The file is rewritten write-through after each lookup that adds an entry; a crash loses that entry only", and Test-strategy #5 pins "checked from the per-entry octet totals". The persist is now declared (write-through per lookup), so the residual whole-file rewrite is bounded by `026-B2` and stated, which is what the r0 fix asked for. Verified the precedent the design leans on exists: `apps/discovery-cli/src/matches.rs:36,194` (`STORE_READ_BUDGET_OCTETS`, `fs::metadata` gate before read).
- r0-major (unbudgeted catalog document) — **closed**. `MAX_CATALOG_DOCUMENT_OCTETS` (1,048,576) is a private `constants.rs` budget, "`fs::metadata`-gated before the read of the `--corpus` or local-entries file, refused by name, mirroring A22", named in the `corpus.rs` refusal list, and pinned as a fixture + named refusal in #1. This also bounds the slug→candidates index, since postings are proportional to document octets.
- r0-minor (no effective capacity number) — **closed**: "One saturated entry is `MAX_RESPONSE_OCTETS` (≈64 KiB), so `026-B2` alone caps the working set at ≈16 fat entries (≈90 at realistic ~40-octet candidates) — accepted; #5 and `cached_slugs` read expect that, not 5,000." Internally consistent with `apps/discovery-cli/src/catalog.rs:23,26` (`MAX_RESPONSE_OCTETS = 65_536`, `MAX_CANDIDATES = 256`).
- r0-minor (`Arc<Mutex<Corpus>>` stalls the serving face) — **partially closed**: the primitive is now `Arc<RwLock<…>>` with shared reads and the persist moved to "a separate persist-only lock", but the guarantee the sentence claims is not established for the path that matters most (see finding 1).
- r0-minor (unbounded connection count) — **partially closed**: `MAX_CONCURRENT_CONNECTIONS` is added, enforced at accept, replaces the cache-eviction clause in the Risks row, and is pinned in #11 — but it is the only budget in the list with no value (finding 2).
- r0-minor (unnamed TTL-refresh driver) — **partially closed**: the driver is now named ("fired lazily by the first lookup or health read after expiry on that request's own thread — there is no timer thread"), which was my second offered option; the once-per-TTL amortization it relies on is asserted without an enforcement mechanism under the design's own thread-per-connection model (finding 3).
- r0-minor (join algorithm stated as a linear scan) — **closed**: step 2 now says "at load, postings are built already ordered by `game_id` byte order, so a request is one probe plus a clone of at most `MAX_CANDIDATES` records", and #2 pins "probes the load-built index".

Checklist item 6 (research baseline gap): the cold-scan cliff (serial per-slug client loop, `026-R3` prefetch deferral) is still the accepted gap the ADR itself reserves (`026-R3`, ADR Consequences "a cold caching registry's first scan pays N serial upstream lookups"); not re-opened. Startup cost and memory growth are now bounded for all three loaded documents plus connections.

## Findings

- [minor][re-raised] §The admin face and auth → **Concurrency (open Q10)** — "mutations take the write lock, mutate the model, and perform the atomic tmp-and-rename under a separate persist-only lock, so serving reads never wait on filesystem IO" — the r0 stall is only removed if the model write lock is *released* before the persist, and the sentence does not say so: `std::sync::RwLock` blocks new shared readers while a writer holds it, so a mutation that holds the write lock across the tmp-write/rename reproduces exactly the stall r0 flagged, now with a second lock in the picture. Three further consequences of the same under-specification: (a) if the persist serializes a snapshot taken at mutation time rather than the model's current state under the persist lock, two mutations can finish their persists out of order and the file can end at an older `revision` than one already served; (b) the paragraph names `Arc<RwLock<Cache>>` only in passing, but in caching mode the *ordinary request path* is a model mutation plus a write-through rewrite of up to `026-B2` octets (§Budgets), so whether that rewrite happens under the Cache write lock, and whether "a separate persist-only lock" is one lock shared with the corpus persist or one per document, decides whether a cold lookup's disk IO can stall warm candidate reads or an admin POST's persist can stall every cache write; (c) §The serving face step 2 now puts the slug→candidates postings in `corpus.rs`, and nothing says whether a mutation updates that game's postings in place or rebuilds the index under the write lock. Fix: one sentence fixing the protocol — take the model write lock, mutate the model and update that game's postings at their sorted position (no rebuild), release it, then under a per-document persist lock serialize the model's *current* state and rename; and state that the caching-mode cache write-through follows the same order with its own persist lock, so the stated "serving reads never wait on filesystem IO" holds on the hot path and not only for admin mutations.
- [minor][re-raised] §Budgets (request budgets paragraph), with §`apps/registry` `serve.rs` and §Risks last row — "`MAX_CONCURRENT_CONNECTIONS` (over-cap closed at accept, one thread per admitted connection)" — this is the only budget in the `constants.rs` list with no value: the two request budgets carry 65,536, the corpus and cache carry 1,048,576, and the TTL carries 3,600. Under the design's thread-per-connection model (no runtime, no pool) that number *is* the peak-thread and peak-stack-reservation bound for the flagship deployment the ADR names (`026-C5`'s non-loopback public root), so leaving it blank leaves the growth bound my r0 finding asked for nominal: #11's "over-`MAX_CONCURRENT_CONNECTIONS` is closed at accept" cannot be pinned to a number, `T-005` will pick one arbitrarily, and an operator sizing a public root has no capacity expectation to size against. Fix: give the constant a default in the same parenthetical (e.g. a stated value plus "overridable by `--max-connections`", or a stated fixed default) and name that default in #11's assertion.
- [minor][new] §Caching mode → **Upstream reachability** — "probed **at most once per TTL**, fired lazily by the first lookup or health read after expiry on that request's own thread — there is no timer thread … A query pays no health round trip beyond that one TTL-gated probe" — naming the lazy driver closes r0's question but introduces an amortization bound nothing enforces: with one thread per connection, several threads can pass the expiry test before the verdict stamp is written, so "at most once per TTL" is a claim about the code, not a property of it, and each extra probe costs the mirrored `2 s`/`5 s` on a serving thread (§upstream client). Compounding it, `--refresh-interval` "overrides `026-B3`" with no stated floor, so a small operator-set TTL degrades the bound toward a synchronous upstream probe per request on both `/v1/candidates` and `/v1/health` — the per-request synchronous IO the r1 text exists to avoid. Fix: one clause making the probe single-flight (the thread that compare-and-sets the `last_upstream_fetch` stamp under the Cache write lock is the only one that probes for that TTL, the rest serve the previous verdict) and one clause stating the floor for `--refresh-interval` (at least the upstream read timeout).
- [nit][new] §Budgets — "after a write the registry evicts the oldest entry by **insertion sequence** (ties by `fetched_at`, …)" — the switch from `fetched_at` order to insertion order fixes the clock-jump hazard, but the document never says whether a warm hit (Caching-mode step 2, "Cached entry within TTL answers as-is") moves the entry to the newest sequence. If it does not, eviction is FIFO, and with the design's own accepted working set (≈16 fat / ≈90 realistic entries, or a few thousand thin ones under `026-B1`) a burst of cold slugs evicts the hot ones and the next query pays another serial upstream round trip. Fix: one clause naming the policy — either "a warm hit re-stamps the entry's insertion sequence (LRU)" or "eviction is FIFO by insertion sequence; a hot slug may be evicted by cold churn" — so `T-007`'s eviction test pins the right behavior.
- [nit][new] §Budgets — "`026-B2` is **re-checked at load**", read against the same paragraph's "`MAX_CATALOG_DOCUMENT_OCTETS` (1,048,576), `fs::metadata`-gated before the read of the `--corpus` or local-entries file" — the r1 revision applies the pre-allocation gate to the two catalog documents but not to the third load path, the cache file: as written, an oversized `cache-v1.json` is read and parsed before `026-B2` refuses it. Both precedents the design invokes gate before allocating — `apps/discovery-cli/src/matches.rs:194` and `crates/core/src/toml.rs:51-58` ("refused without being allocated") — and the ADR's `026-B2` itself says "refused by name like the match store's". Fix: extend that parenthetical to "… or local-entries file, and the cache read is gated at `026-B2` the same way", with the refusal case noted in #5.
- [nit][new] §Budgets — "`MAX_REQUEST_BODY_OCTETS` (65,536, sized to one `026-C3` record inside the document cap)" — the "sized to" justification does not close: `026-C3` bounds each `source_key` by `025-B1` and `name` by `013-B4`, but nothing bounds the number of `source_keys` on one record (no shipped or proposed count cap exists — a grep of `crates/` finds no `source_keys` bound), so a record of a few hundred keys is legal at load under the 1 MiB document cap while being refuseable as a POST body. That leaves a hand-edited local-entries record the server loaded but its own admin face can never upsert. Fix: bound `source_keys` per record (a `constants.rs` count cap that keeps one record provably inside `MAX_REQUEST_BODY_OCTETS`) and refuse a record over it by name in the `corpus.rs` list and #1, or re-word the parenthetical so the body cap is stated as the per-record cap that load also enforces.
