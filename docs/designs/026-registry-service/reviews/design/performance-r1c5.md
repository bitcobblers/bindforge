## Findings

- [minor][regression] Chosen design → Budgets (request-budgets paragraph) — "`MAX_REQUEST_BODY_OCTETS` (= `MAX_CATALOG_DOCUMENT_OCTETS`, so any record a loadable corpus could legally hold also fits an upsert and no per-record `source_keys` bound is needed)" — the round-1 value this seat reviewed was 65,536; the revision silently raises the admitted request body 256× to 16,777,216 and the paragraph's capacity accounting for `MAX_CONCURRENT_CONNECTIONS` names only "≤64 live threads and ≤64 in-flight upstream hops", never admitted octets. The reader this design mirrors allocates the whole promised body once it clears the cap (`catalog.rs:364`), and the design never orders the admin auth check ahead of the body read ("an over-cap body is refused before any mutation" bounds mutation, not reading), so the peak inbound reservation for the flagship 026-C5 routable root is now 64 × 16 MiB ≈ 1 GiB plus the parsed value, against a record that needs kilobytes. The stated justification buys only the round-trip consistency this seat asked for in r1 (a loaded record the admin face could never re-upsert); it does not price what it costs. Fix: keep the two constants equal only if the paragraph states the admitted-octets bound it implies (64 × `MAX_CATALOG_DOCUMENT_OCTETS`) and that the auth check precedes the body read; otherwise re-split them — a per-record `source_keys` count cap chosen so one record fits a small `MAX_REQUEST_BODY_OCTETS` (65,536), named in the `corpus.rs` refusal list and #1, which is the alternative fix r1 offered.

- [minor][regression] Chosen design → The admin face and auth ("Concurrency (open Q10)") read against §Budgets ("`MAX_CATALOG_DOCUMENT_OCTETS` (16,777,216 — ≈120,000 records …)") — "a mutation serializes the new model, writes the fixed tmp name, renames it into place, and swaps the model in, **all under the one write lock** … A reader may wait on one local write, and that latency is accepted" — the r0 stall this seat flagged is now accepted rather than removed, which is the author's call; what the same revision changed underneath it is the size of "one local write": the corpus cap this seat approved against was 1 MiB, and §Budgets now raises it 16× to 16,777,216 justified by the root's own ≈120,000-record scale. So the accepted wait on the root is one whole-document serialize plus one write of up to 16 MiB, held in the `Corpus` write lock, during which `std::sync::RwLock` admits no new shared reader — up to 63 of the 64 admitted connections queue behind an operator's upsert. "That latency is accepted" no longer names a bound, and #11's new "N concurrent upserts leave the persisted document equal to the model" pins ordering, not the reader's worst-case wait. Fix: one clause in §Concurrency making the accepted wait a number — "the write lock is held for one serialize plus one local write of at most `MAX_CATALOG_DOCUMENT_OCTETS` octets; admin mutations are operator-rare on the root" — or write the tmp outside the model write lock from the buffer prepared under it and take the lock only for the rename and model swap, which keeps the ordering guarantee #11 tests.

- [minor][new] Chosen design → Budgets (cache eviction paragraph) — "after a write the registry serializes the cache and re-serializes after each dropped entry — one extra pass per eviction at most — dropping the oldest-`fetched_at` entries … until the buffer is ≤ `026-B2` octets" — the deletion of the running-total bookkeeping moves the whole octet test onto the serialized buffer, and the parenthetical bounds the passes per eviction but never bounds the evictions themselves, which the loop's own condition leaves open. Reachable inside the design's stated numbers: `026-B1`'s 5,000 entries at the paragraph's own ~150-210-octet realistic size sit just under 1 MiB, and one saturated `MAX_CANDIDATES` answer (≈`MAX_RESPONSE_OCTETS`, 65,536 octets — the figure this same paragraph carried before this revision) then requires dropping a few hundred thin entries, each drop costing another full ~1 MiB re-serialization, i.e. O(evictions × document) serialization of hundreds of MiB inside one cold-lookup request path. The round this diff replaces guaranteed the opposite ("O(1) plus evictions, never a whole-document re-serialization"), and #5 asserts only the end state, so nothing pins the cost. Fix: keep the exact-length test but stop re-serializing per drop — subtract each dropped entry's own serialized length (taken from the pass just done) from the buffer total, drop until the running total clears `026-B2`, then serialize once and check the exact length, looping only if that check still fails; that keeps "the octet test is the document's exact length" and restores the per-write bound. State which lock the write-through runs under while doing it (see the carried item below).

- [minor][re-raised] Caching mode → "Upstream reachability" — "probed **at most once per TTL**, fired lazily by the first *lookup* after expiry on that request's own thread" — unchanged in substance by this revision (dropping health reads as a driver narrows the window but leaves the concurrent cold-lookups-after-expiry case, which is the hot one); the design still names no stamp or compare-and-set, so with one thread per admitted connection several of the 64 threads can pass the expiry test before any verdict stamp exists, and "at most once per TTL" stays a statement of intent rather than a property, each extra probe costing the mirrored 2 s connect / 5 s read on a serving thread — the cost the Risks row "A cold caching registry's first scan is N serial upstream lookups" is mitigated against. Compounded by `--refresh-interval <seconds>`, now specified as "a bare unsigned count of seconds" with no floor and pinned live at `1` by #6, well under those timeouts, degrading the bound toward a synchronous upstream probe per lookup. Fix: make the probe single-flight in one clause (the thread that compare-and-sets the `last_upstream_fetch` stamp is the only one that probes for that TTL; the rest serve the previous verdict) and state the floor for `--refresh-interval` (at least the upstream read timeout).

- [nit][re-raised] Chosen design → Budgets — "`fs::metadata`-gated before the read of the `--corpus` or local-entries file and refused by name (A22)" — the third load path is still outside the gate: the cache's `026-B2` is only "re-checked at load", so as written an oversized `cache-v1.json` is read and parsed before it is refused, while the ADR's `026-B2` says the cache file is "refused by name **like the match store's**" and the precedent the design cites gates before allocating (`matches.rs` `load` / `STORE_READ_BUDGET_OCTETS`, A22; `catalog.rs:353-364` checks the promise before the `vec![0u8; length]`). Fix: extend the parenthetical to "… or local-entries file, and the cache read is `026-B2`-gated at `fs::metadata` the same way", with the refusal named in #5.
