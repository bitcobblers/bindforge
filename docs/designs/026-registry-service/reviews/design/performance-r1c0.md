## Findings

- [major][new] Caching mode (lookup step 4) + Budgets (write-time dual caps) — "4. **Miss with reachable upstream** fetches `GET <upstream>/v1/candidates?slug=`, validates the answer, and caches it with its `fetched_at`" / "after any cache write, the registry evicts the oldest `fetched_at` until **both** `count ≤ 026-B1` **and** `serialized bytes ≤ 026-B2` hold — so the file is provably inside both caps after every mutation" — the per-lookup cost on the request path is unbudgeted and unbounded-in-work: each cold lookup must (a) serialize the whole cache document to test the byte invariant, (b) re-sort entries by `slug` byte order for the next write (`026-C7`), (c) find the oldest `fetched_at` among up to 5,000 entries, and (d) re-persist the *entire* document through the `026-C7`/A7 tmp-write + rename + re-chmod discipline — up to 1,048,576 octets rewritten per slug, synchronously, in the handler. The shipped client's scan is serial per slug (`main.rs:191`), and `026-R3` keeps prefetch deferred, so a first scan of N games pays N × (serialize + sort + evict-scan + full-file rewrite) of a document that grows toward `026-B2` — O(N × cache bytes) on the user-visible critical path, on top of the N serial upstream round trips. The document has no request-latency budget anywhere, and the Risks row for the cold-scan cliff mitigates only the extra health round trip ("Cache the upstream-health verdict and reuse lookup outcome"), while the low-and-slow row's "oldest-first cache eviction bounds the entry growth" bounds entry *count*, not per-write work. Fix: keep the dual invariant but make it incremental — hold each entry's serialized octet count in the in-memory cache model with a running total, so the post-write check is O(1) plus evictions instead of a whole-document re-serialization; and state in one sentence when the file is rewritten (write-through per lookup, or coalesced at end-of-scan/idle and on clean shutdown, with the crash-loss window named), replacing the current implied per-mutation full serialization and full rewrite. Add the matching pin to Test-strategy #5.

- [major][new] Catalog document and its spec (loader refusals) + Budgets — "The registry's loader (`corpus.rs`) refuses by name: `version != 1`, `revision` negative, a `game_id` failing the grammar+bound (A4), a `name` over 128 octets (A5), a `source_key` failing `spells_lookup_key` or `025-B1` (A3, A16), a non-object/missing field" — the `026-C3` catalog document is the only document this design loads with **no octet ceiling and no entry-count cap**. Every other load in the design is budgeted: the cache at `026-B2` = 1,048,576, and the newly elaborated `MAX_REQUEST_HEADER_OCTETS`/`MAX_REQUEST_BODY_OCTETS`. The refusals listed are all field-level, and the A7 "load discipline" the section cites as its model *includes* a size gate: `matches.rs` refuses "past the 65536-octet read budget" on `fs::metadata` before allocating (`matches.rs:36,194`), and core refuses over `MAX_DOCUMENT_BYTES` "without being allocated" (`toml.rs:56`). Consequences: the root's boot read plus its retained in-memory model and the slug→candidates index — the design's main translation table — are unbounded against the ADR's own sizing ("tens of thousands of games, each with several store keys"), and in caching mode the admin face can grow the local-entries document without any cap. Fix: add one private constant to `constants.rs` (`MAX_CATALOG_DOCUMENT_OCTETS`, following the `STORE_READ_BUDGET_OCTETS` precedent the design already invokes: `fs::metadata` gate before the read) refused by name at load for both the `--corpus` file and the local-entries document, list it beside the other private budgets in §Budgets, and add a refusal case to Test-strategy #1. The design already justifies private, non-ADR budgets for the request path, so no new ADR unit is needed.

- [minor][new] Budgets (budget reconciliation) — "The research's \"budgets do not close\" finding (5,000 entries × up to 256 candidates can exceed 1 MiB) is resolved by making both caps **write-time** invariants" — the resolution makes `026-B1`'s 5,000 nominal, but the design never states the resulting effective capacity, which the numbers put two orders of magnitude lower. Each entry's candidates came from a response capped at `MAX_RESPONSE_OCTETS = 65_536` with ≤ 256 `{game_id, name}` pairs (game_id ≤ 128, name ≤ 128), so one saturated entry is ≈ 64 KiB and `026-B2` alone caps the cache at ≈ 16 slugs; at a realistic ~40-octet candidate it is ≈ 90 slugs. Since eviction is oldest-first, a handful of fat entries can evict many thin ones, so the caching registry's working set may be tens of slugs rather than 5,000 — which directly deepens the cold-scan cliff the design already flags (`026-R3`). The r0 revision entry records the caps being made jointly satisfiable, which is sound as far as it goes; it just supplies no capacity number for T-007's eviction test or for reading `health.cached_slugs`. Fix: one sentence in §Budgets giving the per-entry worst case (derived from `MAX_RESPONSE_OCTETS`) and the resulting effective slug capacity, stated as accepted, so the eviction unit test and the operator-facing counts are pinned to the right expectation.

- [minor][new] Chosen design → The admin face and auth, "Concurrency (open Q10)" — "serving reads take the lock on the **in-memory** model (never the file)" and "mutations take the same lock, mutate the model, then write the atomic tmp-and-rename" — as written, every `GET /v1/candidates` takes an exclusive `Mutex<Corpus>`, so candidate queries serialize against each other even with no writer present, and the tmp-write + rename + re-chmod — synchronous filesystem IO on a document the ADR sizes in the tens of thousands of entries — happens inside that same lock, so one admin `POST`/`DELETE` stalls the whole serving face for the duration of the disk write. This matters for the design's flagship deployment (a public root on a routable bind, `026-C5`) with thread-per-connection serving. The lock is only load-bearing for the two-writer refusal, and that refusal is already enforced by the fixed-name `create_new(true)` tmp (A7), not by this mutex. Fix: name the primitive and the persist's placement in one sentence — `Arc<RwLock<Corpus>>` with reads on the shared lock, and the tmp-and-rename either stated as held under the write lock with a stated cost expectation, or performed under a separate persist lock so the serving path never waits on the filesystem.

- [minor][new] Risks row "Low-and-slow / one-inbound-per-outbound exposure on a routable bind" — "Thread-per-connection with a request-read timeout; `MAX_REQUEST_HEADER_OCTETS`/`MAX_REQUEST_BODY_OCTETS`; oldest-first cache eviction bounds the entry growth (`026-B1`)" — the mitigations bound bytes and time *per* connection, but nothing bounds the *number* of connections, and the model allocates one OS thread per connection under a `std`-only posture with no runtime to absorb it. A peer holding many idle keep-alive sockets on a non-loopback bind drives unbounded thread/stack growth; the cited "entry growth" bound covers cache entries (`026-B1`), not connections, so the row claims coverage it does not provide. Fix: name one more private constant in the §Budgets `constants.rs` list (`MAX_CONCURRENT_CONNECTIONS`, excess refused at accept, or a stated accept-backlog posture), and replace the cache-eviction clause in that mitigation with it; pin it in Test-strategy #11.

- [minor][new] Caching mode, "Upstream reachability" — "that verdict is **cached and refreshed on the same TTL**" alongside Serving face's "it does not perform a live upstream probe per call" — the design never names what performs the TTL refresh. Local entries and warm cache hits (lookup steps 1–2) make zero upstream requests, so `health.upstream` can go arbitrarily long without an upstream interaction; the module plan (`serve.rs` accept loop/router/mode selection, `upstream.rs` client) names no timer or refresher. If the refresh is lazy inside `GET /v1/health`, then the route the design says never probes does issue one at every TTL boundary, and a monitoring poller pays the mirrored `2 s` connect / `5 s` read timeout inside a health check — with `--refresh-interval` free to make that boundary frequent. Fix: one sentence naming the driver — a background refresher on the TTL interval owned by `serve.rs` (which also makes "last-known" literally true), or an explicit statement that the health route may pay at most one bounded upstream probe per TTL, with that probe's timeout pinned.

- [minor][new] Chosen design → The serving face, join step 2 — "Answer = the join: games whose `source_keys` contain the slug" — this is the design's only statement of the hot-path algorithm, and it describes a linear scan over every game and its `source_keys` per request. The structure that avoids it exists only in the module list (`corpus.rs` — "load + validate + the slug→candidates index") and is never connected to the route or to the stable-ordering requirement, so as written a request scans and then sorts before "Ordered by `game_id` byte order; truncated to the first `MAX_CANDIDATES`". Fix: state in step 2 that the slug→candidates index maps the decoded slug to postings already sorted by `game_id` byte order at load, so a request is a probe plus a clone of at most `MAX_CANDIDATES` projected records, and that the sort/truncation cost is paid at load, not per request.

## FYI (no severity)

- `GET /v1/admin/stats` answers `{games, source_keys, revision}` and `GET /v1/health` answers `cached_slugs`/`last_upstream_fetch`: if `source_keys` is a total across games and `last_upstream_fetch` a max over entries, those are per-request aggregates over a document the design leaves unbounded; keeping them as counters maintained in the locked model keeps the routes O(1). Worth a line for the complexity and correctness seats as well.
- `026-B2`'s value is stated to coincide with core's `MAX_DOCUMENT_BYTES` and the design deliberately defines its own private constant; that is a reasonable independence call, but it means two 1 MiB ceilings drift independently — noting for the compatibility seat, not a performance objection.
