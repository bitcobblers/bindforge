# Compatibility review r1 (full-panel pass c0)

verdict: request-changes

scope: the whole document — `docs/designs/010-lightweight-plan-flow/02-proposal.md`
inputs used: `02-proposal.md` (including its Revision log), `docs/adrs/010-lightweight-plan-flow.md`. No review report or transcript was opened. No prior compatibility findings existed for this seat, so every finding below is `new`.

## Checklist coverage

1. **Compatibility matrix — every row has a status.** All 13 rows carry a status; no empty cell, so no blocker. One row is `unknown` (Windows) → finding 1 (major, per the checklist's explicit rule).
2. **OS input APIs (X11 / Wayland / Windows Raw Input / macOS HID).** This design has no OS input surface at all — it adds a stage, a seat list and a config record (A20, "No new platform surface: the flow adds a stage, a seat list and a config record"), which is the justification the checklist asks for, so no per-API targeting is owed. The row *set* omits macOS → finding 2.
3. **Node version floor.** A20 records the floor as `>=22.23.4` from `tools/orchestration/package.json`; nothing in the design claims an API above it (the additions are a TS record, a zod enum, prompt text, an agent file, a skill file), and Test strategy #21 pins that the suite runs at the `engines` floor. Covered.
4. **Native modules / packaging story.** The design adds pure-JS registry data, one prompt template, one agent config, one skill file; no dependency, no prebuild, no `node-gyp`, no CI matrix change. Covered — no silent native dependency.
5. **Keyboard reality (layouts, dead keys, IME, non-ASCII binding names).** No binding/keyboard surface is touched; the only new user-facing string vocabulary is the `flow` frontmatter value, matched exactly against `full`/`light` and case-sensitively (Test strategy #6). N/A, not a gap.
6. **File paths.** No per-OS config dir is introduced — run state stays repo-relative (`.pipeline.json`, `docs/designs/NNN-<slug>/`), which is compatible. Separator/case handling at the newly widened ownership predicate is unstated → finding 3.
7. **Test strategy names a platform test per supported platform.** The linux row has #21; the checkpoint-compat row has #16; the CRLF row has #6; the lane rows have #20; the Windows row is explicitly disclaimed by #21. Covered.

## Findings

- [major][new] Compatibility matrix — "| Windows | unknown | No Windows CI job exists in this repo; nothing in this design exercises a platform-specific path, and no test claims Windows (Test strategy #21)" — the checklist treats a row that reads `unknown` as a major: the design leaves Windows support undefined rather than claimed or refused, so an operator running a light job on Windows has no support statement to act on, and the row's own justification ("nothing in this design exercises a platform-specific path") describes the *delta*, not the support surface. The Deferred bullet "A Windows CI job to replace the `unknown` compatibility row — no follow-up yet" is consistent with ADR-010 (the ADR never mentions Windows), so the deferral is **not** re-opened here — the row, not the deferral, is what needs a status. Fix: give the row a definite status in the same shape as the row above it — `| Windows | no | The repo's tested support surface is linux; this design adds no Windows-specific path and claims no Windows support (A20, Test strategy #21) |` — and align Test strategy #21's closing clause with it; only add the CI job if the row is to become `yes`.

- [minor][new] Compatibility matrix — "| Node ≥ 22.23.4 (package `engines`), linux | yes | No new platform surface" — the matrix's OS rows are linux and Windows only, so the checklist's platform set (which names macOS) is unaddressed: a reader cannot tell whether a light run is supported on macOS, and the design never states the repo's support surface outside the linux row. Fix: add one OS-status row set that closes the question, e.g. `| macOS | no | Same support surface as Windows: no platform-specific path, no test claims it (A20) |`, and make #21 name the OSes the suite actually runs on; claim macOS `yes` only with a #21 entry that runs the suite there, as checklist item 7 requires.

- [minor][new] Ownership — the security spine, widened in one flow — "`stagePathAllowed(stage, path, flow = 'full')` (A8): `namesReservedSegment(path)` **stays first and wins in both flows**" — the design widens `implement`/`fix` write access to test paths through a path predicate that A8 describes in regex terms (`TEST_PATH_RE`, `namesReservedSegment`), and it never states the path form the predicate receives, so the widening and the reserved-name precedence are both decided by string matching on separators and case. That is checklist item 6 (separators and case handled by a library, not string matching): a `tests\x.test.ts` write (Windows) or a `Tests/x.test.ts` write (case-insensitive filesystem) is exactly the string pair that flips a deny into an allow. Fix: one clause in the Ownership section naming the existing contract as the authority — paths reach `stagePathAllowed`/`ownershipIssue` repo-root-relative and POSIX-normalized by the existing helper, so the added `flow` parameter introduces no new path parsing — and extend Test strategy #7's reserved-name list with a backslash/case-variant path so the precedence is asserted against the normalized form, not only the canonical spelling.

## FYI (no severity)

- Forward compatibility (rollback) is the one checkpoint direction the design leaves open: the matrix and #16 pin the backward case (a pre-`flow` fixture resolves as `full` at `version: 1`), but nothing says what a pre-`flow` `StateSchema` does with a checkpoint that carries `flow: "light"` after a rollback — that depends on whether the schema strips unknown keys or rejects them. ADR-010 asks for backward direction only, so this is a spec-integrity/correctness question, not a compatibility gap in this design.
- "`configFor('full', base)` is deep-equal to `base`" (Chosen design, Budget resolution) reads as an invariant over any `base`, but it can only hold for a complete config; a partial `base` spreads over `DEFAULT_CONFIG` and yields more keys than `base`. Test strategy #3's second clause (a literal without the new optional fields compiles and resolves to five seats) is the assertion that carries the additive-shape guarantee. Complexity/correctness seat's wording call.
- The size meter is described as "the existing `wc -l`-matching count" (A6, The `plan` stage). If that count is produced by a JS line count, the wording is harmless; if the runner shells out to `wc`, the design inherits an out-of-band Unix dependency, which is a second reason the Windows row cannot read `yes` and supports finding 1.
- ADR-010's own context table lists seven runs ("The seven runs on disk") while the table has six rows and the proposal counts six ("the six completed runs"). Not a compatibility matter.
- `maxReviews: { design: 0, code: 6 }` with `reviewSeats.design: []` means the design-phase cap is unreachable-by-stage rather than enforced; the `--stage` gate is what keeps a light run out of `research`. Worth a correctness seat's eye, not mine.
