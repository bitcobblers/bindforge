# complexity review r1

verdict: approve

## Findings

- [minor][new] Chosen design §1 "Fence runner-reserved paths in the ownership matrix" — "starts with `${STATE_FILE}.` (the saveState tmp pattern, `state-store.ts:186`)" — the tmp-name convention is minted inside `saveState` (`state-store.ts:186`), but the fence re-derives it inline in `gates.ts` as a hard-coded prefix rule. The design's own "share one vocabulary" move exports the reserved *names* to `types.ts` yet leaves the reserved *pattern* duplicated across two files, so a future change to the tmp scheme in `state-store.ts` silently desynchronizes the fence's second rule. Fix: export the pattern (a small predicate like `isStateTmpSegment`, or the tmp base-name constant) from `state-store.ts` where it is minted and have `gates.ts` consume it — the same single-vocabulary move the design already makes for `STATE_FILE`/`ESCALATION.md`; net code unchanged, one definition removed from `gates.ts`.
- [nit][new] Chosen design §2 "The cross-version resume contract" — "Canonical statement, written into the `StateSchema` header in `state-store.ts` and into `docs/workflows.md` for operators" — the full rule set is written verbatim in two places, and nothing in the Test strategy pins the two copies together, so the operator doc can silently drift from the contract the fixtures enforce. Fix: keep the full contract in one home (the `StateSchema` header, where the engineer adding a field reads it) and let `docs/workflows.md` carry only the operator-facing subset (refusal message, recovery postures) with a pointer to the header — reducing, not adding, duplicated text.

## Value check (checklist item 7)

Proportionate. Four small changes, each tracing to an ADR-006 question: the §1 rule extends the existing `stagePathAllowed` predicate rather than adding a module; §2 is contract text plus three load-only fixtures with *no* runtime mechanism (no migration ladder, explicitly "no mechanism"); §3 reuses the existing gate log, `ESCALATION.md` marker, and a precedent error class (`StopDriving` already establishes the discriminated-catch pattern); §4 reuses today's pid-liveness logic unchanged. No new dependencies (Node builtins only, within the `>= 22.23.4` floor), no config knobs, no one-implementation abstraction layers, no schema field changes. The heavier alternatives (digest reconciliation, lock-ID nonce, v2 ladder, multi-run concurrency) are rejected or Deferred, and Options considered shows each rejection rests on evidence (A7 commit-ordering invariant, forgeable digests, the dirty-by-normal resume state). I could not sketch a 30–50% smaller design that still answers all three ADR questions: dropping the fixtures unpins Q1 (the run-2 lesson), dropping the §3 escalation guard re-opens the run-2 blocker, and dropping §4 undermines the single-flight premise §1's trust posture cites. Deferring any half of it past the first merge would ship a partial trust story; the one-merge Rollout is justified.

## FYI (no severity)

- The §1 fence matches the path's *last segment* ("return `false` when the path's last segment is `STATE_FILE`"); a stage writing *inside* a planted `.pipeline.json/` directory is not caught by the predicate itself and relies on the ownership sweep restoring the "deletion plus untracked files" pair — the correctness/compatibility seats may want to confirm that chain closes the containment case.
