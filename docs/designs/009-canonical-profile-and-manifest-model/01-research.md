# Research: ADR-009 — Canonical profile, transform, and manifest model

Lenses applied: **Prior art** (→ Prior art), **Standards** (→ Platform notes),
**Security landscape** (→ Risks & unknowns).

## Summary

Every piece of ADR-009's five-contract model has precedent in shipping systems — named-action input vocabularies in Unity, Unreal, and Godot; base+overlay chains in QMK layers and Steam Input action-set layers; declarative per-game manifests in Lutris installer YAML; delta patches in RFC 6902 — but no existing format performs the ADR's core move (translating a profile across games via a manifest join), so `schemas/` fills a genuine gap rather than adopting a winner (source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.13/manual/ActionBindings.html ; https://docs.qmk.fm/feature_layers ; https://github.com/lutris/lutris/blob/master/docs/installers.rst). TOML v1.1.0 (published 18 Dec 2025) is the current spec and the repo's `schemas/README.md` already commits to a documented TOML v1.1.0 subset grammar with fixture conformance, which ADR-009 extends to `patch`, `manifest`, and `policy`. The sharpest structural tension found: TOML bare keys treat `move.steer-left` as a dotted key that creates a nested table, and the repo's v1 grammar forbids dotted keys entirely — so the taxonomy's dotted ids force an explicit profile-encoding decision the ADR leaves open (source: https://toml.io/en/v1.1.0). Key-name standards are per-platform (HID usage page 0x07, SDL scancodes, evdev, X11 keysyms, Windows VK codes); the ADR's glyph naming (`keyboard:w`) is the layout-dependent symbol axis, and its deferred "physical-position naming" is exactly the layout-independent scancode axis the standards support (source: https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h). Reach-class tables have no authoritative dataset to copy — ergonomics research quantifies reach-distance effects on typing speed and errors, but grading keys as `home/stretch/far/thumb/off-reach` will be BindForge-authored data with no external ground truth (source: https://pubmed.ncbi.nlm.nih.gov/25029899/).

## Findings

Model vocabulary and the action/manifest split:

- Engine input systems already separate *named actions* from *inputs* — Unity Input System "actions" bound via control paths (`<Keyboard>/w`, composites like `2DVector` for WASD), Unreal Enhanced Input "Input Actions" collected in "Input Mapping Contexts", Godot's `InputMap.add_action` project-scope named actions — validating the taxonomy/manifest separation, and none of them is a shareable cross-game file format (source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.13/manual/ActionBindings.html ; https://dev.epicgames.com/documentation/unreal-engine/enhanced-input-in-unreal-engine ; https://docs.godotengine.org/en/stable/classes/class_inputmap.html).
- The ADR's dotted ids collide with TOML: bare keys may contain only `A-Za-z0-9_-`, and a dotted key like `move.steer-left = "keyboard:w"` *is* TOML syntax for a nested table (`{move: {"steer-left": …}}`) — legal TOML that the repo's `schemas/README.md` v1 grammar explicitly refuses (dotted keys are among the refused constructs with an invalid fixture). The profile format must either quote ids as single keys, encode action ids as values in pair tables, or revisit the subset (source: https://toml.io/en/v1.1.0 ; repo: `schemas/README.md`, `schemas/profile/v1/fixtures/invalid/dotted-key.toml`).
- TOML v1.1.0 is the current spec (published 12/18/2025), with a formal ABNF grammar, mandatory UTF-8, case sensitivity, and a documented TOML→JSON structure mapping — the mapping means JSON-Schema-style post-conversion validation is expressible if the project ever wants a machine-checkable schema language (source: https://toml.io/en/v1.1.0 ; https://json-schema.org/draft/2020-12).
- Version pinning vocabulary (`remnant2@0.1`, `version = "1.0.0"`) matches SemVer 2.0.0's public API contract — "API" here being the format/manifest itself; SemVer's rules for pre-1.0 and compatibility promises map directly onto the ADR's "ids in the wild cannot churn" cost (source: https://semver.org).
- The model's claims about shipped games check out: Returnal on PC lists "Left-Handed and Right-Handed presets" plus per-axis mouse inversion options in the community game-feature wiki — the built-in-preset + inversion-as-game-fact pattern the manifest encodes (source: https://www.pcgamingwiki.com/wiki/Returnal).
- The keyboard-geometry claims check out: the touch-typing home position is `ASDF` + `JKL;` with marker keys on F/J, so the right-hand cluster `J K L ;` plus `'` occupies home-row positions the left hand has no counterpart for — the halves' asymmetry is physical, not conventional (source: https://en.wikipedia.org/wiki/Cursor_home_key ; https://en.wikipedia.org/wiki/Touch_typing).
- Handedness practice is a stack of independent decisions, matching the ADR's rejection of one mirror transform: Windows/OSes provide a system-wide primary-mouse-button swap (many players use it, many decline it — community threads show both camps), and left-handed control configurations are a recurring unmet accessibility ask (source: https://support.lenovo.com/us/en/solutions/ht117177 ; https://en.wikipedia.org/wiki/Mouse_button ; https://www.reddit.com/r/southpaws/comments/306gn5/do_left_handed_people_switch_their_mouse_buttons/ ; https://www.resetera.com/threads/why-are-left-handed-control-configurations-still-not-a-standard-accessibility-option.323206/).
- No standard grades per-key, per-hand reach: ergonomics research shows key spacing/reach distance measurably affects typing speed, error rate, and biomechanics, but published studies measure spacing effects, not a canonical `home/stretch/far` grading — the reach tables will be BindForge-authored data with no external ground truth to validate against (source: https://pubmed.ncbi.nlm.nih.gov/25029899/).
- WASD as the de-facto default is documented convention, supporting the ADR's premise that one shipped layout is the status quo (source: https://en.wikipedia.org/wiki/WASD).

Chains, patches, and transforms:

- QMK firmware's layers are per-key overlays on a base keymap — the same base+delta algebra as `*.bindprofile` patches — and are the dominant community model for "my layout sits on top of the shipped one" (source: https://docs.qmk.fm/feature_layers).
- Steam Input ships "action set layers": optional sets of action bindings overlaid on an existing set, plus community sharing/download of complete input configurations from within the product — precedent for both patch layering and the hub's adopt-at-any-rung flow (source: https://partner.steamgames.com/doc/features/steam_controller/action_set_layers ; https://partner.steamgames.com/doc/features/steam_controller/browse_configs).
- Patch-op semantics have an RFC pedigree: JSON Patch (RFC 6902) is an ordered list of `add/remove/replace/move` ops applied deterministically (the ADR's set/clear/swap ≈ replace/remove/move); JSON Merge Patch (RFC 7386) is the simpler null-deletes-keys form — and the RFC 6902 non-commutativity (op order is semantic) is the constraint `merge` must respect when two adopters patch the same base (source: https://www.rfc-editor.org/rfc/rfc6902 ; https://datatracker.ietf.org/doc/html/rfc7392 ; https://www.rfc-editor.org/rfc/rfc7386).
- Deterministic chain resolution (apply base, then each patch in chain order) mirrors git's parent-linked object chain, the reference design for "reproduce state by replaying ancestors" (source: https://git-scm.com/book/en/v2/Git-Internals-Git-Objects).
- The repo scaffold already fixes the chain-safety envelope this ADR inherits: `resolve_chain` with `Cycle`/`ChainTooDeep`, `MAX_CHAIN_DEPTH = 32` ("an initial value ADR-009 may tune but not remove"), `MAX_DOCUMENT_BYTES = 1 MiB` checked before allocation, `MAX_NESTING_DEPTH = 16`, and fixtures for self-deriving chains, over-deep chains, and over-nested documents (repo: `crates/core/src/lib.rs`, `crates/core/src/chain.rs`, `schemas/README.md`, `schemas/profile/v1/fixtures/`).

## Prior art

Prior-art lens — comparable solutions, names/formats, who won by convention:

- **kanata / xremap** — the Rust remapper ecosystem names keys by Linux evdev codes and keeps configs tool-local (kanata `.kbd`, xremap YAML); nothing designed for cross-game sharing exists, so BindForge's taxonomy+manifest join has no incumbent standard to adopt (source: https://github.com/jtroo/kanata ; https://github.com/k0kubun/xremap).
- **Steam Input** — the closest shipped system to BindForge's manifest+hub: per-game configurations, action-set layers, in-product browsing/sharing of community layouts, and templates players apply to *other* games — plus documented friction: users report wanting to carry one layout across games as a template (exactly the itch ADR-009's profiles address), and third parties (SteamInputDB) already index shared configs (source: https://partner.steamgames.com/doc/features/steam_controller/browse_configs ; https://www.reddit.com/r/SteamDeck/comments/tsjjne/how_to_share_controller_template_layout_across/ ; https://steaminputdb.com/).
- **Lutris installer database** — declarative per-game YAML documents ("Games in Lutris are written in the YAML format in a declarative way"), community-curated, schema-validated by the app: the operational model for `data/manifests/<game>/manifest.toml` as reviewed, versioned data (source: https://github.com/lutris/lutris/blob/master/docs/installers.rst).
- **SDL_GameControllerDB** — a community-sourced, plain-text mapping database consumed by many projects: proof the "community DB of input mappings, extended by PR" mechanism scales, and of the format's rough edges (GUID-keyed line strings that users hand-edit) (source: https://github.com/mdqinc/SDL_GameControllerDB).
- **QMK** — layer-based customization built on a shipped base, with data-defined key tables; the reach tables-as-data pattern has a direct analog in firmware keymaps (source: https://docs.qmk.fm/feature_layers).
- **Unity / Unreal / Godot input systems** — all converged on *named semantic actions* bound to inputs (control paths, Input Actions, InputMap actions), so "dotted lowercase action ids" rides a well-trodden convention; Unity's control paths (`<Keyboard>/w`) show OS-neutral input naming working at scale (source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.13/manual/ActionBindings.html ; https://dev.epicgames.com/documentation/unreal-engine/enhanced-input-in-unreal-engine ; https://docs.godotengine.org/en/stable/classes/class_inputmap.html).
- **Games with built-in handedness presets** (Returnal's left/right presets on PC) — the `seeded-from` flow (profiles deriving from a shipped preset) reflects shipped practice, not a hypothetical (source: https://www.pcgamingwiki.com/wiki/Returnal).

## Platform notes

Standards lens — the identifier standards the input vocabulary must map onto:

- **HID Usage Tables (USB-IF, rev 1.22)** define Usage Page 0x07 keyboard/keypad usages — the hardware-level key numbering the ecosystem converges on; SDL3's scancode enum is explicitly "based on the USB usage page standard" (source: https://www.usb.org/sites/default/files/hut1_22.pdf ; https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h).
- **SDL3 scancodes** are "the physical representation of a key on the keyboard, independent of language and keyboard mapping" — the layout-independent naming axis the ADR defers; the header's own comments show glyph↔position mapping varying across ANSI/ISO layouts and OSes (e.g., `SDL_SCANCODE_BACKSLASH` moves position between ISO and ANSI; ISO adds `NONUSBACKSLASH`; JIS adds the `INTERNATIONAL*`/`LANG*` keys) — the reach tables' ANSI-US restriction is a real scope limit with documented precedent (source: https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h ; https://wiki.libsdl.org/SDL3/BestKeyboardPractices).
- **Per-OS key identifiers, all layout-dependent at the symbol layer**: Linux `evdev` key codes, X11 keysyms (`keysymdef.h`, symbol names), Windows Virtual-Key codes (layout-dependent, including OEM pseudo-keys), macOS Carbon virtual keycodes (`Events.h`) — confirming the ADR's premise that `keyboard:<key>` names need a mapping table per platform, none of which is a global common denominator (source: https://github.com/torvalds/linux/blob/master/include/uapi/linux/input-event-codes.h ; https://gitlab.freedesktop.org/xorg/proto/x11proto/-/blob/master/keysymdef.h ; https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes ; https://www.popclip.app/dev/all).
- **ANSI vs ISO vs JIS physical geometries differ in key count and shape** (Enter, extra ISO key, JIS extras) — glyph naming on US-ANSI (`keyboard:w`) is unambiguous, but a profile shared into a JIS user's `henkan`-adjacent bindings needs the deferred physical-position scheme (source: https://en.wikipedia.org/wiki/Keyboard_layout ; https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h).
- **Gamepad naming has a true common denominator** the reserved `gamepad:*` ids can later adopt: the W3C Gamepad API's "standard" gamepad layout (Unity's Input System maps to it), with SDL_GameControllerDB as the community mapping layer — the ADR's "reserved, unmodeled" stance leaves this door open (source: https://www.w3.org/TR/gamepad/ ; https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API ; https://docs.unity3d.com/Packages/com.unity.inputsystem@1.6/manual/SupportedDevices.html ; https://github.com/mdqinc/SDL_GameControllerDB).
- **Format substrate**: TOML v1.1.0 (spec + ABNF; MIME `application/toml`) is the current standard the repo's grammar subset is pinned to; the repo's versioning rule (one dir per major, documents declare `format`+`version`, never defaulted) is in place and matches SemVer semantics (source: https://toml.io/en/v1.1.0 ; https://semver.org ; repo: `schemas/README.md`).

## Risks & unknowns

Security-landscape lens, plus model-specific risks:

- **Untrusted-document deserialization is a documented attack class**: small adversarial documents causing stack-overflow DoS via deep nesting is a recurring Rust-ecosystem finding — serde_cbor's nested-tag overflow (CVE-2019-25001, CVSS 7.5, fixed by bounding nesting), serde-json-wasm's same flaw on untrusted JSON, serde_cbor's later unmaintained status — the TOML path needs the same posture: serde_json ships a default recursion limit (lifting it is a feature-gated escape hatch), and TOML arrays/inline tables nest arbitrarily per spec, so the repo's `MAX_NESTING_DEPTH = 16` + 1 MiB pre-allocation cap are the right class of guard, not paranoia (source: https://rustsec.org/advisories/RUSTSEC-2019-0025.html ; https://rustsec.org/advisories/RUSTSEC-2024-0012.html ; https://osv.dev/RUSTSEC-2021-0127 ; https://docs.rs/serde_json/latest/serde_json/struct.Deserializer.html ; https://toml.io/en/v1.1.0 ; repo: `schemas/README.md`).
- **Path-like references are path-traversal bait**: `based-on = "profiles/lefty-r2.bindprofile"` and `data/manifests/<game>/` both map ids to filesystem paths; documents arriving from the hub are untrusted, so id/reference validation (no `..`, no absolute paths, case/encoding canonicalization) is required at every entry point — the classic Path Traversal class (source: https://owasp.org/www-community/attacks/Path_Traversal).
- **"Provenance labels the chain; it never substitutes for validation" matches supply-chain doctrine**: SLSA provenance describes how an artifact was built and is explicitly an input to verification, not a trust grant — the ADR's `generated-by`-recorded-never-trusted stance needs a concrete verification mechanism later (signatures/checksums at the hub, ADR-014), which is currently undecided (source: https://slsa.dev/provenance/v1).
- **Dotted-id ↔ TOML collision** (see Findings): shipping profiles in which every action key is quoted, or pair-tables, is a format decision with lifetime cost — fixing it after ids are "in the wild" is a major-version break the repo's own versioning rule makes expensive (source: https://toml.io/en/v1.1.0 ; repo: `schemas/README.md`).
- **Reach tables are an authored compatibility promise**: no standard dataset grades per-hand reach; two hand-authored TOML tables become load-bearing for placement legality and cannot churn without invalidating placement verdicts in profiles in the wild. The ADR names no authoring methodology, review bar, or fixture set for them (repo: `schemas/reach-classes/v1/` — left/right tables + conformance fixtures exist; source: https://pubmed.ncbi.nlm.nih.gov/25029899/).
- **The "IJKL breaks the home-row anchor, OKL; does not" claim is contestable** — both placements preserve the WASD shape and both leave a cluster finger on home-row keys; community practice genuinely splits on placement. The model can carry both as legal placements (it does), but the anchor claim as written asserts a fact the reach tables, not prose, should decide (source: https://en.wikipedia.org/wiki/Cursor_home_key ; https://www.resetera.com/threads/why-are-left-handed-control-configurations-still-not-a-standard-accessibility-option.323206/).
- **Config fingerprint stability**: "detected config fingerprint" must survive per-game config formats, locale/path variation, and launcher layouts to be usable for drift detection; prior art (Steam/Lutris/Goverlay families) detects game installs by id and config *paths*, not content fingerprints, so there is no proven fingerprint recipe to copy (source: https://github.com/lutris/lutris/blob/master/docs/installers.rst).
- **Supply-chain posture for the new crates is already wired**: the workspace runs scheduled `cargo deny check` (advisories/bans/licenses/sources) as triage input, and `crates/core` deliberately depends on nothing — the taxonomy/reach/chain code the ADR adds inherits both (repo: `deny.toml`, `crates/core/Cargo.toml`).
- **TOML-subset validation has no schema language**: the repo commits to prose `spec.md` + golden fixtures (JSON Schema Test Suite model) and refuses a machine-checkable schema; the TOML→JSON mapping makes JSON Schema expressible post-conversion, which the designer may want for the hub's upload gate (source: https://github.com/json-schema-org/JSON-Schema-Test-Suite ; https://toml.io/en/v1.1.0 ; repo: `schemas/README.md`).

## Open questions

For the designer:

1. How do dotted action ids appear as TOML keys under the v1 subset that forbids dotted keys — quoted keys (`"move.steer-left" = "keyboard:w"`), pair tables (`{action = …, input = …}` arrays), or a separator change (`move/steer-left`)? Every consumer's diff/edit ergonomics follow this (source: https://toml.io/en/v1.1.0 ; repo: `schemas/profile/v1/spec.md`).
2. What methodology creates and validates the reach tables (5 grades × 2 hands): the SDL3/HID geometry is known, but the grade boundaries (`home` vs `stretch` vs `far`) are authored judgment — who reviews, against what fixtures, and does a v2 table for ISO/JIS share ids with v1 (source: https://github.com/libsdl-org/SDL/blob/main/include/SDL3/SDL_scancode.h ; https://pubmed.ncbi.nlm.nih.gov/25029899/)?
3. Does `merge` of two patches on one base need three-way semantics (git model) or reject-all-conflicts-and-replay-ops (RFC 6902 model)? Op-order non-commutativity makes "fork, tweak, merge" lossy without a rule (source: https://www.rfc-editor.org/rfc/rfc6902 ; https://git-scm.com/book/en/v2/Git-Internals-Git-Objects).
4. Which reserved `gamepad:*` id names should the taxonomy mint now — W3C "standard gamepad" semantics (`standard-gamepad-button-0`-style vs. BindForge-semantic `move.steer-left`-on-left-stick)? The deferral is fine; the *namespace shape* is being frozen now (source: https://www.w3.org/TR/gamepad/).
5. What exactly is the manifest's "detected config fingerprint" (content hash of the config file? path+version from the game's own metadata?) and what re-validates on a manifest bump when the player, not BindForge, owns the config file on disk (source: https://github.com/lutris/lutris/blob/master/docs/installers.rst)?
6. Is the 1 MiB / 16-deep / 32-chain budget right for the v1 formats the ADR adds (patch, manifest, policy) — manifests carry full action tables (Remnant 2's?) and stay well under, while hub uploads need the same numbers enforced on the wire (repo: `schemas/README.md` ; source: https://www.rfc-editor.org/rfc/rfc6902)?
7. Does the hub verify `based-on` chains before download (server-side resolution) so a client never walks a malicious chain (cycle guard exists client-side — is server-side pre-resolution a policy promise, with traversal-sanitized ids)? (repo: `crates/core/src/chain.rs` ; source: https://owasp.org/www-community/attacks/Path_Traversal)
8. Should the manifest record a *per-action* "invertible-by-game-option" flag (game ships a native invert-Y toggle), since axis kind alone doesn't say inversion is already a game option and the manifest is "what the game *is*" (source: https://www.pcgamingwiki.com/wiki/Returnal)?
