# Security review r1

verdict: request-changes

Scope: whole document (panel pass c0, round 1). Inputs: `02-proposal.md`,
`docs/adrs/025-discovery-identity-and-catalog-matching.md`, the proposal's
Revision log, plus read-only inspection of the shipped code
(`apps/discovery-cli/src/main.rs`, `crates/core/src/error.rs`,
`crates/core/src/placement.rs`, `crates/core/src/manifest.rs`,
`crates/discovery/src/steam_common.rs`, `crates/discovery/src/keyvalues.rs`,
`Cargo.lock`).

Checklist walk: item 1 (trust-boundary classification) — store file and server
response are classified untrusted and the source key is quarantined from the
grammar and from paths (`025-L5`, the boundary tests, the `is_slug_name` +
`MAX_SLUG_OCTETS` triple check on `game_id`): sound; the endpoint config is the
one source left unclassified (finding 1). Item 2 (parsing untrusted data) —
sound for the ACF path (size cap before allocation, `1–20` ASCII digits for
`appid`) and under-specified for the HTTP response (finding 4) and the store
read (finding 5). Item 3 (path handling) — satisfied: relative env values are
treated unset, `game_id` is grammar-bound before it can be a path component,
`install_dir` keeps its `..`/absolute/`/`/NUL refusals, and no path is
interpolated into a shell string. Item 4 (PII storage/echo) — findings 3, 5, 7.
Item 5 (dependency advisories) — not applicable: the design names no new
dependency and commits to no `Cargo.lock` change (verified: `Cargo.lock`'s only
external names are `clap`, `serde`, `serde_json`, `winreg`; the rejected `ureq`
option is the one that would have added a tree, and it is not chosen). Item 6
(privileges) — the CLI gains a data-dir write, a loopback TCP connect and a
stdin read; no device access; least-privilege holds. Item 7 (fail closed) —
sound: gate before enumeration, mid-scan failure yields no partial table, an
unreadable store is refused with nothing rewritten, a non-`200` (so every
redirect) is refused, malformed manifests skip-and-count.

Nothing here re-litigates the Revision log's decisions: the loopback-only
transport, the CLI-placed gate, the store format, the refusal-not-start-empty
load rule and the appid sole-source are all accepted as chosen. The findings
below are about where those decisions are *checked*, not which way they go.

## Findings

- [major][new] "Catalog client and gate — `apps/discovery-cli/src/catalog.rs` (new)" — "It requires scheme `http` and a loopback host (`127.0.0.1`, `[::1]`, `localhost`)" — the loopback-only authority is the sole enforcement of the design's headline non-disclosure property (Options considered: "it cannot disclose an installed-game inventory to a remote host"; Risks row 3 mitigation: "This build can only reach a loopback authority" against a risk the design itself rates Medium impact / Certain-by-design likelihood), but the document never states the string split that decides it. There is no rule for a userinfo (`http://127.0.0.1:8080@host.example/`), for where the authority ends (`/`, `?`, `#`), for an empty host, for the port's character set, or for the non-dotted IPv4 spellings; and there is no URL parser to fall back on, because the workspace's only external crates are `clap`, `serde`, `serde_json`, `winreg` (`Cargo.lock`) and the design commits to "No new dependency and no `Cargo.lock` change". Test strategy 9 pins four spellings only — `http://127.0.0.1:PORT` accepted, `https://…` and `http://catalog.example` refused, unset refused — none of which separates a correct authority split from one that merely contains `127.0.0.1`, so a build that passes every pinned case can still put `GET /v1/candidates?slug=steam%2F900001` on a remote socket, i.e. the property the design claims cannot be established from this text. The endpoint also arrives from `BINDFORGE_CATALOG_URL`, which is a config source a shell profile can set; unlike the store path ("a relative value being unset"), it is never classified. Fix: state a pure `fn parse_endpoint(base: &str) -> Result<Endpoint, CatalogError>` in the same style as the design's other pure seams (`candidates_url`, `selection`, the env-lookup closure) with the accepted grammar spelled out — literal `http://` prefix; authority runs to the first `/`, `?` or `#`; a `@` anywhere in the authority is refused; the host must be exactly one of the three literals; a port, if present, is 1–5 ASCII digits — and add the userinfo, embedded-`?`, embedded-`#` and odd-IPv4 spellings to Test strategy 9's rejection list, keeping the check at the one `HttpCatalog` construction site so no call path can bypass it.

- [minor][new] "Catalog client and gate" — "`probe()` asks the authority, not an endpoint: resolve the host/port and `TcpStream::connect_timeout`" — the loopback property is established by name rather than by address. `localhost` is resolved by the system resolver, so a `hosts`/NSS entry pointing it elsewhere satisfies the stated check; and because `ToSocketAddrs` resolution can return several addresses which `connect_timeout` tries in order, a name that resolves to one loopback and one remote address passes the name test yet connects outward — the same failure as the previous finding, from the resolver side rather than the parse side. Fix: after resolution require every candidate `SocketAddr`'s `IpAddr::is_loopback()` and refuse otherwise (which also makes the two IP literals redundant, since they are just the addresses that pass), or state the name-literal rule as an accepted residual risk beside the inventory-disclosure row in Risks.

- [minor][new] "Scan flow and output — `apps/discovery-cli/src/main.rs" (steps 6–8) with the gate section's escape clause — "every echoed value — a slug, a candidate `name`, a rejected `game_id` — goes through `bindforge_core::escape_and_truncate`" and "`Game Id` prints the resolved id or `-`" — the escape invariant is enumerated over exactly three values, while the two table columns this design keeps are raw third-party bytes: `display_name` and `install_path`, both read out of the ACF (`parse_manifest` only `.trim()`s `name`; `usable_install_dir` refuses `.`, `..`, `/`, NUL, absolute paths and — on Windows only — `\`, and admits every other byte). `row_cells`/`render_table` (apps/discovery-cli/src/main.rs:157–165) pass cells through unchanged, so an ESC/OSC sequence in an `name` or `installdir` value reaches the operator's terminal as a control sequence, and a cell is bounded only by `keyvalues::MAX_DOCUMENT_BYTES = 1 MiB` (crates/discovery/src/keyvalues.rs:21). The product's own grammar refuses ASCII control characters in a native name (crates/core/src/manifest.rs:330–348), and this design clamps the *hidden* `friendly_name` to `MAX_NATIVE_NAME_OCTETS` while leaving the visible one uncapped — the bound lands on the field nobody reads. This is inherited behaviour, not introduced here; it is a finding because the design rewrites `COLUMNS` and the refusal-echo rule in the same section and states a one-line invariant the renderer does not meet. Fix: since the cell builder is being touched, state that the two ACF-sourced cells render through `escape_and_truncate` (replacing today's raw `row_cells` passthrough), or state 013's control-character rule as the explicit acceptance, and pin a control-character `name` fixture so the table cannot emit a control sequence.

- [minor][new] "Catalog client and gate" — "status other than `200`, a `Transfer-Encoding` header, a missing or over-`65_536`-byte `Content-Length`, a body that is not valid `Vec<Candidate>` JSON" — the refused shapes are named but the matching rules are not, and a hand-rolled parse is where those details are the control: header field names are case-insensitive, so a `transfer-encoding: chunked` spelling must be matched case-insensitively or the named refusal is skipped (the JSON parse then fails by luck rather than by rule); two `Content-Length` lines, or one carrying leading zeros, a `+`, or non-digits, is the confusion the cap exists to prevent, and the document says which value is too big but not which line wins or what spelling is legal; and the 65 536 bound covers the body only — nothing bounds the header block, which a peer that never sends the blank line can stream into memory for the whole 5 s read timeout. Finally the accepted candidate array has no client-side count bound, so one 64 KiB `200` becomes a prompt of roughly two thousand numbered lines (the count/pagination *contract* is deferred to `025-R1`; a read cap is not). Fix: one sentence stating that header names are matched case-insensitively, that exactly one `Content-Length` is accepted and only as 1–5 ASCII digits, that the header block is refused past the same 65 536-octet budget, and that a body over a named candidate maximum is an `Unreachable` refusal; add those spellings as response-parse cases in Test strategy 10.

- [minor][new] "Match store — `apps/discovery-cli/src/matches.rs` (new)" — "one file, `<data>/bindforge/matches.json`" and "through `matches.json.tmp` + `std::fs::rename`" — the section states the store's path, shape and atomic-write mechanism but never its access mode or a read bound, and the store is this design's own trust root for cross-source identity: the record whose `game_id` the CLI trusts forever without expiry ("Records never expire and are re-trusted on every scan", `025-L4`) is protected only by directory ownership. A `umask`-default 0644 file in a 0755 `bindforge/` directory makes the confirmed installed-game inventory readable by every local user, and if any ancestor is group- or world-writable (a shared `XDG_DATA_HOME`, a `/tmp`-like value the env seam accepts because it only checks absoluteness) another user can instead *write* a record and choose which `game_id` attaches to the user's installs — a silently wrong cross-source join that survives every later scan. The fixed `matches.json.tmp` name carries the same owner-only assumption: a pre-created symlink there is followed by a plain create. Load also has no byte bound, so an arbitrarily large `matches.json` is read into memory whole, where the ACF path caps size before allocation (crates/discovery/src/steam_common.rs:371–380). Fix: state that the `bindforge/` directory and both store files are created owner-only (0700/0600 on unix) and the tmp file exclusively, and that a store above a named byte budget (the `keyvalues::MAX_DOCUMENT_BYTES` shape) is the same named refusal — with the mode and the budget pinned in Test strategy 6 and 7, so the disclosure level becomes a stated property rather than a `umask` accident.

- [nit][new] "Match store" — "a `slug` past `025-B1`, or a `game_id` failing `is_slug_name` + `MAX_SLUG_OCTETS` is the named refusal" — `slug` is the only record field bounded by length alone, so a hand-edited or corrupted file persists a slug carrying control characters, spaces or path-ish spellings. Nothing renders or path-joins a store slug today (queries are issued only for discovered rows' slugs), so the gap is latent rather than live, but it sits against this design's own rule that an identifier is validated "at all three places it is seen". Fix: also refuse at load a `slug` not spelled `<token>/<external-id>` with `<token>` in `Source`'s closed set, or state in the section that a store slug is only ever compared byte-for-byte with a discovered slug and never rendered or joined, so the next reader knows which invariant the field carries.

- [nit][new] "Match store" and "Catalog client and gate" — "the named refusal `error: match store unreadable: <path>`" and "error: catalog unreachable: `<reason>`" — these two lines interpolate values the escape clause does not enumerate: `<path>` is composed from `$XDG_DATA_HOME`/`$HOME`/`%APPDATA%` and `<reason>` from a connect error whose display text can carry the host spelling from `--catalog-url`/`BINDFORGE_CATALOG_URL`, so one embedded newline or escape character puts a second, well-formed-looking line on stderr — against the invariant the workspace already states for this renderer, that a value from outside the product "can never put a second line or a path on an operator's terminal" (crates/core/src/error.rs:176–188). Naming the store path is right (the user's stated remedy is to remove the file), so the fix is not to drop it. Fix: extend the one escape clause to "every interpolated value in every named refusal", naming the store path and the reason, and add a newline-in-`$XDG_DATA_HOME` case to Test strategy 6.

## FYI (no severity)

- `std::fs::rename` over an existing `matches.json` has no replace semantics on Windows, so the second save on that platform fails where the design promises an atomic rewrite — correctness/compatibility, and it interacts with the Compatibility matrix row that already concedes Windows runs no test binary.
- `appid` accepted as "1–20 ASCII digits" admits leading zeros and all-zeros, so `steam/0123` and `steam/123` would be two identities, two queries and two store records for one install; correctness may want the value canonicalized (reject a leading zero, or parse and re-spell) at the one place the digits are read.
- ADR-025's Decision says a matched game "keeps its game id across scans and machines of the same user"; the proposal's mechanism is one local file and the Deferred list does not carry the cross-machine half. Not a security matter, but the clause is unmet rather than deferred.
- Scan wall-time is linear in distinct unresolved slugs under the 2 s connect and 5 s read timeouts, since the design queries once per slug and defers batching — shape for the performance seat.
- Process note for the record: one broad `docs/` content grep surfaced a single incidental line from another seat's r1c0 report before I noticed the path. It is not reflected above; every finding here is derived from the proposal, the ADR and the code.
