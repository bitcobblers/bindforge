## Findings

- [minor][new] Chosen design → Emission — `crates/discovery/src/steam_common.rs` + Test strategy #4 — "the identity gate becomes bound-only: `slug.len() > bindforge_core::MAX_DISCOVERY_SLUG_OCTETS` is the refusal (`025-L3`)" and "The plugin-side skip case at the same bound is asserted separately." — For the only emitter this run ships, the key is `Source::Steam.lookup_key(appid)` where `parse_manifest` "requires 1–20 ASCII digits", so the longest slug any input can produce is `steam/` + 20 = 26 octets, 102 short of the bound. The plugin-side comparison is dead for every reachable input, and its promised test case is writable only by hand-building an `AppManifest` whose appid the parser already refuses — a case that pins an unreachable path rather than a behavior. `025-L3` names one boundary ("The product checks only `025-B1` at the emit boundary") and the Goals sentence says the constant "is the only thing the emit boundary checks"; that boundary is `refuse_invalid_slugs`, where a row from any `dyn DiscoveryPlugin` is aggregated and where a future over-long Epic key would in fact arrive. Fix: drop the plugin-side `slug.len()` comparison and test #4's last sentence, leaving the 1–20-digit cap plus the one CLI boundary to hold `025-B1`; if the defence-in-depth line is kept instead, replace that sentence with the 21-digit skip case test #3 already asserts, so no case fabricates an input the parser refuses.

- [minor][new] Goals / Non-goals vs Chosen design → Catalog client and gate — Goals: "a connectivity gate with one named refusal" vs Chosen design: "Two named refusals, one gate: `error: catalog unreachable: <reason>` … `error: catalog transport unavailable: <reason>`" — the document promises one refusal name and ships two, and the second belongs to the loopback endpoint policy, the one mechanism with no Goal behind it (its reason lives only in the Options entry and the Risks table, and its cost is an error variant, the compatibility-matrix row, and Test strategy #9's policy cases). Fix: state the policy in one Goals bullet ("this build's client reaches a loopback authority only; `https` and non-loopback `http` refuse by name") and make the gate count agree in both places — either say "two named refusals" in Goals, or collapse to one name `catalog unreachable: <reason>` whose reason string carries the flag/env/ADR-026 text the Risks mitigation already promises, deleting `TransportUnavailable` rather than adding a Goal for it.

- [minor][new] Chosen design → Corpus boundary and ledger — "A corpus sweep asserting no file under `data/` or `schemas/*/v*/fixtures/valid/` contains `steam/`, `epic/`, or `local/` — Rollout 4's … pinned literally against the shipped corpus" — `025-L5` is asserted three ways here, and the sweep is the only non-structural one: `!is_slug_name(slug)` is a real proof (`lookup_key` always inserts a `/`, which `is_slug_name` refuses — verified at `crates/core/src/placement.rs:95-105`), and `id-source-key.toml` is refused by the existing conformance walk (A12). The sweep instead constrains unrelated files: the two files under `data/` are prose READMEs (verified: `data/profiles/README.md`, `data/manifests/README.md`, one already discussing paths shown to senders), and this design's own store location, `$HOME/.local/share/bindforge`, contains the substring `local/` — the first README that documents where the data lives fails an unrelated gate. The same section's `!is_slug_name(friendly_name)` assertion is contingent for the same kind of reason: it holds only because every current fixture name carries a space or a capital (`"Example Game"`, `"Secondary Title"`, `"BrokenMarker900201"`), so a future lowercase single-word fixture name would fail an assertion about the fixtures rather than about the design. Fix: delete the sweep and the `!is_slug_name(friendly_name)` clause, keeping `!is_slug_name(slug)` plus the invalid fixture — which is what Rollout 4 actually names ("boundary fixtures assert no source key or friendly name reaches a manifest or profile"); the friendly-name half of `025-L5` stays held by the rule that it is written only to the JSON row and the store.

- [nit][new] Options considered — Transport, option (a) — "on A17's unverified but plausible reading it puts a C-toolchain build script in the `x86_64-pc-windows-msvc` compile-check leg, which is the gate this run must not break" — the rejection of a maintained client rests on a premise the register itself marks "plausible but unexercised" (A17), and the option never considers the no-TLS-provider build of such a client (`default-features = false`), whose absence of a native provider is exactly what would answer the premise; the code the premise buys is `The request is std-only: `TcpStream` with a 2 s connect and 5 s read timeout …` plus its six parse refusals, the hostile-response risk row, and Test strategy #10's parse cases. Fix: either exercise the premise once on the `x86_64-pc-windows-msvc` check leg, or restate the decision on the ground the document already relies on elsewhere — `Cargo.lock` stays frozen (Rollout 7: "if one appears, it is a finding") and repo practice prefers hand-rolled text parsing to a new dependency (`crates/core/tests/gate_contract.rs`: "Hand-rolled because a suite that pulls in a YAML parser would be asserting against a dependency") — so the hand-rolled parse stands on verified grounds.
