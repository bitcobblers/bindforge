## Findings

- [major][new] §4 KeyValues reader + §8 CLI wiring — "`keyvalues::parse` accepts, for both file kinds: whitespace-separated tokens; quoted and bare keys and values" and "The printing code is untouched, so the table header and JSON shape are unchanged." — the accepted subset constrains structure (braces, depth, conditionals, file size) but never constrains the *character class* inside a key or value, and it does not cap a value's length beyond the 1 MiB file cap. The design's only consumers print these strings raw: `apps/discovery-cli/src/main.rs:48-57` interpolates `game.display_name` and `game.install_path.display()` straight into a pipe-delimited table on stdout, and §5 copies `name`/`installdir` into those fields verbatim. A manifest whose `name` carries `0x1b` control bytes gets terminal-escape injection (OSC/CSI sequences reach the user's terminal and any log capturing `discovery list`); a value carrying a newline forges extra table rows; a ~1 MiB single-token name is printed whole. Valid UTF-8 control characters pass both the `&str` gate and the grammar. The `--json` path is safe only incidentally (serde escapes control chars), so the exposure is the human table the design chose to leave untouched — and this plugin is the first data source that ever feeds it, since `DummyPlugin` returned `vec![]`. Trust is not "the user's own files" either: `name` is written by the Steam client from server-supplied store metadata, and §3 accepts arbitrary absolute library `path`s, so a manifest on an auto-mounted (often world-writable) library is read and printed. Fix: in §4 add the missing clause to the explicit subset — a key or value containing any control character other than tab, or exceeding a named per-value length cap, is a positioned `KeyValueError` — and add the matching case to *Test strategy* #1. That keeps §8's printer untouched and keeps the sanitizer out of the public surface; naming the character class is exactly the control the Options section claims the hand-rolled reader buys ("puts the grammar subset ... under this repo's control").

- [major][new] Rollout step 5 — "a contributor runs `discovery list` ... together with one real `appmanifest_*.acf` and the machine's `libraryfolders.vdf` if they can be shared" — this instructs a contributor to paste raw host files into `03-build-notes.md`, which per the repo's layout is checked into a public repo and effectively unretractable, with "if they can be shared" as the only guard and no redaction requirement. Real files of both kinds carry personal data: absolute paths that encode the account name and machine layout, and, in `libraryfolders.vdf`, the `apps` map that is the owner's complete installed-app inventory. The task's Done-when asks only that `discovery list` "correctly identifies installed games" on a real machine (docs/tasks/T-001-steam-linux-discovery.md:24); pasting the files is the design's own addition, so the exposure is discretionary and the design owns it. Fix: make the step capture a *redacted* capture — replace the home prefix and username with a placeholder (`$HOME/...`), drop the `apps` map and any `label` values, keep only the structural shape and the keys the reader must handle — and say so in the step, so the contributor follows the scrub rather than deciding per-file.

- [minor][new] Context / Assumption register — "T-001 ... adds the first implementation — `SteamLinuxPlugin`, which reads library folders from `libraryfolders.vdf`, enumerates `appmanifest_*.acf`" — no line in the document classifies the two data sources, which is the step every later control in §2/§4/§5 implicitly depends on. The Risks row calls them "user-editable files" only, which understates the surface (see the first finding: `name` is transitively network-influenced) and leaves the 1 MiB cap, the 16-level cap, the canonicalization and the `installdir` rejects reading as robustness choices rather than trust-boundary controls — a later edit that "relaxes" one of them for convenience then looks harmless. Fix: one added assumption-register row (or a sentence in Context) classifying `libraryfolders.vdf` and `appmanifest_*.acf` as untrusted external input — user-writable on disk and, for `name`/`installdir`, written by the client from store metadata — with their strings reaching the CLI's unescaped printer.

- [minor][new] §4 KeyValues reader — "Files larger than 1 MiB are skipped as malformed (A16): the reader's work is bounded per file" — the enforcement point is unspecified, and the neighbouring text describes the opposite order: "the caller reads bytes and skips a file that is not valid UTF-8", i.e. read-everything-then-decide. A read-then-check implementation defeats the cap it is claiming: peak memory is the file's real size, not 1 MiB, and a non-regular entry named `appmanifest_*.acf` (FIFO, or a device node in a library directory) is read to completion or blocks the scan outright, with §7's skip-and-continue turning the block into a hang rather than a skip. Nothing in §4 or *Test strategy* says only regular files are opened. Fix: state in §4 that the caller checks `symlink_metadata`'s file type and `st_size` and opens regular files only, and that the read itself is bounded (`Read::take(1MiB + 1)`), so the cap holds whether or not the size field is truthful.

- [nit][new] §3 Library selection within a root — "a `path` is used as-is when absolute and otherwise joined to the directory holding the VDF" — accepting an absolute path from an untrusted VDF is required here (the *Compatibility matrix* row "libraries on arbitrary mounts (`/run/media/…`, `/mnt/…`, ZFS)"), so this is not a defect; what is missing is the recorded blast radius. Fix: one sentence noting that a hostile `path` can only make the plugin open files named `appmanifest_*.acf` directly inside a directory that already has a `steamapps` directory, read-only, and that its contents can surface only as `display_name`/`install_path` fields — the reason no confinement rule is imposed.

- [nit][new] §8 CLI wiring / Rollout step 4 — "`install_path = l.join("steamapps").join("common").join(m.install_dir)`", emitted on the `--json` stdout handoff — the checklist's "what leaves the machine when bindings are shared" has no answer anywhere in the document, including *Deferred / out of scope*: `install_path` embeds the host's account name and library layout, and this design is what puts it on the machine-readable channel downstream tooling consumes. No behaviour change is asked for, only ownership. Fix: add one *Deferred* line: whether `install_path` may be embedded unredacted in a shared binding file is the sharing/codec design's decision, not this plugin's.

## Checklist coverage

1. Trust boundaries — gap (finding 3); no data source is classified. No network access, no shared binding file is read.
2. Parsing untrusted data — mostly covered (depth cap, file cap, no code evaluation, conditionals/`#base` rejected); character class and length unconstrained (finding 1), cap enforcement point unspecified (finding 4).
3. Path handling — covered: roots and library paths canonicalized and de-duped, `installdir` rejected on `.`/`..`/absolute/`/`, no recursion below `steamapps/` so the `compatdata` look-alikes are never opened, nothing interpolated into a shell (`Command` is never used).
4. Secrets and PII — the §7 error path is correctly minimal ("the count of files skipped ... nothing else — no file contents"), and AppID is never read or stored, which is the right privacy posture; the rollout capture procedure is the gap (finding 2), plus unowned sharing question (finding 6).
5. Dependency advisories — not applicable: the design adds no dependency, and I confirmed `Cargo.lock` is the 32-package closure A15 claims and contains no KeyValues parser, `dirs`, `walkdir` or `tempfile`; the rejected candidates (`keyvalues-parser`, `steamlocate`) are not introduced, so there is nothing to look up.
6. Privileges — covered: read-only filesystem access under `$HOME`/`$XDG_DATA_HOME`/Flatpak/Snap trees and VDF-named mounts; no device access, no network, no writes (including in tests); least privilege holds.
7. Fail closed — covered per file: skip-and-continue with one `Err`, and because discovery only reports, a partial scan applies nothing. `Ok(vec![])` for "not installed" is consistent with the task.

## FYI (no severity)

- `std::env::home_dir()` (A9, §2) is *not* deprecated on the pinned 1.85.0 floor — current std docs carry no deprecation notice — so there is no `deprecated`-lint risk against `cargo clippy --workspace --all-targets -- -D warnings`. Checked because the opposite would have been a compatibility finding; the compatibility seat need not spend effort there.
- `normalize_slug` (crates/discovery/src/slug.rs:1-35) always prefixes `unknown/` and never fails, so §5's rationale for the `name` fallback ("a `DiscoveredGame` needs a non-empty `display_name` because the slug derives from it") does not actually buy a *meaningful* slug: a `name` of no alphanumeric characters yields `unknown/` with an empty tail, and every such row shares it. Correctness seat's call, not mine; §5 already accepts duplicate slugs across libraries.
- §9's fixture tree puts a decoy `appmanifest_900099.acf` under `compatdata/`, and *Test strategy* #4 asserts it is never discovered — good negative coverage for the "never walk recursively" claim; a second decoy with a hostile `name` (control byte) would pin finding 1's fix cheaply if that fix is taken.
