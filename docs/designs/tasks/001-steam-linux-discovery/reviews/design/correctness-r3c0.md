## Findings

- [blocker][new] **§3 Library selection within a root** (with **§2 Canonical path rule**, **§5**, **§9 Fixtures**, **Test strategy #3/#6/#8**) — "`<root>/steamapps` itself, always" and "a `path` is used as-is when absolute and otherwise joined to the directory holding the VDF" and "`appmanifest_*.acf` files are read only as entries directly inside a selected library's `steamapps/`" — these three rules put libraries at two different levels, so the fixture and the design's own anti-silent-zero guarantee cannot both hold. Since manifests are read from `<library>/steamapps/` and `install_path = l.join("steamapps").join("common")…` (A2, and `Library::from_dir`/`resolve_app_dir` in the cited steamlocate `library.rs` confirm a library is the *parent* of `steamapps/`), the always-included entry must be `<root>`, not `<root>/steamapps`. As written: (a) `<root>/steamapps` fails §2's own gate ("dropping entries … that lack the required `steamapps` directory", i.e. `<root>/steamapps/steamapps`), so the "guaranteed scan of each root's own `steamapps/`" (Goals bullet 2) is dropped, and Test #3's "a root whose `libraryfolders.vdf` is absent still yields its own `steamapps`" and Risks row 2's mitigation both fail; (b) in the fixture, `"0" → "."` joined to the VDF's directory `<root>/steamapps` is `<root>/steamapps` (level wrong by one), `"1" → "../secondary"` joined there is `<root>/secondary` (level right), so no single join rule resolves both entries — evaluated as written the tree yields **one** game (`appmanifest_900100`), not the "Four games survive from this tree" of §9 and the exactly-four assertion of Test #8; (c) §2's claim that canonicalization resolves "the `"0" → root` duplicate" is false against §3, because §3 never puts `<root>` in the set — the fixture hides this only because it spells `"0"` as the `steamapps` directory, whereas the cited source shows real files store `"path" "/path/to/first/library"`. Fix: state one level — libraries are library folders (parents of `steamapps/`); the always-included entry is `<root>` (its `steamapps` existence is already guaranteed by §2's root gate, so say the gate is what guarantees the scan); join relative `path` values to `<root>` (the VDF directory's parent) and change the fixture's `"1"` entry to `"secondary"` so both entries resolve under that one rule without machine paths. Everything else in §9, Test #3/#6/#8 and §2's de-dupe claim then holds unchanged, and the legacy/absent-VDF case yields the root's games.

- [major][new] **§2 Root selection** / **A9** — "`home` comes from `std::env::home_dir()` (A9)" — on the toolchain this repo pins (`rust-toolchain.toml` `channel = "1.85.0"`), `std::env::home_dir` still carries `#[deprecated(since = "1.29.0", …)]`; the deprecation was removed only in 1.87.0 (rust-lang/rust#137327), and the 1.85.0 docs page shows "Deprecated since 1.29.0". A call site therefore emits `use of deprecated function`, which `cargo clippy --workspace --all-targets -- -D warnings` (A18, `.github/workflows/check.yml:31`, and Test strategy #10's own gate) turns into a hard failure. A9 is marked `verified` on the basis of the *current-stable* docs page, which no longer shows the banner — the basis does not support the row for the pinned toolchain (checklist 1). Fix: get home from `std::env::var_os("HOME")` and treat absent/empty as "no home directory", which §7 already defines as `Ok(vec![])` — no new dependency, so A15 stays intact; or keep the call behind `#[allow(deprecated)]`. Either way re-cite A9 to `https://doc.rust-lang.org/1.85.0/std/env/fn.home_dir.html` (note also that on 1.85.0 `HOME=""` yields `Some("")`, giving relative candidates that only the canonicalize gate removes).

- [major][new] **§7 Failure policy and the one error path** vs **Test strategy #7** — "at least one root was selected but **no** library under any selected root could be scanned" — §7's first paragraph already classifies "a manifest that fails to parse" as a *skipped file* and reserves the error for libraries that "could not be scanned", but Test #7 pins the opposite: "a root that has a `steamapps` directory whose entries are all unparseable returns exactly one `Err(DiscoveryError::PluginError(_))`". A `steamapps` directory whose entries all fail to parse *was* scanned, so the code that implements §7 literally returns `Ok(vec![])` for exactly the case Test #7 demands an `Err` for; the all-unreadable-library variant that does satisfy §7 cannot be built from a read-only checked-in fixture (§9: "No test writes to the filesystem" — a mode change is a write and would not survive checkout). Consequence: the mitigation claimed in Risks row 4 ("§7's single error path; *Test strategy* #7 pins both sides of it") is not implemented, and "Steam present, every manifest broken" prints nothing. Fix: restate the trigger as "at least one root was selected, zero games were emitted, and at least one file was skipped as unreadable or malformed" — this matches the message §7 already specifies (it counts skipped files), makes Test #7's all-unparseable fixture the `Err` side, and leaves the `Ok(vec![])` side (nonexistent root, no roots, Steam installed with no games → zero skipped files) untouched.

- [minor][new] **§1 Modules and public surface** — "Every `pub` item above is exercised by a test in *Test strategy*" — `SteamLinuxPlugin::from_host()` is the one `pub` item no test in *Test strategy* calls, and the document says so itself in Risks row 5: "`from_host()` cannot be unit-tested", with `host_candidates` as the substitute. Fix: qualify the sentence — "every `pub` item except `from_host()`, whose candidate list is asserted path-by-path through `host_candidates` in Test strategy #5 and whose probe is the §2 root gate".

- [minor][new] **§2 Canonical path rule** — "then sorting, then de-duplicating … so no library is ever scanned twice" — the rule is scoped to "every set of directories the plugin scans", i.e. per root, so a library registered by two *different* selected roots (native plus Flatpak or Snap installs pointing at the same `/run/media/…` library — exactly the multi-layout case the A8 candidate list exists for) is selected twice and every game in it is emitted twice as two byte-identical rows in `discovery list` and in `--json`. Fix: apply the canonical path rule to the union of library paths across all selected roots (one de-duped set per `discover()` call, assembled in the private scan loop) instead of one set per root, which makes the "never scanned twice" sentence literally true; Test #3's per-root `libraries_in_root` assertions are unaffected.

- [nit][new] **§8 CLI wiring (`apps/discovery-cli`)** — "registered in place of the deleted `DummyPlugin`" — deleting `DummyPlugin` is what makes `use discovery::plugin::DiscoveryPlugin;` (`apps/discovery-cli/src/main.rs:4`) an unused import, since nothing else in `main.rs` names the trait (`register_plugin`'s `Box<dyn DiscoveryPlugin>` argument supplies the trait object type for the coercion); under the `-D warnings` gate the leftover import fails the build. Fix: one clause — "`DummyPlugin` and its `DiscoveryPlugin` import are removed together, and the trait is not re-imported".
