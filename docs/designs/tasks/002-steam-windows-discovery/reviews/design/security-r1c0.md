## Checklist walk

1. **Trust boundaries** — satisfied. Registry values (HKCU is writable by any same-user process; HKLM needs admin), process environment, `libraryfolders.vdf` and `appmanifest_*.acf` files are each treated as attacker-influenceable: §6 states "A manifest is untrusted input in the same way the Linux design already treats it, and the composed path is emitted without being opened", and the Risks table carries the row "A corrupt or hostile registry value makes the plugin scan somewhere unexpected". No network input; nothing leaves the machine.
2. **Parsing untrusted data** — satisfied. The shared 1 MiB cap and valid-UTF-8 gate are reused (`keyvalues.rs:21` `MAX_DOCUMENT_BYTES = 1024 * 1024`; oversize/non-UTF-8 → `skipped` at `steam_linux.rs:287-316`), verified in code. Plain-text formats: no decompression, no code evaluation anywhere in the design.
3. **Path handling** — satisfied with one minor gap (finding F1). Canonicalization + `steamapps`-adjacency gate verified at `steam_linux.rs:322-334`. `usable_install_dir` (`steam_linux.rs:275-282`: NUL, `.`, `..`, absolute, `/`) plus the new Windows `\` clause removes every separator from an `installdir` on Windows, and §6 correctly notes the `\` clause — not host-OS `Path::is_absolute` — decides cases like `C:\games` and `\\server\share`, so Windows-shaped values are refused by tests that run on Linux. Shell-string interpolation: none — the `reg.exe` option is explicitly rejected (§Options considered).
4. **Secrets and PII** — not applicable in substance. No credentials read; rows carry only install paths; the new error path is test-pinned to "leaks no file contents" (Test strategy #6); no network transmission.
5. **Dependencies** — satisfied. Checked RustSec advisory-db (`crates/winreg`, `crates/cfg-if`, `crates/windows-sys`: no directories, i.e. no advisories) and the GitHub advisory database for winreg (only hit was GHSA-r98r-j25q-rmpr, which is the unrelated `failure` crate). No known unfixed advisory for `winreg` 0.56, `cfg-if`, or `windows-sys`. Lock claims verified: `windows-sys 0.61.2` and `windows-link 0.2.1` are in `Cargo.lock` (lines 249-262); `winreg`/`cfg-if` are absent and would be the only additions, matching A10.
6. **Privileges** — satisfied. `KEY_READ` (+ view flags) on two read-only keys, filesystem reads only, no elevation, and the registry crate is target-gated so non-Windows builds never compile it (A11, §3, §9).
7. **Fail closed** — satisfied. Every registry failure ("absent key, absent value, access denied, other `vtype`, non-UTF-16 data" → `None`, §3) is "no candidate", never a partial value; §4's REG_SZ-only rule refuses `REG_EXPAND_SZ`/`REG_MULTI_SZ`/`REG_DWORD` rather than guessing, so no `%VAR%` text can enter an emitted path; no-roots is `Ok(vec![])`; the single three-clause error path is preserved.

## Findings

- [minor][new] F1 — §5 Root candidates: "no normalization happens here — the canonical-path rule is what turns both into one comparable spelling" (with Risks: "A candidate must canonicalize and contain a `steamapps/` directory before anything under it is read") — on Windows the first contact with a candidate root *is* `std::fs::canonicalize`, which opens the path; a registry-sourced candidate in server-service form (`\\server\share` — any same-user process can write `HKCU\Software\Valve\Steam\SteamPath` as a plain `REG_SZ`, which §4's REG_SZ-only rule happily returns) triggers an outbound SMB session with the user's NTLM credentials to the named server, and can stall the CLI on an unreachable host, before the gate rejects the candidate. The stated mitigation covers what is read *behind* the gate, not the gate's own side effect. Impact is bounded (a same-user registry writer can coerce SMB auth itself), so this is hardening, not a blocker; but it makes §3's "Reading is the only thing that can fail, and a failure is 'no candidate', never an error" untrue in the sense of "without effect". Fix: in `host_candidates`'s Windows arm, syntactically refuse candidate roots that are not drive-absolute local paths (equivalently, drop UNC-form `\\…` candidates) before the list reaches the canonical-path rule — replacing canonicalize-as-first-contact with a one-line syntax check; every legitimate registry/env candidate (A3, A6) passes it.

## FYI (no severity)

- §5's `absolute_env` reuse (crates/discovery/src/steam_linux.rs:338-342) is `Path::is_absolute`, whose semantics are host-OS: Test strategy #3's fake-env cases run with Linux path semantics on the Linux runner, so a Windows-absolute fake value like `C:\Program Files (x86)` classifies differently per host — a correctness/test-semantics question for that seat, not a security one.
- VDF-relative-`path` traversal beyond the root (bounded only by canonicalize + the `steamapps` gate) and un-sanitized `display_name` characters reaching the table output are both inherited unchanged from the T-001 shared core, which the task's reuse clause mandates; noted for the correctness seat, not findings here.
- A20 (32-bit-host 64-bit-view query "fails rather than returning another key's data") is registered as unverified with a benign worst case; if the manual gate (Rollout #5) ever disproves it, re-check the candidate-confusion angle then — nothing actionable in this document today.
