# Research: Windows Steam discovery plugin (T-002)

## Summary

ADR-022 scopes the Windows Steam backend to "read Steam install via registry, enumerate library folders, parse `appmanifest_*.acf`" — everything after root selection is the same VDF/ACF scan that `SteamLinuxPlugin` already implements, so the task's core shape is extracting a shared scan core and adding a registry-backed host probe behind an injectable seam (source: docs/adrs/022-game-discovery.md, docs/tasks/T-002-steam-windows-discovery.md). Community tooling has converged on a stable host-probing convention: `HKCU\Software\Valve\Steam` → `SteamPath` (forward-slash paths) with the machine-level `SOFTWARE\Valve\Steam` → `InstallPath` (32-bit registry view) as fallback, plus `%ProgramFiles(x86)%\Steam` and `%ProgramFiles%\Steam` defaults (source: https://github.com/osztenkurden/steam-game-path/blob/master/docs/windows-registry.md). The genuinely Windows-specific surface is small: registry access (a `winreg`/`windows-core` choice, gated with Cargo `[target.'cfg(windows)']` sections), backslash path semantics (including the required extra `installdir` rejection), `fs::canonicalize` returning `\\?\`-prefixed paths, and cross-compile verification via `cargo check --target x86_64-pc-windows-*` (source: https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html). The main open risks are which `libraryfolders.vdf` location is authoritative on current Steam, registry value types, and how far Windows filename-validation hardening goes beyond the mandated backslash refusal.

## Findings

### Task and ADR surface

- ADR-022's Decision fixes the Windows backend contract: registry → Steam install, `libraryfolders.vdf` enumeration, `appmanifest_*.acf` parsing, per-manifest `DiscoveredGame` with `unknown/<kebab(name)>` slug, platform tag, `codec_id = None`, no AppID usage, no persistence (source: docs/adrs/022-game-discovery.md).
- The task's hard requirement is reuse with no copy-pasted scan logic: keep `keyvalues` and `normalize_slug` as-is; share `AppManifest`/`parse_manifest`, `libraries_in_root`, the `appmanifest_*.acf` enumeration, the size-capped UTF-8 reader, the canonical-path rule, skip-counting/degraded-scan semantics, the single error path, and the output sort — via a `steam_common`-style internal module or a platform-parameterized core; `SteamLinuxPlugin` behavior and tests must not change (source: docs/tasks/T-002-steam-windows-discovery.md).
- The seam pattern to mirror already exists: `SteamLinuxPlugin::from_roots(Vec<PathBuf>)` is the roots-injection constructor used by tests and `--steam-root`, and `host_candidates(home, &dyn Fn(&str) -> Option<String>)` keeps the host probe pure by taking the environment as a lookup function; the task asks for the same shape for the registry (source: crates/discovery/src/steam_linux.rs).
- `Platform::SteamWindows` already exists in `game.rs` and renders as `steam-windows` in `Display`/serde; only `discovered_game()` in the Linux plugin hardcodes `Platform::SteamLinux`, which is exactly the parameter the shared core must take (source: crates/discovery/src/game.rs, crates/discovery/src/steam_linux.rs).
- CLI wiring point: `apps/discovery-cli` registers exactly one plugin today, choosing `from_host()` vs `from_roots()` from `--steam-root`; both `steam-linux` and `steam-windows` must be registered and `--steam-root` must keep working for both (source: apps/discovery-cli/src/main.rs).
- The `keyvalues` parser is explicitly platform-neutral ("a later Windows plugin can reuse it") and already unescapes `\\` and `\"` inside quoted tokens — required because Windows `libraryfolders.vdf` writes paths with doubled backslashes (source: crates/discovery/src/keyvalues.rs, https://github.com/Playmoir/knowledge-base/blob/main/steam-library-integration.md).
- The mandated extra `installdir` rule (refuse `\`) closes a real gap, not a formality: the current `usable_install_dir` rejects `.`, `..`, NUL, absolute paths and `/`, but on Linux a backslash is an ordinary filename character, while on Windows it is the path separator and a reserved character in file names — so `foo\bar` would silently become a nested path in the emitted `install_path` (source: crates/discovery/src/steam_linux.rs, https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

### Host probing (registry and defaults)

- The user-level key is `HKCU\Software\Valve\Steam`, value `SteamPath`, type `REG_SZ`; registry exports show the value is stored lowercase with forward slashes, e.g. `"SteamPath"="c:/program files (x86)/steam"` (source: https://superuser.com/questions/1507846/how-do-i-properly-use-tokens-and-skip-with-reg-query, https://noverse.dev/docs/app-guides/steam/).
- The machine-level key is `HKLM\SOFTWARE\Valve\Steam`, value `InstallPath`; because Steam is a 32-bit application, on 64-bit Windows this physically lives under `WOW6432Node`, which community implementations reach either by hardcoding `SOFTWARE\Wow6432Node\Valve\Steam` or by requesting the 32-bit registry view (source: https://stackoverflow.com/questions/39557722/where-does-steam-store-library-directories, https://github.com/osztenkurden/steam-game-path/blob/master/docs/windows-registry.md).
- A recent, well-documented lookup order (steam-game-path): `HKLM\SOFTWARE\Valve\Steam` `InstallPath` in the 32-bit view, then 64-bit view, then `HKCU\SOFTWARE\Valve\Steam` `SteamPath` in the 32-bit view, then 64-bit view; it accepts `REG_SZ` or `REG_EXPAND_SZ` and stops at the first usable path. The task prescribes HKCU-first ordering, so the ordering choice should be pinned in the proposal (source: https://github.com/osztenkurden/steam-game-path/blob/master/docs/windows-registry.md, docs/tasks/T-002-steam-windows-discovery.md).
- Microsoft's rules for the 32/64-bit views: `HKLM\Software` is redirected to `HKLM\Software\Wow6432Node` for 32-bit processes; applications should not access the physical `Wow6432Node` location directly but open keys with the `KEY_WOW64_32KEY`/`KEY_WOW64_64KEY` flags on `RegOpenKeyEx` (available through both candidate crates) (source: https://learn.microsoft.com/en-us/windows/win32/winprog64/registry-redirector, https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view).
- `HKCU\Software` is not in the WOW64-redirected-keys list, and keys without a redirected parent listed are shared; so the per-user `HKCU\Software\Valve\Steam` key has one physical copy that a 64-bit process reads directly — the view-flag subtlety applies to the HKLM fallback (source: https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys).
- Conventional default roots: `%ProgramFiles(x86)%\Steam` and `%ProgramFiles%\Steam`; Microsoft documents `%PROGRAMFILES(X86)%` as "the `C:\Program Files (x86)` folder on 64-bit systems", i.e. it is absent on 32-bit Windows, so the lookup must tolerate the variable being unset; `C:\Program Files (x86)\Steam` is the default Steam install location (source: https://learn.microsoft.com/en-us/windows/deployment/usmt/usmt-recognized-environment-variables, https://stackoverflow.com/questions/39557722/where-does-steam-store-library-directories).
- The existing `canonical_paths` rule (canonicalize, require an adjacent `steamapps/` dir, dedup) makes every candidate self-validating: a registry-sourced or default candidate that does not exist simply drops out, so probing needs no separate existence gate — same behavior the Linux candidate list relies on (source: crates/discovery/src/steam_linux.rs).

### Shared scan core — Windows-relevant format facts

- Modern `libraryfolders.vdf` shape matches what the existing `library_paths` extractor reads: a `libraryfolders` section whose children keyed by decimal index carry `path`, `label`, `contentid`, `totalsize`, `apps`; Windows values carry escaped backslashes, e.g. `"path"\t\t"C:\\Program Files (x86)\\Steam"` (source: https://stackoverflow.com/questions/78531838/deserialize-steams-libraryfolders-vdf-into-an-object-c, crates/discovery/src/steam_linux.rs).
- Community tooling treats an entry's `path` as the library root whose `steamapps/` holds manifests, with a `mounted` flag: Lutris only appends a library when `mounted` is `"1"` or absent — an unmounted external-drive library must not abort the scan; in BindForge's core the existing canonicalize-and-require-`steamapps` rule already drops such roots silently (source: https://github.com/lutris/lutris/blob/master/lutris/util/steam/config.py, crates/discovery/src/steam_linux.rs).
- `appmanifest_*.acf` is the same KeyValues format with an `AppState` section carrying `appid`, `name`, `installdir`, `StateFlags`, `buildid`; `installdir` is a single directory name relative to `<library>/steamapps/common/`, matching the existing `parse_manifest` → `join("steamapps").join("common").join(installdir)` emission (source: https://frankea.github.io/Whisky/documentation/whiskykit/steamappmanifest/, https://steamtools.games/manifest-files, crates/discovery/src/steam_linux.rs).
- Windows file-naming rules add hardening surface beyond the mandated backslash refusal: reserved characters `<>:"/\|?*`, reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`, also with extensions) are forbidden in any directory name, and names must not end in a space or period — a hostile or corrupt `installdir` could otherwise produce an emitted path a consumer cannot safely open (source: https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).

### Dependency and toolchain surface

- `winreg` (v0.56, MIT, MSRV 1.60, ~2.0K SLoC) is a small safe wrapper exposing `HKCU`/`HKLM` constants and `get_value::<String>` (which decodes `REG_SZ`, `REG_EXPAND_SZ` and `REG_MULTI_SZ`); its README self-describes as "work in progress" with a single maintainer (source: https://docs.rs/winreg/latest/winreg/, https://crates.io/crates/winreg).
- The alternative named by the task is the Microsoft `windows`/`windows-core` crate family calling `RegOpenKeyEx`/`RegGetValueW` directly, which is where the `KEY_WOW64_*` flags live (source: https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view, docs/tasks/T-002-steam-windows-discovery.md).
- Either dependency can be confined to Windows builds with Cargo's `[target.'cfg(windows)'.dependencies]` table, so the Linux workspace graph is untouched (source: https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html).
- `x86_64-pc-windows-msvc` and `x86_64-pc-windows-gnu` are Tier 1 (with host tools) targets with a precompiled `std` shipped by Rust; the `windows-gnu` page states explicitly that these targets support cross-compilation from other hosts (a mingw-w64 C toolchain is needed for linking) (source: https://doc.rust-lang.org/rustc/platform-support.html, https://doc.rust-lang.org/rustc/platform-support/windows-gnu.html).
- `cargo check` "compiles the packages without performing the final step of code generation", i.e. no binary is linked, so `cargo check --target x86_64-pc-windows-msvc` type-checks the `#[cfg(windows)]` code on Linux without MSVC or MinGW installed — matching the task's compile-verification gate (source: https://doc.rust-lang.org/cargo/commands/cargo-check.html).
- `std::fs::canonicalize` on Windows goes through `CreateFile` + `GetFinalPathNameByHandle` and returns extended-length (`\\?\`) paths, to which "you can only join backslash-delimited paths" — since the core joins `steamapps/common/<installdir>` onto the canonical library path, emitted `install_path` values will carry the `\\?\` prefix unless the design strips it (source: https://doc.rust-lang.org/std/fs/fn.canonicalize.html).

## Prior art

- **SteamLinuxPlugin (this repo, T-001)** — the direct model: pure `host_candidates` + `from_roots` seam, degraded-scan skip counting, the single error path, canonical-path dedup; its integration tests use fixture trees that the Windows plugin's tests will mirror (source: crates/discovery/src/steam_linux.rs, docs/tasks/T-001-steam-linux-discovery.md).
- **osztenkurden/steam-game-path (Node.js)** — the closest comparable: dependency-free Steam game discovery on Windows/macOS/Linux; its `windows-registry.md` documents the full candidate order, both registry views, and `REG_SZ`/`REG_EXPAND_SZ` acceptance, and notes that shelling out to `reg.exe` makes non-ASCII paths encoding-dependent — an argument for a native registry API over a spawned `reg.exe` (source: https://github.com/osztenkurden/steam-game-path, https://github.com/osztenkurden/steam-game-path/blob/master/docs/windows-registry.md).
- **Lutris (Python)** — long-lived Steam library integration: `get_steamapps_dirs()` unions candidate install dirs, legacy `BaseInstallFolder_N` config entries and `libraryfolders.vdf` `path` entries, honours the `mounted` flag, and skips the non-path `contentstatsid` key; it reads `config/libraryfolders.vdf` rather than `steamapps/libraryfolders.vdf` (source: https://github.com/lutris/lutris/blob/master/lutris/util/steam/config.py).
- **Playmoir knowledge base** — practical write-up of the same two-file scan (`libraryfolders.vdf` + `appmanifest_*.acf`) and the two known gotchas: the file lives at `steamapps/libraryfolders.vdf` (legacy) or `config/libraryfolders.vdf` (newer) depending on client version, and `\\` escapes must be unescaped before using extracted Windows paths (source: https://github.com/Playmoir/knowledge-base/blob/main/steam-library-integration.md).
- **Whisky SteamAppManifest (Swift)** — documents the ACF `AppState` field set consumed for discovery (`name`, `installdir` relative to `steamapps/common`, `StateFlags`, `buildid`), matching the subset BindForge parses and confirming that ignoring everything else (AppIDs included, per ADR-022) is the norm (source: https://frankea.github.io/Whisky/documentation/whiskykit/steamappmanifest/).

## Platform notes

- **Registry value content is surprising data, not paths.** `SteamPath` arrives lowercase and forward-slash-delimited (`c:/program files (x86)/steam`) while `InstallPath` arrives backslash-delimited; both must flow through the same candidate pipeline, and `canonicalize` (with its `\\?\` result) is what normalizes them for joining (source: https://superuser.com/questions/1507846/how-do-i-properly-use-tokens-and-skip-with-reg-query, https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file, https://doc.rust-lang.org/std/fs/fn.canonicalize.html).
- **Registry view flags.** Use `KEY_WOW64_32KEY`/`KEY_WOW64_64KEY` rather than hardcoded `Wow6432Node` paths when reading the HKLM fallback; the HKCU key is shared and unaffected (source: https://learn.microsoft.com/en-us/windows/win32/winprog64/accessing-an-alternate-registry-view, https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys).
- **Environment variables.** Read `ProgramFiles(x86)` and `ProgramFiles` through a lookup function (mirroring the Linux `env: &dyn Fn` pattern); the `(x86)` variable is 64-bit-systems-only, so treat unset as "no candidate", and note that unlike `XDG_DATA_HOME` these values are always absolute when set (source: https://learn.microsoft.com/en-us/windows/deployment/usmt/usmt-recognized-environment-variables, crates/discovery/src/steam_linux.rs).
- **Path handling.** Windows paths are case-insensitive, backslash-separated, UNC- and drive-letter-rooted; `\\?\` extended-length paths disable normalization entirely. A registry value or VDF path with a trailing space/period behaves differently at the shell layer than the filesystem layer (source: https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).
- **Compile verification from Linux.** `[target.'cfg(windows)'.dependencies]` keeps the registry crate out of the Linux lock graph; `cargo check --target x86_64-pc-windows-msvc` needs only `rustup target add` (no linker); `x86_64-pc-windows-gnu` additionally supports full cross-builds with mingw-w64 if CI later wants real binaries (source: https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html, https://doc.rust-lang.org/rustc/platform-support/windows-gnu.html, https://doc.rust-lang.org/cargo/commands/cargo-check.html).
- **Workspace facts.** `crates/discovery` today depends only on `serde`; the workspace pins edition 2024 / rust-version 1.85, above both candidates' MSRVs, and the `Platform` enum plus serde output format already carry `SteamWindows` (source: crates/discovery/Cargo.toml, Cargo.toml, crates/discovery/src/game.rs).

## Risks & unknowns

- **Which `libraryfolders.vdf` is authoritative.** Community sources report the file at both `<root>/steamapps/libraryfolders.vdf` (legacy) and `<root>/config/libraryfolders.vdf` (newer clients); Lutris reads only the `config/` copy, while BindForge's shared core reads only the `steamapps/` copy. Windows Steam may write one location more reliably than the other; if the shared core reads only `steamapps/`, parity is preserved but a Windows-only regression is possible (source: https://github.com/Playmoir/knowledge-base/blob/main/steam-library-integration.md, https://github.com/lutris/lutris/blob/master/lutris/util/steam/config.py, crates/discovery/src/steam_linux.rs).
- **Registry value types and expansion.** The observed `SteamPath` is `REG_SZ`, but precedents accept `REG_EXPAND_SZ` (which `winreg`'s `get_value::<String>` would return unexpanded, containing raw `%VAR%` text); unexpanded or multi-string values must not become candidates (source: https://docs.rs/winreg/latest/winreg/, https://github.com/osztenkurden/steam-game-path/blob/master/docs/windows-registry.md).
- **Registry data is untrusted input.** A corrupt or hostile value could be an absolute path anywhere on the machine, a UNC path, or a path with reserved-device-name components; the pipeline's only guard is that the candidate must canonicalize and contain a `steamapps/` directory before being scanned — acceptable for discovery, but the emitted `install_path` inherits whatever the registry pointed at (source: crates/discovery/src/steam_linux.rs, https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file).
- **`\\?\` prefixes in user-visible output.** Canonical-path rule plus Windows `canonicalize` means `discovery list` output and JSON will contain `\\?\C:\...` paths unless the design strips or normalizes them; consumers that later open these paths behave differently under the `\\?\` namespace (source: https://doc.rust-lang.org/std/fs/fn.canonicalize.html).
- **HKLM readability across install types.** A per-user or non-default Steam install may have no HKLM key (or vice versa); both keys are normally user-readable per community usage, but there is no Valve documentation stating guarantees, and no Windows runner exists yet to verify against real installs — the task itself defers the on-Windows check to a manual gate (source: docs/tasks/T-002-steam-windows-discovery.md, https://stackoverflow.com/questions/58388230/how-to-read-the-steam-install-path-from-the-windows-registry).
- **`winreg` maintenance posture.** Single-maintainer crate self-described "work in progress"; a low-activity dependency for a registry seam is tolerable given the injectable seam, but `windows`/`windows-core` is the vendor-supported alternative at the cost of a much larger dependency tree (source: https://docs.rs/crate/winreg/latest, https://crates.io/crates/winreg).
- **Fixture portability.** The existing VDF path-resolution rule lets relative `path` values resolve against the VDF's directory so checked-in fixtures stay host-independent; on Windows, fixture `path` values must use `\` or `/` in a way the shared parser and `PathBuf` both normalize consistently — a test-design detail worth deciding once for both platforms (source: crates/discovery/src/steam_linux.rs).

## Open questions

1. Registry crate and seam shape: `winreg` behind a trait vs a plain lookup function (`Fn(RegistryKey, value) -> Option<String>`) mirroring the Linux `env: &dyn Fn(&str) -> Option<String>` pattern — and should the fake-registry type live in the crate (public, for the CLI/tests) or `#[cfg(test)]`-style only (source: docs/tasks/T-002-steam-windows-discovery.md, crates/discovery/src/steam_linux.rs)?
2. Candidate ordering and views: the task fixes HKCU-`SteamPath`-first with a machine-key fallback and env defaults appended; does the design query the HKLM key with both `KEY_WOW64_32KEY` and `KEY_WOW64_64KEY` (steam-game-path does), and are `%ProgramFiles(x86)%\Steam` / `%ProgramFiles%\Steam` appended after registry candidates only, or always?
3. Shared-core decomposition: `steam_common` internal module vs a platform-parameterized `SteamCore` struct (per the task's two suggested shapes) — which keeps the Linux plugin's public API and tests byte-identical while giving the Windows plugin its platform tag in the §7 error message (today the message string starts `steam-linux:`) (source: docs/tasks/T-002-steam-windows-discovery.md, crates/discovery/src/steam_linux.rs)?
4. `libraryfolders.vdf` location policy: keep `steamapps/`-only for cross-platform parity, or accept a second probe at `config/libraryfolders.vdf` given the community reports — and if the latter, does it apply to Linux too, where behavior must not change (source: https://github.com/Playmoir/knowledge-base/blob/main/steam-library-integration.md)?
5. Emitted-path namespace: strip the `\\?\` prefix from canonical paths on Windows (and how: a small Windows-only normalizer vs not canonicalizing the emitted root), or ship extended-length paths and document them?
6. `installdir` hardening beyond the mandated `\` refusal: are reserved device names (`CON`, `NUL`, `COM1`–`9`), trailing dots/spaces, and colon (ADS) rejection in scope, or is the two-separator refusal the complete rule for v1 (source: https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)?
7. `REG_EXPAND_SZ` handling: expand `%VAR%` (another FFI call), refuse the type, or accept verbatim and let the canonical-path rule filter the result?
8. CLI behavior with both plugins registered: on a Linux host with `--steam-root`, should the Windows plugin also scan those roots (producing `steam-windows`-tagged rows from Linux fixture trees), or does the platform tag of roots injected via `--steam-root` follow the host? (source: apps/discovery-cli/src/main.rs)
