## Findings

- [major][re-raised] Chosen design — Read-only git — "So neither the config sources outside the repo (A6) nor a planted `.git/config` or `.git/hooks` runs at runner privilege" (with Apply/escalation: "the plant is inert before any git there" and "a `pipeline resume` (runner.ts:1376) runs over it until the operator removes it"); Risks row 1 — "the plant pinned inert before the escalation's own commit — pinned by #13"; Test strategy #13 — "the hostile config is a `core.fsmonitor` touching a marker file, which stays absent" — The author's recorded rebuttal (Revision log r3: "the plant pinned inert before the escalation's own commit by one config-free env over every runner git call") is unsound: the env is config-free only for sources *outside* the repo. `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=<empty file>` suppress system/global/XDG only; the `-c` pins cover exactly two keys (`core.fsmonitor=false`, `core.hooksPath=<empty dir>`). The planted root `.git/config` — precisely #13's own `git log --output=.git/config` case, which the sweep can neither see nor undo (A4) — remains the discovered repo-local config every runner git call reads at runner privilege: the escalation's own `ESCALATION.md` commit (`finalizeEscalate` → `commitStage`, so `git add -A` then commit) and every subsequent `pipeline resume`, which the doc itself concedes runs over the live plant. Unplanted exec-capable keys survive: `alias.status = '!…'` shadows the builtin the runner spawns (e.g. `gitOk`) and git expands it at the first non-option argument; `filter.evil.clean = '!…'` paired with a stage-written `.gitattributes` (a worktree file the stage legitimately owns) runs at commitStage's `git add -A` — agent-to-runner privilege execution on the escalation path itself. The proposal's own A6 concedes config "is read from more than one place: repo-local `.git/config`, …", contradicting the blanket inertness sentence. #13 pins one hostile key (fsmonitor), so no test pins the claim the design actually makes. `.git/hooks` genuinely is neutralized by the `hooksPath` pin; the `.git/config` half of the claim is false. This replaces the r1 posture this seat approved ("no attempt 2 and no finalize, since both would run in that worktree under the planted config"). Fix: restore the r1 posture — on `git-plant-detected`, no runner git call runs over the infected worktree; this replaces the "Escalation still commits `ESCALATION.md` … so the plant is inert before any git there" sentence and row 1's "the plant pinned inert before the escalation's own commit" (the plant itself stops the pipeline at the operator; the shared config-free env stays for the outside-repo sources it does kill). The alternative of scoping the claim to the two pinned keys and deferring `alias.*`/`filter.<driver>.clean` explicitly admits the escalation commit executes attacker config at runner privilege — this seat cannot approve that variant, so #13's gate must then also pin the claim as scoped (hostile `filter.evil.clean` matching a stage-written `.gitattributes`, marker absent across the escalation's `git add -A`) rather than only fsmonitor.

- [minor][re-raised] Chosen design — Read-only git — "a child agent's `.git` write is audit-blind and the `subagent` deny below is the only cover for that route"; parenthetical — "review seats already run the same two of four, `git diff*` and `git log*`"; Risks row 1 — "child-agent writes are audit-blind, covered by the advisory `subagent` deny only" — Closure of the r1 finding is still incomplete, and the dissent made no change. The `subagent` deny is appended to "the same two configs" (the item-5 seats, coder and test-engineer) only, while the doc's own parenthetical keeps non-item-5 review seats running `git diff*`/`git log*` — both `--output=<file>` write sinks per A6 — in a writable worktree with no `subagent` deny: for those seats the child-session `.git` route has zero cover, not "the deny only". It is also placed nowhere: the Deferred sandbox bullet covers only "config writes landing outside the worktree, or at its root with no `.git` segment", and an in-worktree, `.git`-segment plant from a review seat's child session is neither. Fix: one clause on the Deferred sandbox bullet placing the non-item-5 seats' child-session `.git` route there (the still-unmade r1 ask), or extend the `subagent` deny to every seat whose shell can write the worktree.
