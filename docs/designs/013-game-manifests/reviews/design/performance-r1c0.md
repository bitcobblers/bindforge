# performance review r1

verdict: request-changes

## Findings

- [major][new] Chosen design → The contract → Rules → **Budgets** (and the `presets` row of the entry table) — "`MAX_MANIFEST_ROWS = 256` bounds each of `actions`, `dead-keys`, and `docked-actions`" omits `presets`, and the entry table gives `presets` no count cap. The array is therefore bounded only by the shared 1 MiB document budget: a hostile manifest can carry on the order of 10⁴ slug-grammar preset ids (each ≤63 octets). The per-element `is_slug_name` check and the "each preset id appears once" rule in **One fact per document** then run superlinear in that count (naïve duplicate checking is O(n²) over ~10⁴ entries) — exactly the "many rows" abuse the Risks table claims is covered: "The four named budgets refuse before any join". As written, one of the five string-array shapes falls outside that mitigation, and both the fixture list (no `presets-past-cap.toml`) and Test strategy #4 ("257 `actions` rows, a 65th group — refuse") pin budgets that don't cover it. Fix: bring `presets` under the named budget family — reuse `MAX_MANIFEST_ROWS` (presets are row-shaped entries; no new constant needed) — and add the `presets-past-cap.toml` invalid fixture plus a preset-count case to Test strategy #4, so the mitigation sentence is true of every array in the entry table.
- [nit][new] Chosen design → The contract → Rules → **Budgets** — "Named constants in `manifest.rs`, exported like the existing budget family (A6)": the four values (256 / 64 / 16 / 128) carry no derivation, while the neighboring **Identity grammar** bullet derives its 63-octet cap ("the same DNS-label bound RFC 1035 §2.3.1 publishes"). The values are comfortably above the cited baseline (the 40-id taxonomy, A7; TF2-scale bind lists, A9), so no gap to flag, but a one-line rationale ("256 ≈ several TF2-sized bind lists; 128 octets ≥ the longest surveyed multi-word native name") would make future cap disputes data-driven rather than taste-driven, per the checklist's baseline-quoting item. Fix: one sentence after the constants naming the baseline observation each cap sits above.

## FYI (no severity)

- What the series reads from here — ADR-015's precondition checks are described as "a set-membership lookup over loaded data": with the budgets in place the loaded shapes are ≤256 dead keys, ≤64×16 group members, and ≤256 docked rows, so linear scans over the `Vec`s in the `Manifest` struct are bounded and no per-event IO or allocation is introduced by this design; if 015 turns out to evaluate those checks per event rather than per translation, the lookup cost belongs in 015's document, not here.
- Caching/invalidation: this design ships no caches; its invalidation story is the monotone `revision` + `for` pin, review-enforced per A10 — consistent with the ADR's Decision; nothing for this seat to chase.
