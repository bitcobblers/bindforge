# Research: Configurable reply timeout for the orchestration smoke-test CLI

## Summary

The smoke-test CLI in `tools/orchestration` waits a hard-coded 30 s (`POLL_TIMEOUT_MS`) for the assistant's reply, and the task is to make that configurable via a `--timeout <seconds>` flag and an `OPENCODE_REPLY_TIMEOUT_SECONDS` env default while keeping 30 s as the default (source: docs/prompts/add-timeout-flag.md). The CLI already has an env-var-as-default / flag-wins pattern (`configFromEnv` feeding yargs defaults) that the new option can follow (source: tools/orchestration/src/cli.ts). The timeout lives in `waitForReply`, which computes a wall-clock deadline and returns `null` on expiry, causing `runPrompt` to throw "No response received from OpenCode" — the point where the timeout must be "honored" and "reported" (source: tools/orchestration/src/opencode-runner.ts). Comparable CLIs and libraries (curl, libpq, GNU coreutils `timeout`) converge on seconds as the interface unit, env/flag layering, and a distinguishable timeout outcome. The open design decisions are what `0`/negative/non-numeric values mean, the exact error message and exit behavior, and how the new parameter threads through `runPrompt`'s existing signature and tests.

## Findings

- The reply wait is hard-coded today: `POLL_INTERVAL_MS = 250` and `POLL_TIMEOUT_MS = 30_000` are module constants in the runner; nothing on the `runPrompt` path accepts a timeout (source: tools/orchestration/src/opencode-runner.ts, lines 24–26 and 210–215).
- `waitForReply` computes `deadline = Date.now() + POLL_TIMEOUT_MS`, polls `message.list` each 250 ms after the first immediate check, and returns `null` once the deadline passes; `runPrompt` then throws `Error('No response received from OpenCode')`. That message is the current and only timeout report, and it does not mention the elapsed duration (source: tools/orchestration/src/opencode-runner.ts, lines 220–223 and 253–274).
- The CLI already implements the exact precedence the task needs — env vars supply yargs option defaults and explicit flags win: `configFromEnv()` reads `OPENCODE_BASE_URL`, `OPENCODE_SERVER_USERNAME`, `OPENCODE_SERVER_PASSWORD`, `OPENCODE_AGENT` and each option's `default` comes from it. `OPENCODE_REPLY_TIMEOUT_SECONDS` slots into this established `OPENCODE_*` family (source: tools/orchestration/src/cli.ts, lines 46–88; option table in tools/orchestration/README.md).
- The runner receives no timeout today, so "honored by `runPrompt`" implies a signature change (e.g. a field on `PromptOptions` such as `timeoutMs`/`timeoutSeconds`); `runPrompt` has exactly one production call site, `main()` in `cli.ts` line 112, plus test call sites (source: grep of tools/orchestration/src and tools/orchestration/tests).
- An existing test already locks in the current timeout behavior: it uses `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(31_000)` and asserts rejection with "No response received from OpenCode". "Existing tests must stay green" means the default must remain exactly 30 s, and new configurable-timeout tests can reuse the same fake-timer pattern with a small value (source: tools/orchestration/tests/opencode-runner.test.ts, lines 243–257; docs/prompts/add-timeout-flag.md line 13).
- Documentation will need updating alongside the code: the README's option table lists only the four existing flag/env pairs, and its Behaviour section states "polls `message.list` every 250 ms (up to 30 s)" (source: tools/orchestration/README.md, lines 16–21 and 34–35).
- There is an internal naming precedent for a configured timeout: the pipeline stage config uses `stageTimeoutMs` with a 15-minute default, but the pipeline CLI builds its own request loop and never calls `runPrompt`, so it is out of scope (source: tools/orchestration/src/pipeline/stages.ts, lines 31–39; tools/orchestration/src/pipeline/cli.ts, line 8).
- The task is explicitly bounded: keep the change inside `tools/orchestration`, keep 30 s as the default, and keep existing tests green (source: docs/prompts/add-timeout-flag.md, lines 7–13).

## Prior art

Applying the **Prior art** lens (comparable solutions, names/formats, conventions):

- **curl** splits timeout into `CURLOPT_TIMEOUT` (a long, "the maximum time in seconds that you allow the entire transfer operation to take", added in curl 7.1) and `CURLOPT_TIMEOUT_MS` (same option in milliseconds), with last-set-wins when both are given; the default is `0`, meaning "never times out during transfer" (source: https://curl.se/libcurl/c/CURLOPT_TIMEOUT.html). Its docs also caution that a single hard limit "has limited use in dynamic use cases with varying transfer times" — directly relevant since assistant replies vary widely in duration (source: same URL).
- **PostgreSQL libpq** uses `connect_timeout`, "Maximum time to wait while connecting, in seconds (write as a decimal integer…); Zero, negative, or not specified means wait indefinitely", and exposes the same parameter through the `PGCONNECT_TIMEOUT` environment variable — a direct precedent for a seconds-based timeout with an env-var twin (source: https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CONNECT-TIMEOUT and https://www.postgresql.org/docs/current/libpq-envars.html).
- libpq also formalizes the precedence this repo already uses informally: unset parameter → environment variable → built-in default (source: https://www.postgresql.org/docs/current/libpq-connect.html).
- **GNU coreutils `timeout`** takes duration as "a floating point number … followed by an optional unit" with `s` (seconds) as the default unit (`s`/`m`/`h`/`d`), treats "a duration of 0" as disabling the timeout, and reports a timed-out run distinguishably with exit status `124` — precedent for making the timeout outcome identifiable beyond a generic error (source: https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html).
- Naming convention by convergence: all three use plain seconds for the human-facing interface (`--max-time`-style flags, `connect_timeout`, `timeout 5s`); millisecond variants exist only as machine/API alternatives (`CURLOPT_TIMEOUT_MS`). A seconds-valued `--timeout` plus a `…_SECONDS` env var matches that convention, while the repo's internal constants stay `…_MS` (source: URLs above; tools/orchestration/src/opencode-runner.ts, lines 25–26).
- No comparable tool treats a negative value as valid except libpq, which folds it into "wait indefinitely" (source: https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CONNECT-TIMEOUT). Whether to allow that at all is left as an open question below.

## Platform notes

Applying the **Platform notes** lens (toolchain specifics relevant to BindForge):

- The repo pins Node Next module resolution with `target: ES2022`, runs tests on Vitest 5, and parses CLI options with yargs 17.7.3 (`@types/yargs` for typing); yargs parses `--ships=4`-style numeric options as numbers, so a numeric `--timeout` needs only a `type: 'number'`-style declaration plus validation (source: tools/orchestration/tsconfig.json; tools/orchestration/package.json, lines 40–46; https://raw.githubusercontent.com/yargs/yargs/main/README.md).
- Node's timer clamp is a real trap for alternative designs: for `setTimeout`, "when `delay` is larger than 2147483647 or less than 1 or `NaN`, the `delay` will be set to 1" — so a hypothetical `Promise.race`-style implementation would silently degenerate to a 1 ms timer for huge or bogus values (source: https://nodejs.org/api/timers.html#settimeoutcallback-delay-args). The current design is immune because the deadline is wall-clock arithmetic (`Date.now() + timeout`) and only a fixed 250 ms `sleep()` is passed to `setTimeout` (source: tools/orchestration/src/opencode-runner.ts, lines 257–298).
- Env vars are always strings, so the env default needs an explicit, validated conversion; today every `OPENCODE_*` env read is used as a raw string with no numeric parsing precedent in this CLI (source: tools/orchestration/src/cli.ts, lines 50–57).
- No OS-specific behavior is involved: the wait is HTTP polling plus timers, identical on Linux/macOS/Windows (source: tools/orchestration/src/opencode-runner.ts).

## Risks & unknowns

- The 31 s fake-timer test couples the test to both the 30 s default and the exact rejection message; any change to the default or to the message shape breaks "existing tests must stay green" unless the test is intentionally updated alongside (source: tools/orchestration/tests/opencode-runner.test.ts, lines 243–257).
- "Reported clearly when it elapses" is unspecified: current output is one generic `Error` string with no timeout duration, no flag/env attribution, and no distinct exit code (source: tools/orchestration/src/opencode-runner.ts, lines 220–223).
- Seconds→ms conversion of unbounded user input (huge `--timeout`) is safe with the deadline pattern but would hit the Node timer clamp with other designs (source: https://nodejs.org/api/timers.html#settimeoutcallback-delay-args).
- A timeout smaller than one poll interval still yields exactly one immediate `message.list` check before the deadline can expire, because the current loop checks for a reply before sleeping — surprising but bounded behavior the designer should pin down (source: tools/orchestration/src/opencode-runner.ts, lines 259–271).
- Unknown whether `@opencode/client` itself exposes per-request HTTP timeouts that could produce different failure modes (connection hang vs reply timeout); the repo code does not configure any (source: tools/orchestration/src/opencode-runner.ts, lines 46–62).

## Open questions

1. What should `--timeout 0` (or `OPENCODE_REPLY_TIMEOUT_SECONDS=0`) mean — "wait forever" as in curl, libpq, and coreutils (source: https://curl.se/libcurl/c/CURLOPT_TIMEOUT.html; https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CONNECT-TIMEOUT; https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html) — or a validation error?
2. Are negative, fractional, and non-numeric values rejected, and what upper bound (if any) is enforced?
3. How should the elapsed timeout be reported: extended error message with the effective duration and its source (flag/env/default), a dedicated exit code in the `124`-style coreutils tradition (source: https://www.gnu.org/software/coreutils/manual/html_node/timeout-invocation.html), or the current generic message?
4. API shape: add the timeout to `PromptOptions` (e.g. `timeoutMs`) or as a separate `runPrompt` argument, and should the value cross the CLI↔runner boundary in seconds or ms?
5. Is the 250 ms poll interval expected to stay hard-coded, or should the design mention it (the README documents the pair "250 ms / 30 s") (source: tools/orchestration/README.md, lines 34–35)?
6. Should the existing 31 s fake-timer test keep asserting the 30 s default verbatim as a regression guard, with new tests covering flag/env overrides at small timeouts (source: tools/orchestration/tests/opencode-runner.test.ts, lines 243–257)?
