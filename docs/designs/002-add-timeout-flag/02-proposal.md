# Design: Configurable reply timeout for the orchestration CLI (`--timeout` / `OPENCODE_REPLY_TIMEOUT_SECONDS`)

## Context

The smoke-test CLI in `tools/orchestration` waits a hard-coded 30 s for the assistant's reply. This design makes that wait configurable via a `--timeout <seconds>` flag and an `OPENCODE_REPLY_TIMEOUT_SECONDS` environment default, keeping 30 s as the default, honouring the value inside `runPrompt`, and reporting the elapsed timeout clearly. Source document: `docs/prompts/add-timeout-flag.md`; supporting research: `docs/designs/002-add-timeout-flag/01-research.md`. The change stays inside `tools/orchestration` and existing tests must stay green.

## Goals / Non-goals

- Goals:
  - A `--timeout <seconds>` CLI option with `OPENCODE_REPLY_TIMEOUT_SECONDS` as its environment default, resolved flag → env → 30 s.
  - `runPrompt` honours the configured timeout (no longer a hard-coded constant on its path) and fails closed on invalid values at the API boundary, not only in the CLI.
  - When the timeout elapses, the failure is distinguishable by error type and reported with the effective duration and how to change it.
  - Existing tests pass unchanged, including the test that pins today's default and message.
  - `tools/orchestration/README.md` stays truthful about the new option and the polling behaviour.
- Non-goals:
  - Making the 250 ms poll interval configurable.
  - Any change to the pipeline (`src/pipeline/`), including its `stageTimeoutMs`.
  - Per-request HTTP timeouts inside `@opencode/client`.
  - New process exit codes or a distinct "timeout" exit status.
  - "Wait forever" semantics for `0` or negative values (see Options considered).
  - Redaction of credential material in the pre-existing startup print of `baseUrl` (existing behaviour, cli.ts:107; the new banner text adds only the resolved duration — see security r1 logging rule).
  - Adding CI configuration anywhere in the repository (outside `tools/orchestration`; affects how the compatibility matrix is exercised — see Compatibility matrix and Test strategy #12).
  - Any change outside `tools/orchestration`.

## Options considered

**API threading.** Add `timeoutMs?: number` to `PromptOptions` in `opencode-runner.ts`, versus a fifth positional argument to `runPrompt`, versus passing seconds at the API boundary. The positional argument is rejected: it worsens every call site (`runPrompt(client, {}, schema, prompt, 30)` reads poorly) and churns all test call sites for no gain, while `PromptOptions` is the established place for per-run knobs (`agent`, `title`). A `timeoutSeconds` field at the API boundary is rejected because the repository's internal convention is milliseconds (`stageTimeoutMs`, `POLL_TIMEOUT_MS`, A10); seconds are reserved for the human-facing CLI surface (A6).

**Value semantics for `0`, negative, fractional, and huge inputs.** Reject everything except integer seconds in `1..3_600`, versus libpq/curl/coreutils-style "`0` means wait forever". Waiting forever is rejected: this CLI exists as a bounded connectivity/auth smoke test whose purpose is defeated by an unbounded wait, and the task pins the bounded 30 s as the default (A14). Fractional seconds are rejected because the prior-art human-facing interfaces are integer seconds (A6, libpq explicitly "decimal integer") and sub-second polling granularity is meaningless against a 250 ms poll interval; coreutils' floating-point durations are the outlier and are tied to its unit-suffix syntax, which we are not adopting. The upper bound is a **product decision** (A16), not an evidence-backed limit, and is sized from an abuse standpoint as much as a typo-guard one: with the interval fixed at 250 ms, a valid wait issues roughly `timeoutMs / 250` `message.list` requests — ~121 at the 30 s default, ~14 400 at the 3 600 s cap — so the cap also bounds request pressure and the recursion's pending-promise depth against whatever `OPENCODE_BASE_URL` names. An 86 400 s bound (2880× the default, ~345 600 polls) was considered and judged too large a self-inflicted DoS surface for a smoke test; no upper bound at all was considered (the wall-clock deadline makes huge values technically safe, A9) and rejected because a mistyped unit would silently hammer a server. If long timeouts ever become normal practice, making the poll interval adaptive is the obvious follow-up — the fixed interval is the knob that becomes load-relevant at large `--timeout` values.

**Timeout reporting.** Three shapes: keep the current generic message, throw a dedicated error type with an extended message, or additionally adopt the coreutils-style exit status 124. Keeping the generic message is rejected because the task requires the elapsed timeout to be "reported clearly" and the current message names neither the duration nor the knobs (A2). Exit code 124 is rejected: the CLI's contract today is exit 1 for any failure (A13), no consumer in this repository needs a distinct code, and adding one is a compatibility change beyond the task's scope; an exit code can be revisited if CI tooling demands it. The chosen shape is a `ReplyTimeoutError` whose message keeps the old string as an exact prefix — this is what makes "existing tests stay green" compatible with a clearer report (A5). Following the same "no consumer in this repository" argument used against exit code 124, the error class carries **no data properties**: the effective duration is already in the message, and `main()`'s catch only prints the error (cli.ts:120–123).

**Wiring in `cli.ts`.** Mirror the established pattern exactly (parse env in `configFromEnv()`, feed it as the yargs `default:`), versus a single exported resolver function that owns precedence and validation. The pure-pattern mirror is rejected for this option because yargs would coerce a bad env string to a non-finite value that slips through as a default (A8), and precedence/validation would be split across `configFromEnv()`, the yargs schema, and `main()`. The chosen resolver keeps env reads centralized in `configFromEnv()` (preserving A3's intent) while making precedence and validation one exported, unit-testable function. Because the resolved value is a validated number while the env read is a raw string, the env bag gets its own type (`EnvValues`) instead of overloading `CliConfig` — the two interfaces are module-private, so reshaping them breaks no exported API. The other four options keep the existing pattern untouched because plain strings need no validation.

**Poll interval configurability.** Rejected as scope creep: the task names only the reply timeout, and the README's "250 ms" half of the pair stays accurate after rewording (A15). Its load relevance at large timeouts is instead bounded by the 3 600 s cap (above) and recorded in the Risks table.

## Chosen design

Two source files change in `tools/orchestration/src/`, plus one `package.json` line, the README, and the tests in `tools/orchestration/tests/`.

**`src/opencode-runner.ts`**

- Replace `const POLL_TIMEOUT_MS = 30_000` (line 26) with `export const DEFAULT_REPLY_TIMEOUT_MS = 30_000;` and add `export const MAX_REPLY_TIMEOUT_MS = 3_600_000;`, following the existing `DEFAULT_BASE_URL` export pattern (line 20) so both bounds have a single source of truth shared with the CLI. `POLL_INTERVAL_MS = 250` stays as is.
- Add an optional `timeoutMs?: number` field to `PromptOptions` (interface at lines 101–117). Its docblock states the full runner-side contract: the wall-clock cap on waiting for the completed assistant reply; when provided it must be an integer in `1..MAX_REPLY_TIMEOUT_MS` and is **enforced by `runPrompt` itself** (fail closed, see next bullet), so the cap is a property of the exported API, not only of the CLI; values below `POLL_INTERVAL_MS` (i.e. < 250) are legal: the loop tests the deadline only *after* each reply check (opencode-runner.ts:259–271), so such a value yields exactly two `message.list` checks — one immediate, one after a single 250 ms sleep — then a timeout, overshooting the configured deadline by at most one poll interval (pre-existing loop shape, unchanged; Test strategy #6 pins it). Being optional, every existing call site compiles and behaves identically (A4, A11).
- **Boundary validation (fail closed).** `runPrompt` resolves `const timeoutMs = options.timeoutMs ?? DEFAULT_REPLY_TIMEOUT_MS`, then throws a `TypeError` naming the bad value unless `Number.isInteger(timeoutMs) && timeoutMs >= 1 && timeoutMs <= MAX_REPLY_TIMEOUT_MS`, *before* creating the session, so an invalid value produces zero HTTP requests. This is required because `??` only catches `null`/`undefined`: a direct API consumer passing `Number.POSITIVE_INFINITY`, `NaN`, `0`, or a negative value into `Date.now() + timeoutMs` would make `Date.now() >= deadline` permanently false and poll `message.list` every 250 ms forever — the resolver's guard would never run, and the design's huge-value safety argument (A9, A16) would silently fail open.
- Add to the Errors section (near `describeError`, line 301+): `export class ReplyTimeoutError extends Error` with the message `No response received from OpenCode within <n> s (set --timeout or $OPENCODE_REPLY_TIMEOUT_SECONDS to change it)` — the old string kept verbatim as the prefix (A5) so the failure is both backward-compatible and clearer. `<n>` is formatted as `timeoutMs / 1000` rendered as a plain JS number, so integer-second CLI values print `within 4 s` and sub-poll API values print `within 0.1 s` — no other rounding or units. The class carries no data properties (see Timeout reporting).
- Change `waitForReply(client, sessionID)` to `waitForReply(client, sessionID, timeoutMs)`; the deadline stays wall-clock arithmetic (`Date.now() + timeoutMs`, lines 253–274), the same pattern the pipeline runner already uses (A10) and immune to the timer clamp (A9). `waitForReply` receives only validated values and keeps its `null`-on-expiry contract; `runPrompt`'s throw site (lines 220–223) becomes `throw new ReplyTimeoutError(...)`.

**`src/cli.ts`**

- Two distinct module-private types, stated explicitly (both are internal to `cli.ts` today — `CliConfig` is not exported, cli.ts:16 — so reshaping breaks no API):
  - `interface EnvValues { baseUrl: string; username?: string; password?: string; agent?: string; replyTimeoutSeconds?: string }` — the raw env bag returned by `configFromEnv()` (today typed `CliConfig`, cli.ts:50), which gains `replyTimeoutSeconds` read raw from `process.env.OPENCODE_REPLY_TIMEOUT_SECONDS` (env reads stay centralized; A7).
  - `CliConfig` keeps `baseUrl/username?/password?/agent?` and gains exactly **one** timeout field, `timeoutSeconds: number`, populated by `main()` from `resolveReplyTimeoutSeconds(...)` inside the `const config: CliConfig = {...}` literal (lines 95–100) — `configFromEnv()` never returns it, so the value appears once, as a validated number.
- `CliArgs` (lines 26–31) gains `timeout?: number`. The yargs schema gains `.option('timeout', { type: 'number', describe: 'Seconds to wait for the assistant reply (default: 30; env: $OPENCODE_REPLY_TIMEOUT_SECONDS)' })` with deliberately **no** `default:` — precedence lives in the resolver below.
- New exported pure function `resolveReplyTimeoutSeconds(flagValue: number | undefined, envValue: string | undefined): number`:
  - Format gate on env first: if `envValue !== undefined && !/^\d{1,5}$/.test(envValue)`, throw naming `$OPENCODE_REPLY_TIMEOUT_SECONDS` and the expected format — this precedes any `Number()` call, which is far looser than integer seconds (`"0x2d"` → 45, `"1e4"` → 10000, `" 45\n"` → 45, `"+45"` → 45 would all silently change the user's written value). The gate runs whether or not `--timeout` is present, so a malformed env value fails the run even when a valid flag overrides it — a broken environment is a configuration error, not something to silently ignore (Test strategy #8).
  - Precedence flag → env → `DEFAULT_REPLY_TIMEOUT_MS / 1000`; the range check (`Number.isInteger` and `1..MAX_REPLY_TIMEOUT_MS / 1000`) is separate from the format rejection and its message names the source (`--timeout` or `$OPENCODE_REPLY_TIMEOUT_SECONDS`). `Number.isInteger` also catches yargs' non-finite output for junk flag input (A8).
  - Error messages never interpolate the raw env string: any reflected value is embedded via `JSON.stringify(value)`, which escapes control and ANSI bytes, so `console.error(error)` (cli.ts:121) can print the message without terminal-escape injection or spoofed follow-on output. Flag values reach the resolver as numbers and print safely.
  - The 30 default and the 3 600 cap are derived as `DEFAULT_REPLY_TIMEOUT_MS / 1000` and `MAX_REPLY_TIMEOUT_MS / 1000` to avoid a second set of hard-coded bounds.
- `main()` runs the resolver **immediately after `parseArgs()` and before `createClient()` (line 101) and before any `console.log`**, so a config error produces exactly one error line and no side effects (no auth-header client built, no success-shaped banner printed). The startup log (line 107) is extended with only ` waiting up to <n> s for the reply` — static text plus the resolved integer; no new config value is printed, and the pre-existing unredacted `baseUrl` on that line is left untouched (non-goal). The existing "no password was provided" hint (lines 108–110) stays verbatim: it names `--password`/`OPENCODE_SERVER_PASSWORD` but never echoes a credential value, so the extended banner adds only the resolved duration (security r1's logging rule). The call at line 112 becomes `runPrompt(client, { agent: config.agent, timeoutMs: config.timeoutSeconds * 1000 }, FunFactSchema, SAMPLE_PROMPT)`. Seconds cross the CLI boundary; milliseconds cross the CLI↔runner boundary (A6, A10).

**Data flow and input trust.** argv and env are both **untrusted operator input** — CI config, container images, and wrapper scripts can set either independently of the human typing the command — and are covered by `resolveReplyTimeoutSeconds`' regex format gate, range check, and `JSON.stringify`-escaped reflection; the runner-side `TypeError` check is the second gate for API consumers who bypass the CLI. The OpenCode server's reply remains **untrusted network input** as today: `waitForReply`/`findCompletedReply`/`parseContent` JSON-parse response bodies and `main()` prints the validated result — this design adds no new trust to that path and changes nothing in it. The only value that crosses into the deadline arithmetic is the validated integer: argv/env → `parseArgs()` (yargs yields the flag as a number or `undefined`) and `configFromEnv()` (raw env string) → `resolveReplyTimeoutSeconds()` (precedence, format gate, validated integer seconds; validation errors print and exit 1 like any other config error, A13) → `× 1000` → `PromptOptions.timeoutMs` → `runPrompt`'s boundary `TypeError` check → `waitForReply` wall-clock deadline → on expiry `ReplyTimeoutError` → module-level catch prints it, exit code 1 unchanged (A13).

**`package.json`** — add `"engines": { "node": ">=22.12.0" }`, the Node floor the Compatibility matrix now names: it matches the existing `vitest ^5.0.5` requirement (A21) and gives the toolchain row a checkable anchor. `engines` is advisory unless `engine-strict` is set, so this adds no enforcement burden — every API this design uses (`Date.now`, `Number.isInteger`, `setTimeout`, `class extends Error`) predates the floor by years. The declared floor is deliberately the **toolchain** floor, the only one the repository can currently support (A21); no lower runtime floor is claimed here, because nothing in the tree establishes one.

**`README.md`** — add the row `| --timeout | OPENCODE_REPLY_TIMEOUT_SECONDS | 30 s (integer, 1–3 600) |` to the options table (lines 16–21) and reword Behaviour item 3 (lines 34–35) to "polls `message.list` every 250 ms until a completed assistant message is available or the reply timeout (default 30 s, set via `--timeout` or `$OPENCODE_REPLY_TIMEOUT_SECONDS`) elapses" (A15). The pre-existing drift at README:28 (session title "SDK connection test" vs `SESSION_TITLE = 'Untitled Session'`, opencode-runner.ts:22) is out of this change set; the implementer leaves it alone or fixes it in a separate `docs:` commit.

## Test strategy

1. Unit (regression guard): the existing test `tests/opencode-runner.test.ts:243–257` (`vi.useFakeTimers()` + `advanceTimersByTimeAsync(31_000)`, default options) passes with **no edits**, proving the 30 s default and that the new message keeps `'No response received from OpenCode'` as a prefix (A5).
2. Unit: `runPrompt` with `options.timeoutMs = 4_000` and a never-replying stub client rejects with an error that is `instanceof ReplyTimeoutError` and whose message contains `within 4 s` (fake-timer pattern from #1).
3. Unit: a reply that appears after one 250 ms poll but before the deadline still resolves successfully with a custom `timeoutMs` (proves the timeout is a cap, not a forced failure).
4. Unit: `runPrompt` with no `options.timeoutMs` rejects only after the 30 s default has elapsed — fake timers advanced 29_000 ms must not reject, 31_000 ms must (proves `DEFAULT_REPLY_TIMEOUT_MS` is the fallback on the runner side).
5. Unit (fail closed at the API boundary): `runPrompt` with `timeoutMs` of `Number.POSITIVE_INFINITY`, `NaN`, `0`, `-5`, and `3_600_001` each rejects immediately with a `TypeError` **and** the stub client's `create`/`prompt`/`list` spies have zero calls — no infinite poll, no session created (security r1 major; real timers, since the call must reject synchronously).
6. Unit (sub-poll-interval contract): `runPrompt` with `timeoutMs = 100` performs exactly **two** `message.list` calls — one immediate, one after a single 250 ms fake-timer sleep, because the deadline is only tested after each reply check (elapsed overshoot ≤ one poll interval) — and then rejects with `ReplyTimeoutError` whose message contains `within 0.1 s` — pins the behaviour that research line 43 asks the designer to fix, and the `<n> s` formatting rule.
7. Unit: `resolveReplyTimeoutSeconds` precedence — flag `45` beats env `"5"`; env `"5"` beats the 30 default; neither present yields 30.
8.
