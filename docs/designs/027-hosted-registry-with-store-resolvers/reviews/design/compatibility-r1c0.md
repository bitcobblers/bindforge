## Findings

- [major][new] §Issued entries, the mint, and identity bookkeeping → "The mint rule (`027-C5`, restated in full)", step 3 — "Truncation is **not** part of the rule: … a derived slug is grammar-valid and within `MAX_SLUG_OCTETS` by construction" — the claim is false by arithmetic, because the rule *adds* octets to an input that is already allowed to sit on the same bound: `MAX_NATIVE_NAME_OCTETS = 128` (`crates/core/src/manifest.rs:58`) and `MAX_SLUG_OCTETS = 128` (`crates/core/src/placement.rs:83`) are one number, and step 2's `g-` prefix adds 2 octets while `027-C5`'s collision spelling `-steam-<appid>` adds 7 + the appid's digits. A legal 128-octet store name that opens with a digit mints 130 octets; any name whose derived slug is ≥ ~115 octets mints over 128 the moment it collides. Both the rule it claims to re-pin and the source ADR say otherwise: `024-C2` ends "prefix `g-` a leading digit; … **cap at the shared bound**" (`docs/adrs/024-game-slug-identity.md`), and `027-C5` spells the mint as "the shared-grammar slug … **bounded to the slug budget**" — so the step was dropped, not re-pinned. Concrete failure, with evidence: an over-bound `game_id` fails the registry's own issued-document gate (`apps/registry/src/corpus.rs`, `game_id_is_valid` inside `record_from_value`, which §Issued entries adopts verbatim via "the same `corpus.rs::Catalog` type"), so the mint writes an `issued-v1.json` its next load refuses by name; on the client side the `025-L5` gate drops the candidate (`apps/discovery-cli/src/catalog.rs:456-470`) and the match store refuses to confirm it (`apps/discovery-cli/src/matches.rs:284` and `:354`, same `is_slug_name` ∧ `≤ MAX_SLUG_OCTETS` check) — the minted identity is unservable and unusable, and `027-L2` makes it permanent. Test strategy #1 asserts "every output satisfies `is_slug_name` ∧ `≤ MAX_SLUG_OCTETS`", a property the rule as written cannot deliver. Fix: replace the "by construction" sentence with a bound test that routes to the *already-existing* step-4 fallback — "empty result **or** a derived slug that does not fit `MAX_SLUG_OCTETS` with room for the `-steam-<appid>` suffix (and the `g-` prefix)" mints `steam-<appid>` — no truncation rule, no new mechanism, and the fallback stays a function of the appid so it is record-stable per `027-L2`.

- [major][new] §Options considered → "**In-process HTTPS pull over a pure-Rust TLS stack** (chosen)" (with §Test strategy #17 "CI needs no edit" and the matrix's Linux "rustls/ring build in CI" / Windows "not run in CI") — the chosen stack is not pure Rust: the `ring` provider compiles C and hand-written assembly for the *target* through a build script, and build scripts run even under `cargo check`. The shipped gate already cross-compiles this workspace for Windows from Linux — `.github/workflows/check.yml:26-32` runs `rustup target add x86_64-pc-windows-msvc` then `cargo check --workspace --all-targets --target x86_64-pc-windows-msvc` on `ubuntu-latest`, precisely because "cargo check performs no code generation or linking" — and that runner has no MSVC C toolchain for a foreign-target build script to drive. The design's whole mitigation for the dependency is "versions pinned; cargo trio covers it" plus "CI needs no edit", and it never states the host-toolchain prerequisite the crate's std-only posture previously let the project disclaim: `README.md:13-15` documents the cargo gate as needing none of the listed system dependencies. Fix: settle the packaging/toolchain question in the document before implementation — either record the evidence that the pinned `rustls`/`ring` versions keep that existing leg green, or name the workflow change (compile-check `apps/registry` on the host while the rest of the workspace keeps the cross-target leg) and the `README.md` contributor-prerequisite line that now names a C toolchain; and stop calling a C/asm build-script dependency a "pure-Rust TLS stack".

- [minor][new] Compatibility matrix → "Windows … not run in CI" and "macOS … not a macOS CI runner", both rows "Supported? Yes", with §Test strategy #16 "proven through the `DataLayout`/env-injection seams and compile coverage, not a runner" — two rows claim support that no gate in the repository produces, and the Windows note is factually wrong: the shipped workflow *does* run a Windows compile leg for the whole workspace (including `apps/registry`), which is exactly where finding 2 lands; macOS has no leg of any kind, so "compile coverage" names something nobody runs. Checklist #7 wants a platform test named for every platform the matrix supports. Fix: correct the Windows note to the existing `x86_64-pc-windows-msvc` compile leg (and make it the place finding 2's resolution is proven); either add the same-style compile-only leg for a macOS target from the Linux runner (the workflow already justifies that technique for `cfg(windows)`) or change the macOS/Windows rows to the honest status — dev/one-shot posture, not a hosting target — so "Yes" is reserved for what CI actually builds.

- [minor][new] §Options considered (mint basis) — "the six curated ids are exactly what the rule would mint from those names — is what makes mint-then-promote cohere rather than collide" — the shipped seed contradicts it: `data/catalog/v1/catalog.json` spells the record named "Portal 2" as `portal-two`, which this rule derives as `portal-2`; five of six converge, not six. The consequence is not cosmetic under `027-L2`: if that curated record is ever deleted, appid 620 re-mints as `portal-2` and both ids stay alive forever, with the older one already held by any match store that confirmed it — precisely the second-identity case the immortality law exists to keep singular. Fix: restate the convergence evidence with the real count and name `portal-two` as the exception, and add the sentence on what a re-mint of a curated appid costs under `027-L2` (Rollout 6's cap/promotion arithmetic is where an operator reads it).

- [minor][new] Compatibility matrix → "Bound CLI clients (any platform) … the new `503`s render as the shipped status-line-only refusal" — the rendering is right but the consequence is understated: the shipped client fails the *whole scan* on any non-200 (`apps/discovery-cli/src/main.rs`, step 4: "A mid-scan failure fails closed: no partial table (`025-C4`)"), so once a snapshot passes `027-B2`'s age bound the first novel steam key turns a user's `discovery list` into a refused run, and the Risks table's "`027-L3`'s named `503` is the honest degraded posture while corpus+issued keep serving" is a server-side claim no bound client can render. The posture itself is `027-L3`-mandated and is not re-opened here. Fix: one clause in that matrix row, echoed in the key-revocation risk row, naming the fail-closed client rendering, so the runbook treats snapshot age as a user-visible availability property rather than an operator-only detail.
