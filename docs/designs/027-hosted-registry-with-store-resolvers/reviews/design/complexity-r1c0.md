# complexity review r1 (c0, full panel, whole document)

verdict: request-changes

## Findings

- [major][new] Chosen design §Issued entries — "The mint rule", step 3 — "Truncation is **not** part of the rule: … a derived slug is grammar-valid and within `MAX_SLUG_OCTETS` by construction" — the fold step cannot exceed the name's octets, but the rule's own later steps add octets: step 2's `g-` prefix adds 2 octets (the suite's `g-7-days-to-die` vector is the design's own pin) and step 5's `-steam-<appid>` suffix adds 7+ octets. The snapshot loader admits names up to `MAX_NATIVE_NAME_OCTETS = 128` (verified: `crates/core/src/placement.rs`), so an ASCII digit-leading name of 127–128 octets mints a 129–130-octet id, and any collision suffix onto a slug over ~121 octets also breaches `MAX_SLUG_OCTETS = 128`, which the very `026-C3` loader the design reuses enforces (`corpus.rs::game_id_valid`: `is_slug_name(game_id) && game_id.len() <= MAX_SLUG_OCTETS`). The mechanism removal ("no new rule") rests on arithmetic that omits the rule's own expansions; Test strategy #1's "every output satisfies `is_slug_name` ∧ `≤ MAX_SLUG_OCTETS`" is unfalsifiable-by-construction as pinned. Fix: add one final step to the mint rule — if the final id exceeds `MAX_SLUG_OCTETS`, substitute `steam-<appid>` (≤26 octets under the closed key grammar's appid bound), held-set-checked like any id, and delete the "by construction" claim; this replaces text, it adds no stage beyond one length compare.

- [major][new] Chosen design §Issued entries — "The mint rule", step 5 — "A suffix-vs-suffix collision is arithmetically impossible (the suffix is a function of the appid)" — the held set is `games ∪ retired` across **both** catalog documents, and corpus ids are operator-chosen grammar strings, not mint outputs; a curated (or retired) record whose free-chosen id already spells `<slug>-steam-<appid>` for the same slug/appid pair is reachable, and as written the mint emits a suffixed id that is already held — no refusal, `027-L2` uniqueness broken across documents. The impossibility argument only holds if every suffixed id came from a mint, which the corpus's `026-C4` upsert freedom contradicts. Fix: run the existing held ∪ retired check on the *suffixed* id before serving, routing to the same named `503` `mint identity held`; this replaces the impossibility sentence with one more lookup the rule's machinery already performs.

- [minor][new] §The store pull / §Budgets — "Per page, up to `STEAM_PAGE_ATTEMPTS` (3) attempts separated by `STEAM_RETRY_SECONDS`" — one 3,600 s constant serves two different loop tempos: the refresh thread's between-pull retry and the within-pull page-attempt gap. One flaky page at startup therefore defers the named startup refusal by up to 2+ hours (two hour-long gaps inside the pre-bind full pull), a behavior no Risks row, Rollout item, or runbook mention acknowledges. Fix: split the knob — a short seconds-scale backoff for page attempts, `STEAM_RETRY_SECONDS` reserved for the refresh thread — or pin the startup cadence explicitly in §The store pull and add a Risks row; name what the single number replaces.

## Checklist walk

1. Reuse: verified — `corpus.rs::Catalog` (cap-as-parameter), `persist.rs` fixed-tmp `create_new`/`0600`/`0700`, the `FETCHED_AT_*` pair (`constants.rs:68,72`), the hand-rolled `TcpStream` HTTP posture (`upstream.rs`), and the loopback-fake test discipline are all reused, not re-invented. No live slug-derivation exists to reuse: `derive_slug` survives only in the never-default `retired-adr-024-suites` gate and the retirement gate scans `crates/discovery/src` + `apps/discovery-cli/src` (verified in `crates/discovery/Cargo.toml`, `retirement_tests.rs`), so the fresh `mint.rs` is forced, not duplicative. `tools/` holds only the Node orchestration CLI — nothing reusable.
2. Goal trace: every moving part names its `027-C/L/B` unit; the one part unasked by the ADR (retired-ids) traces cleanly to `027-L2`'s "deleting a record never frees its id", and folding it into `issued-v1.json` would violate `027-C4`'s pinned `026-C3` shape. The epic slot is a named-`503` rule, not a dead abstraction.
3. Smaller design: the reduction candidates (tombstones-in-place, shared framing crate, batched writes, file key custody) are all considered or deferred with reasons; nothing else looks safely cuttable. The two mint findings are the cost of two of those cuts — the cuts are the right shape but the closure arguments need the one added compare/lookup each.
4. Dependencies: verified no TLS/HTTP crate anywhere in the workspace; `rustls`+`webpki-roots`+`ring` are genuinely new, confined to the `steam.rs` seam, and proportionate to a keyed secret crossing the public internet; the plaintext alternative the removal would buy is properly refused. `ureq` rejection reasoning is sound.
5. Deferral: Rollout items 2–5 already stage mode → resolver → issuance → curation; issuance-without-delete-route (item 4 before 5) is exactly the window that keeps retired-ids from being needed earlier. Nothing further worth deferring.
6. Knobs: all fourteen new constants have named consumers; `Mode::Hosted` as a one-inhabitant enum is a health-field carrier, not a knob. The `STEAM_RETRY_SECONDS` dual-tempo finding above is the only knob-shaped defect.
7. Value: proportionate. One hosted mode, one resolver, one mint, one retirement ledger, one seam for TLS — against the ADR's goal of a registry that actually answers. Complexity is concentrated in identity permanence, which is precisely what the ADR's Consequences say is load-bearing.

## FYI (no severity)

- §Budgets: "A6's daily allowance is ~6,000× the worst pull" — 100,000/day ÷ 12 pages ≈ 8,300 (≈2,800 with the 3-attempt bound); the figure is untraceable, though the orders-of-magnitude conclusion is safe either way. (correctness)
- §Issued entries, retired ids: the behavior of a delete whose retired-list append would breach `MAX_RETIRED_IDS_OCTETS` is unpinned — 32 MiB is well past 200k ids so it is remote, but the refusal posture should be named. (correctness)
- §Risks write-amplification row: "already an accepted `026` posture" understates the change — `026` mutations were operator-paced on a hand-curated document; here they are traffic-paced on a document that grows toward ~30–64 MiB. The mitigation (one mint per key ever) is doing more work than the row admits. (performance)
- The two mint-rule findings ride the correctness seat's likely read; I raise them because both are closure arguments for mechanism removals the design makes explicitly.
